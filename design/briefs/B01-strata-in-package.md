# B1 Strata in the package

**Status.** Open.

**Topics.** [Topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages), with [topic 38, §2](../topics/38-problem-setups-and-user-functions.md#2-designs) for the functions that a problem hands to the framework.

**Supersedes.** None.

## Scope

The brief settles how the five strata of the overview ([§3](../overview.md#3-layers)) take shape in the package mhdpy: the subpackages that hold them and their names, the imports that the rule of use allows between the strata and within each of them, where the tests of each stratum lie and whether the rule binds them, and how the rule is checked. It leaves the modules within each subpackage to the briefs of their stratum, the layout of the repository, the build and the dependencies to the brief on the package and its installation, and the interface that the package offers its users to the briefs of stratum 5. It is the first brief and builds on no earlier one.

- [B1D1](#b1d1-the-subpackages-of-the-strata) The subpackages of the strata: decided.
- [B1D2](#b1d2-the-rule-between-the-strata) The rule between the strata: decided.
- [B1D3](#b1d3-the-rule-within-a-stratum) The rule within a stratum: decided.

Still to be written: the place of the tests, and the check of the rule.

## B1D1 The subpackages of the strata

**Decision.** In the context of a package that must hold the five strata of the overview, facing imports whose stratum should be plain and a check that should cover every later module, one subpackage per stratum, named `infrastructure`, `mesh`, `core`, `physics` and `driver` (option A), is chosen over one subpackage per component (B). This achieves readability, and extensibility through a check that covers every new module, accepting import paths one level longer. Decided on 2026-11-09, as recommended, except that stratum 1 bears its name in full rather than as `infra`, since a full word reads at once while an abbreviation must be learnt.

**Question.** The strata need a form in the package before the first module of stratum 1 is written, since every import names it and the check of the rule reads it. Each stratum can become one subpackage, or each component a subpackage of its own, with the strata kept only in the configuration of the check. The subpackages also need names. [Topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages) covers how pyro and Ulula are packaged, and the syntheses record how the references divide their code: [Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation) and [3.5](../references/ulula-synthesis.md#35-units), [pyro 3.2](../references/pyro-synthesis.md#32-grids-and-data) and [3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters), [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop) and [Performance in Python 3.9](../references/performance-in-python-synthesis.md#39-pace-components-compiled-at-initialisation).

**Option A: one subpackage per stratum.** Five subpackages directly below `mhdpy`, one to a stratum, each holding the modules of its components and named after the overview: `infra`, `mesh`, `core`, `physics` and `driver`. Ulula divides its package by role rather than by component: `utils`, `physics` with its constants and units, `core` with the solver, its driver and its plots, `setups` with the problems, and `examples` ([Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation), [3.5](../references/ulula-synthesis.md#35-units)). Pace keeps its dynamics, its microphysics and its utilities in separate packages ([Performance in Python 3.9](../references/performance-in-python-synthesis.md#39-pace-components-compiled-at-initialisation)). For mhdpy, the place of a module names its stratum, so that an import shows at a glance whether it runs downwards, and a stratum can be read as one folder while it is built. The check names five subpackages and covers every later module without change, extensions included, since the overview assigns each extension to a stratum ([§3](../overview.md#3-layers)). Import paths grow by one level, as `mhdpy.core.riemann`, and a listing shows the folders in alphabetical order rather than in that of the strata. A component whose code spans strata is split as the overview assigns it, so that the standard boundaries lie in `mesh` and the characteristic ones in `core`.

**Option B: one subpackage per component.** Each component a subpackage directly below `mhdpy`, such as `eos`, `riemann` or `cooling`. Athena++ gives each component a folder of `src/`, among them `eos`, `hydro`, `reconstruct`, `bvals` and `pgen` ([Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop)), and pyro gives each solver a package of its own beside `mesh` and `util` ([pyro 3.2](../references/pyro-synthesis.md#32-grids-and-data), [3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). The strata then exist only in the configuration of the check, as an ordered list of groups of subpackages. For mhdpy, import paths are one level shorter, as `mhdpy.riemann`, and the tree resembles that of Athena++. The stratum of a module no longer shows from its place, so that a reader looks it up in the configuration or in the overview. Each new component must also be entered in the configuration, or it escapes the rule unnoticed, unless a further test requires every subpackage to belong to a group. The risk grows with every extension.

**Experiments.** None, since the options differ in how the code reads and in what the check covers, which no measurement decides.

**Recommendation.** Option A, since the tree then shows the strata of the overview, and the check covers every later module, extensions included, without being changed. Its names follow the overview, shortened where the overview's name is long: `infra` for the infrastructure, `core` for the numerical core and `driver` for the driver and problems. The option serves readability, the third priority of §1, and extensibility, the fourth, and gives up none.

**Set aside.** Option B would return if components came to move between strata often, since a move then changes only the configuration of the check, while under option A it changes every import of the component.

## B1D2 The rule between the strata

**Decision.** In the context of five subpackages built from the bottom up, facing strata that must each be readable and testable alone while all use the infrastructure, imports from any stratum below and none above, those for type checking alone included (option A), are chosen over imports from the stratum directly below only (B) and no rule (C). This achieves readability, and extensibility through points of extension declared below, accepting that no stratum holds the objects of one above it, as the block of Athena++ holds the physics. Decided on 2026-11-09, as recommended.

**Question.** The subpackages of [B1D1](#b1d1-the-subpackages-of-the-strata) need a rule for the imports between them before the first module is written, since every import obeys it and the check enforces it. The rule also fixes how a lower stratum calls code above it, as the core calls the sources of the physics, and how the package `mhdpy` stands to its strata. To be read first are [§3](../overview.md#3-layers) and [§5](../overview.md#5-crosscutting-concepts) of the overview and [topic 38, §2](../topics/38-problem-setups-and-user-functions.md#2-designs), on how the references hand the functions of a problem to the framework, with the imports of the references in [Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation), [pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters) and [Athena 3.2](../references/athena-synthesis.md#32-arrays-the-mesh-and-its-blocks).

**Option A: any stratum below.** A stratum imports any stratum below it and none above, imports for type checking alone included, and reaches code above only through objects handed down at run time, in a form that it declares. Ulula keeps to such a rule in practice ([Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation)), and all references hand the functions of a problem to the framework rather than let the framework import them ([topic 38, §2](../topics/38-problem-setups-and-user-functions.md#2-designs)). **[GK]** [Buschmann et al.](#buschmann-et-al-1996) (1996) call such layers relaxed, and let lower layers reach upper ones through callbacks. For mhdpy, every stratum uses the services of those below it directly, above all the parameters, units and kernels of stratum 1 ([§3.1](../overview.md#31-infrastructure) of the overview). A stratum can be read and tested with the strata below it alone, as the overview demands of strata built before those above them exist ([§3](../overview.md#3-layers)). The points of extension of §5 become forms declared below, such as a protocol of [PEP 544](#pep-544) for a source, which a module of the physics satisfies without the core importing it. The block of Athena++, which creates and holds the objects of the physics, is excluded, so that the briefs of strata 2 and 3 must let the core or the driver hold them. The package `mhdpy` imports no stratum when it is loaded, since Python runs it before any of its subpackages ([import system](#python-import-system), §5.2.1), so that an import of the driver there would load all five strata with any one of them.

**Option B: the stratum directly below only.** A stratum imports only the stratum directly below it, and code above is reached as in option A. No reference keeps such a rule. **[GK]** [Buschmann et al.](#buschmann-et-al-1996) (1996) call it strict layering, which confines the effect of a change to the layer above and so eases maintenance, at a cost in flexibility and efficiency. For mhdpy, stratum 2 must pass on to the strata above the parameters, units and kernels of stratum 1, which it does not use itself. Such wrappers cost readability and shield little, since every stratum needs the infrastructure.

**Option C: no rule between the strata.** The strata order the overview but not the imports, as in Athena++, whose block and physics point to each other, so that 47 pairs of the folders of `src/` include each other ([Athena 3.2](../references/athena-synthesis.md#32-arrays-the-mesh-and-its-blocks)), and in pyro, whose `mesh` and `util` import each other ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). **[GK]** In Python, a cycle of imports leaves one of its modules half loaded while the other runs, which pyro works around by an import within a function. For mhdpy, a stratum may hold the objects of any other, as the block of Athena++ holds the physics. Nothing then keeps a lower stratum testable without those above it, as the overview requires ([§3](../overview.md#3-layers)). As the strata above do not exist while a lower one is written, the option differs from option A only in later changes and extensions.

**Experiments.** None, since the options differ in what the code may import, which no measurement decides.

**Recommendation.** Option A, since each stratum then stays readable and testable with the strata below it alone, while every stratum uses the infrastructure directly. It serves readability, the third priority of §1, and extensibility, the fourth, as the objects handed down make the points of extension explicit. It gives up none above them, since the results do not depend on the direction of the imports, and the points of extension are called once per step or stage rather than once per cell.

**Set aside.** Option C would return if a design that needs cycles between strata, such as a block that holds the objects of the physics, proved necessary, as the brief on the domain in blocks might find.

## B1D3 The rule within a stratum

**Decision.** In the context of the modules of one stratum, facing components that build on each other within it, imports without cycles (option B) are chosen over free use (A) and independent components (C). This achieves readability, as each module can be read and tested with the modules that it imports, accepting that two modules which would need each other must be split or composed. Decided on 2026-11-09, as recommended.

**Question.** [B1D2](#b1d2-the-rule-between-the-strata) orders the strata, but not the modules within one, which need a rule of their own before the first modules of stratum 1 import each other. The rule shapes how the components of a stratum work together, for instance whether the integrator imports the Riemann solver that it calls or is handed it. To be read first are [Performance in Python 3.1](../references/performance-in-python-synthesis.md#31-agate-interfaces-and-implementations), [3.6](../references/performance-in-python-synthesis.md#36-pyexafmm-a-data-oriented-design-around-numba) and [3.9](../references/performance-in-python-synthesis.md#39-pace-components-compiled-at-initialisation), on codes that compose their components, and [pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters), whose solvers build on one another.

**Option A: free use.** The modules of a stratum import each other as they need, cycles included. pyro lets its parts import each other in this way, so that `mesh` and `util` form a cycle, which an import within a function works around ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). **[GK]** For mhdpy, nothing needs to be planned, but each cycle risks a module that is half loaded when another uses it, as option C of [B1D2](#b1d2-the-rule-between-the-strata) sets out, and the modules of a cycle can be read and tested only together.

**Option B: no cycles.** The modules of a stratum import each other freely, as long as their imports form no cycle, so that they can be ordered from those that import nothing of the stratum to those that build on the most. Ulula's subpackages form such an order ([Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation)), and pyro's solvers build on one another, as `incompressible` on `burgers` ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). **[GK]** The contract of acyclic siblings of [Import Linter](#import-linter) checks this level by level, counting the imports of the descendants of each sibling. For mhdpy, a stratum is read and tested from the bottom up, as the strata are, one module with those that it imports. The integrator may import the solvers that it calls, so that composition is needed only where B1D2 already demands it, across strata.

**Option C: independent components.** The components of one kind within a stratum, such as the Riemann solvers or the limiters, import nothing of each other, and the module that uses them is handed them as objects. AGATE composes interfaces and implementations in this way at run time ([Performance in Python 3.1](../references/performance-in-python-synthesis.md#31-agate-interfaces-and-implementations)), and Pace lets a scientist replace its reconstruction without changes elsewhere ([3.9](../references/performance-in-python-synthesis.md#39-pace-components-compiled-at-initialisation)). PyExaFMM keeps its operators separate, so that each can be tested on its own, at the price of a passage between Numba and Python for each call ([3.6](../references/performance-in-python-synthesis.md#36-pyexafmm-a-data-oriented-design-around-numba)). **[GK]** The contract of independence of [Import Linter](#import-linter) checks such groups, indirect imports included. For mhdpy, a new solver then joins without touching the others, which serves extensibility. The kinds of components, however, are defined by the briefs of each stratum rather than by B1, and a rule for all the modules of a stratum would forbid the integrator to import any solver, which would push all composition up to the driver.

**Experiments.** None, since the options differ in what the code may import, which no measurement decides.

**Recommendation.** Option B, since each module of a stratum can then be read and tested with the modules that it imports alone, as each stratum can with the strata below it, while the modules of a stratum may still build on each other. Option C fits groups of components of one kind, which the briefs of each stratum name: such a brief may declare its group independent and add it to the check. The option serves readability, the third priority of §1, and gives up none above it.

**Set aside.** Option C returns for a group of components of one kind once the brief of its stratum declares the group independent and adds it to the check.
