# mhdpy: A Python-first Package for (Magneto)Hydrodynamics

> This document gives an architectural overview of the mhdpy package. Decision briefs are constructed based on reference (M)HD-codes (like Athena++), larger bodies of text (like the Computational Astrophysical Hydrodynamics book and Pyro-code by Michael Zingale), and experiments that provide, e.g., performance indications of crucial choices within the code. The decisions live in [`decisions/`](decisions/README.md), with each file stating clearly **what** was decided and **why**. The brief on each choice provides background from the reference codes ([Pyro](https://python-hydro.github.io/pyro2/index.html), [Ulula](https://bdiemer.bitbucket.io/ulula/index.html), [Athena(++)](https://www.athena-astro.app/), and [ZEUS](https://zeus3d.ca/zeus3d/version3.6/home.html)) and evidence from the experiments. Based on this the different options are presented with a recommendation that fits the purpose of this code.

## 1. Purpose

### 1.1 Goals

The goal with mhdpy is to build a framework for astrophysical (magneto)hydrodynamical simulations within Python. It is meant for use in educational and scientific work: from standard verification problems to production-scale runs of the size used in published studies. It is recognised that these are ambitious targets that might lead to conflicts needing proper prioritisation of goals. However, the most important point (to the author) of building mhdpy is **learning**: 
- learning how to write *scientifically applicable*, i.e. accurate, code (physics that is demonstrably correct and extensible);
- learning to build a *large, multi-layered* software project robustly, in a form that others can pick up easily.

Besides learning, the other goal is **production-scale** runs. The inspiration for this coding project arose from prior work with production-grade MHD simulation software. This experience is on simulations of the scale of work by [Armillotta, Fraternali, and Marinacci 2016](https://ui.adsabs.harvard.edu/abs/2016MNRAS.462.4157A/abstract) (Galactic fountain clouds leading to coronal condensation to feed star formation), i.e. a simulation grid of roughly 4000x1000 cells without mesh refinement.

### 1.2 Scope

The *eventual* scope of mhdpy encapsulates all physics-modules that are implemented by state-of-the-art (magneto-)hydrodynamics codes (like Athena++), with a focus on astrophysical applications. This ranges from compressible hydrodynamics with general equations of state all the way to the inclusion of lagrangian particles for dust simulations. The whole scope shapes the architecture from the start, even for parts that will be implemented much later. In particular, the lower layers must be able to accommodate them without significant redesign.

### 1.3 Success criteria

The success of mhdpy is judged against four criteria, each formulated such that it can be checked rather than asserted. The learning goal is deliberately not among them. It is not a property of the finished code that could be measured, but is served by the way mhdpy is developed: every architectural choice is made explicitly in a decision brief, grounded in the reference material and supported by experiments.

**Correctness:** No physics module is considered complete before it is verified against problems with known (analytic) solutions. For smooth problems, the measured order of convergence must match the formal order of the scheme. For problems with discontinuities, results are compared with exact or reference solutions. Conserved quantities must be conserved to round-off error wherever the boundary conditions permit. Test problems are identical to the suites used by state-of-the-art reference codes. A capability counts as implemented once the corresponding reference tests are reproduced.

**Production Capability:** As a performance target a run at research-scale (similar to [Armillotta, Fraternali, and Marinacci 2016](https://ui.adsabs.harvard.edu/abs/2016MNRAS.462.4157A/abstract)) should finish overnight (within roughly twelve hours) on the development machine and within an hour on a small multi-core server. Such a run is two-dimensional, about 4 million cells (4000x1000), and includes hydrodynamics with radiative cooling, thermal conduction, and a passive scalar (in the form of metallicity). The cost of a run is roughly set by the total number of cell updates. This means that the runtime (barring any overhead) is simply the total number of cell updates divided by the cell update rate, i.e. cell updates per second. This is a criterion that can be easily tracked during development and a goal is set: A first estimate places the number of required cell updates at approximately $10^{11}$. This means that the overnight run on the development machine requires roughly $2 x 10^6$ cell updates per second and $3x10^7$ in the performance target of the small server. This estimate must be refined once representative runs exist.

**Extensibility:** New physics modules, like alternative cooling function, or a new Riemann solver can be added without changes to the framework. Every module beyond the hydrodynamics core serves as a test of this criterion: it must plug-in through the same interfaces.

**Usability:** Ease-of-use ties in with the extensibility criterion. However, it goes further than just being able to extend the code. mhdpy should install on macOS and Linux with a singular `pip` or `uv` command such that a newcomer can run a standard test problem within minutes by just following the documentation.

### 1.4 Priorities

The above-mentioned goals will, at times, pull in different directions. The decision briefs need a consistent way to resolve such conflicts of interest. Therefore, a ranking is made to apply priorities to criteria: Correctness always comes first: in scientific work, a result that is fast, code that is readable or convenient to work with holds no value if the result is simply wrong. Performance comes second, production-scale runs are a clear target and will contribute to the adoption of mhdpy. Therefore, it is decided that performance takes precedence over extensibility and usability. Sacrifices in terms of readability must be made if performance is to be achieved at times. Readability follows, since the code must remain understandable to serve the learning goal. Moreover, readable code improves its maintainability as it grows and writing extensions becomes very hard if the code to interface with is difficult to understand. Finally extensibility and ease-of-use come in. This means that less focus will be placed on the API, but it is not ignored completely. One exception is made to this ordering: installation must be as simple as possible, preferably through a single `pip` or `uv` command, whatever the ranking would otherwise imply. Every recommendation within a decision brief states where it falls in this ordering.

## 3. The architecture

This section brings the decisions of all briefs together into one description of mhdpy, as it is to be built. It follows the life of a simulation more than the order of the briefs: first the foundations on which everything is developed, then the numerical method, the way data is held and computed on, and finally how physics is added, how a simulation runs, and how users and files meet it. References in parentheses point to the sub-decisions in the briefs, where the options, the evidence and the reasoning can be found.

The layers of mhdpy and the components that go into each of them are shown below. Every layer builds only on the layers beneath it.

```text
L7  Files & interface          snapshots, restart files, history, log, reader, parameter files (TOML),
                               problem library, mhdpy command, public interface
L6  Simulation & driver        Simulation (set-up, step, run), hooks, output schedules, restarts,
                               clean endings, run report
L5  Time integration           integrators (stage tables), source coupling by stiffness,
                               super-time-stepping, time-step control
L4  Numerical building blocks  reconstruction, limiters, Riemann solvers, equation of state,
                               CT and edge EMFs, diffusive fluxes, floors, first-order flux correction
L3  Execution                  phases, phase groups, thread pool, dynamic chunks of blocks
L2  Communication              exchange plans, boundary conditions, restriction & prolongation,
                               flux registers
L1  Data & geometry            variable registry, State, Grid (one block), coordinate system,
                               Mesh (logical locations, Morton order)
L0  Foundation                 Cython kernels (compiled and uncompiled), worker threads, reductions,
                               declared parameters, units, logging

    Physics modules (hydrodynamics, MHD, passive scalars, cooling, conduction, gravity, user modules
    and problems) sit across L1-L5: each declares its variables (L1), its boundary behaviour (L2) and
    its phases (L3), selects the building blocks (L4) and the coupling (L5) it needs, and plugs in at
    named extension points. The framework places and checks the contributions.

    Designed in, built later: MPI (L0, L2), GPUs (L0), mesh refinement (L1, L2), higher-order, WENO
    and DG schemes (L4, L5). Tooling and verification apply to every layer.
```

### 3.1 Foundations: tooling and verification

mhdpy is developed on GitHub, with continuous integration through GitHub Actions (D01.1), under the BSD-3-Clause licence, with the licences of any third-party material kept in `LICENSES/` (D01.3). It supports Python 3.13 and 3.14 and follows the rolling three-year window of SPEC 0, adopting new Python versions as soon as its dependencies provide wheels for them (D01.2). The free-threaded interpreter is a first-class target from 3.14 on, next to the standard one (D05.4). The package uses the src layout, with the tests of each component next to it and shipped with the package (D01.4). Runtime dependencies carry lower bounds only, set at the version current when they are added; the lockfile is committed, and every experiment of the decision briefs is a self-contained script with its own lockfile (D01.6). Code is formatted and checked by ruff at 120 characters (D01.7), type-checked by pyright, strictly at interfaces and more leniently inside numerical kernels (D01.8), tested with pytest (D01.9), and documented with NumPy-style docstrings rendered by Sphinx with MyST (D01.10, D01.11). It is built with meson-python and shipped as wheels for every platform through cibuildwheel (D04.5, superseding D01.5), so that installation stays a single `pip` or `uv` command.

Correctness, the first priority, is demonstrated rather than asserted. Components are developed test-first: their requirements are written down as tests before the code that fulfils them (D02.1). The tests are layered in four levels. Unit tests check single components, invariant tests check symmetries and conservation, convergence tests check that a scheme reaches its formal order, and the benchmark problems of the state-of-the-art reference codes form the culmination (D02.1). Reference solutions are computed rather than stored (D02.2). Results are not compared bit for bit with stored data, which cannot hold across the platforms and library versions mhdpy is tested on; instead, tight error thresholds guard against regressions, and bit-for-bit comparison is reserved for invariants within one run (D02.3). The formal order is verified with limiters off, while production configurations and discontinuous problems are held to thresholds set 10 % above the measured errors (D02.4). Component properties are tested with Hypothesis (D02.6). A fast tier of tests runs on every change, and a full tier weekly, on demand and before releases (D02.5). Users install the tests with the `mhdpy[test]` extra and run them with `pytest --pyargs mhdpy` (D02.7). Line and branch coverage is kept at 100 %, with every exclusion justified where it is made (D02.8), and a verification matrix in the documentation records what has been verified (D02.9).

### 3.2 The numerical method

mhdpy solves the equations of (magneto)hydrodynamics with an unsplit, finite-volume Godunov method (D03.1, D03.4), in total energy, to which a dual-energy variable can be added as an extra scalar (D03.2). The magnetic field is kept divergence-free by constrained transport with upwinded edge electric fields (D03.5). Passive scalars are native, as conserved densities whose fluxes follow the mass flux (D03.6). The method is second order to begin with, but higher-order schemes, and experimental WENO and discontinuous-Galerkin discretisations, are explicitly in scope. Provisions in the interfaces keep the door open to them. The spatial operator is interchangeable, mapping the state to its time derivative. Data may be cell-, face-, edge- or node-centred, and multi-valued per cell. The magnetic field may be registered face- or cell-centred, so that divergence cleaning remains possible where constrained transport does not apply. The ghost width is a parameter, the meaning of stored values (cell average, point value, coefficient) is explicit, initial conditions are functions rather than values, the time-step limit comes from the scheme, and boundary and refinement operators have a selectable order (D03.1, D03.3).

The building blocks of the method are components with fixed interfaces: the Riemann solver, the reconstruction with its limiter, the equation of state and the geometry (D10). They are selected at set-up, and every combination in use is compiled as its own specialisation through Cython's fused types, so that a selection costs nothing at run time (D10.1). Each operation is written once, with the direction as a constant argument, and the compiler produces the code for each direction (D10.2). The equation of state is general, beginning with the ideal and isothermal gas, with tabulated equations of state to follow (D10.3). The Riemann solvers HLL, HLLC, HLLD, Roe and LLF are available from the start, with HLLC as the default for hydrodynamics and HLLD for MHD (D10.4). Reconstruction offers piecewise-linear reconstruction in its form for nonuniform grids, characteristic projection and the piecewise-parabolic method; WENO-Z follows, and further methods are noted for later (D10.5). Densities and pressures are kept physical by a first-order flux correction, which recomputes cells whose update would turn density or pressure negative with first-order fluxes on their faces and so stays conservative, with floors as the last resort; both are counted and reported (D10.6). All kernels follow a fixed set of rules that keep them symmetric and reproducible, and tests check them (D10.7).

In time, the method of lines is integrated with VL2, SSP-RK2 or SSP-RK3, with RK1 for tests; integrators of higher order are of explicit interest and follow (D11.1). Integrators are data: low-storage stage tables, combined by one compiled kernel, so that a new integrator is a table rather than a code path (D11.2). This is the pattern found throughout mhdpy, in the phases of a step and in the exchange plans as well. Sources are coupled according to their declared stiffness. Non-stiff sources enter the stages, while stiff sources such as radiative cooling are Strang-split around the hyperbolic update and integrated cell by cell (D11.3). Diffusion, such as thermal conduction, is integrated by RKL2 super-time-stepping, split around the hyperbolic update in the same way (D11.4). The time step follows the CFL condition together with the limits of physics modules and users. Its growth is bounded, it is shortened to reach output times exactly, and the constraint that limited it is recorded; steps are not rejected, since floors and flux corrections already repair invalid cells (D11.5). All refinement levels advance with one time step (D11.6). A step thus has a fixed order: half of the stiff sources, half a super step of diffusion, the stages of the integrator, the other halves, and the new time step.

### 3.3 Kernels and parallelism

All numerical work is done by kernels written in Cython's pure Python mode (D04.1). The same source runs compiled, as fast as C, and uncompiled, as plain Python, in which form it is measured for coverage; both give bit-for-bit identical results (D04.3). Kernels are functions over arrays with explicit loops, and every operation on whole blocks is compiled, while Python only orchestrates (D04.2). Each call covers a range of blocks, which the kernel loops over in compiled code without the GIL, so that the Python between calls is negligible on either interpreter (D09.2, superseding D04.2 in part). Arithmetic is in double precision throughout (D04.4). The distributed wheels are compiled for every processor of a platform; users who want more speed on one machine can build mhdpy for their own processor (D04.6).

Parallelism is organised around blocks. A process divides its blocks among workers, each of which updates whole blocks with serial kernels; there is no parallelism within a loop and no OpenMP (D05.2). The workers are Python threads, and development focuses on the free-threaded interpreter, while the standard interpreter is kept performing well (D05.3, D05.4). One node is the target now, but distributed memory is designed in: blocks own their data, all communication goes through one layer and all reductions through one function, so that MPI can be added later through mpi4py as an optional extra (D05.1). The state of a simulation is bit-for-bit independent of the number of workers, the scheduling and the decomposition into blocks, because minima are exact and sums are combined in a fixed block order (D05.5). Since the blocks of a process are stored together as one array, a later path to GPUs remains possible without restructuring the data, although every kernel would need an implementation of its own there (D05.6).

A step is a fixed sequence of phases, described as data: named operations with declared inputs and outputs, registered by the integrator and the physics modules (D09.1). The main thread runs the phases in order on a thread pool (D09.4). Workers claim chunks of consecutive blocks in Morton order dynamically, so that no worker waits while others finish uneven shares (D09.3). By default there are as many workers as logical CPUs available to the process (D09.5). The main thread waits for the workers only where a dependency crosses blocks: after an exchange, for a reduction over all blocks, and around a global solver. Consecutive phases that touch only their own blocks are merged into one group, worked out at set-up from their declarations (D13.3).

### 3.4 Data, mesh and geometry

The data of a simulation is described in three layers (D06, D07.1). A grid is the geometry of one block and holds no data. The mesh arranges the blocks and knows their neighbours, without knowledge of the physics. The state holds every variable of every block of a process. Together with the block and the coordinate system, these names are fixed (D07.1).

The state stores its data as a struct of arrays, with x contiguous in memory: each array is indexed `[block, var, k, j, i]` (D06.1, D06.2). Every array is three-dimensional, and vector quantities always have three components; a direction with a single cell simply has no ghost cells, and kernels are written direction by direction (D06.3). There is one array per process for each centring and role, in which each physics module owns a range of variables (D06.4). Face-, edge- and node-centred data is padded to a common shape, so that the components of a staggered quantity share one array (D06.5). Every variable is declared in a registry with its metadata (centring, role, boundary and refinement behaviour, output and restart flags), filled at set-up and then frozen (D06.6). Conserved and primitive variables are both stored (D06.7). Users meet the data through named accessors, not raw indices.

The mesh consists of blocks of identical shape (D07.2). Their size is free in each direction as long as the blocks tile the grid, with an automatic default of about 64 cells per direction in two dimensions and 32 in three (D07.3). Blocks are identified by their logical location, kept in a lookup table, with the Morton order as their canonical order (D07.4). The ghost width is set once at set-up, as the largest requirement of the selected operators and boundary conditions (D07.5). The geometry of the orthogonal coordinate systems is held as separable one-dimensional arrays per direction, behind a coordinate-system interface designed for the general case, so that distorted meshes and the coordinate systems of general relativity remain possible (D07.6). Mesh refinement is designed in now and implemented later (D07.7).

### 3.5 Boundaries and communication

Ghost zones are filled through exchange plans: lists of copies built once from the mesh and executed by a backend, which copies locally now and will communicate through MPI later, from the same plans (D08.1). Each block fills its ghost zones from all its neighbours directly. The copies are made by a compiled kernel, one call per worker and stage (D08.2). Values on faces and edges shared by two blocks are computed independently by both and are identical by construction, so no averaging is needed; a test asserts that they agree (D08.3). Physical boundary conditions act on primitive variables, one condition per face of the domain, with overrides per variable (for example a fixed metallicity at an inflow) and user functions (D08.4). For refinement, restriction and prolongation operators are registered per variable, with the defaults of the reference codes (D08.5), and fluxes and electric fields at fine/coarse boundaries are corrected within the same step through flux registers (D08.6).

### 3.6 Physics modules

A physics module is a declaration made once at set-up (D12.1). It declares its variables with their metadata, its phases or attached passes with the arrays they read and write, its time-step limits, its boundary and refinement behaviour, its parameters, and any internal state that must survive a restart. Together these form its integration contract, which the framework places, orders and checks; nothing in a module runs per block in Python. The equation systems, hydrodynamics and MHD, call the passes of attached modules within each block, on that block's scratch data, through C function pointers resolved once per block (D12.2). Passive scalars, dual energy and explicit diffusive fluxes attach in this way, as do the flux registers and the first-order flux correction. Modules attach at named extension points (equation system, flux contribution, diffusion, non-stiff source, stiff source, global solver, boundary condition, refinement criterion, diagnostic), with generic phases at a declared place as an escape hatch; built-in modules and user modules use the same points (D12.3). Kernels that work per face or per substep are compiled, while simple module code (sources, initial and boundary conditions, diagnostics) may be written in NumPy, always receiving a range of blocks, never a single block (D12.4). The equations are solved in dimensionless code units, with a unit system defined at set-up providing the conversions that modules with physical constants need (D12.5). Compiled modules outside mhdpy are packages built against its published `.pxd` declarations.

### 3.7 Running a simulation

A simulation is one `Simulation` object with explicit stages (D13.1). Its set-up follows a fixed order. It collects and validates the modules' declarations, freezes the registry, builds the mesh and allocates the state, assembles the phases and extension points, applies the initial conditions, runs the first exchange and computes the primitive variables and the first time step. It then reports the integration contract of the whole simulation. It is advanced by `step()` or by `run(until=…)`, which stops at a simulation time, a number of cycles, a wall-clock limit or a condition; user work runs at hook points between steps, after a step and before an output (D13.2). Every output has its own schedule, in simulation time, cycles or wall-clock time, and output times are reached exactly (D13.4).

A restart file contains everything the continuation depends on, exactly and in binary: every array that is not derived, the time, the cycle and the state of the step control, the mesh and the unit system, every module's parameters and internal state (including random-number generators), and the output schedules (D13.5). A restarted run then equals the uninterrupted one bit for bit, also with a different number of workers or a different block size. A run ends cleanly in every case (D13.6). With a wall-clock limit it stops in time to write a restart file. On an interrupt or termination signal it finishes the current step, writes a restart file and exits. After a step that leaves non-finite values despite floors and flux corrections, it writes the failed state for inspection and reports where the step failed. The check costs nothing extra, since it is part of the reduction the time step already makes. While running, a log line at a chosen cadence reports the cycle, time and step, the limiting constraint, cell updates per second, the counts of floors and flux corrections and the memory in use, and every run ends with a summary of its throughput per group of phases (D13.7).

### 3.8 Files and users

Snapshots and restart files are HDF5 files written through h5py (D14.1). Their block data follows the layout of the HDF5 output of the reference codes (`.athdf`), which yt, VisIt and ParaView read as they are, and a group of mhdpy's own adds what that layout has no place for. That group holds the registry, the face-centred data, the unit system, every module's declarations, parameters and state, the schedules and the step control, and the provenance of the file: format and mhdpy versions, interpreter, compiler, build options and platform (D14.2). Snapshots, restart files and history are separate kinds of output in one format, written by one writer. A restart file is a complete snapshot in double precision, so that restart files and snapshots are interchangeable for analysis, and the state of a failed step is written in the same way (D14.3). The history is a text table with one line per entry, written at full precision and flushed line by line, holding the global sums, the quantities declared by modules and users, and the diagnostics of each step. The log is plain text (D14.4). Each output chooses its variables, including derived quantities, its precision (double by default, single on request) and its compression, which is lossless zstd by default (D14.5). Files are written by a background thread while the run continues, under a temporary name and renamed into place once complete, so that an interruption never damages the last good file (D14.6). mhdpy has its own reader, which returns named variables, coordinates, units and parameters and opens a restart file as a `Simulation` ready to run; parameters declared changeable, such as the end time, can be changed on restart (D14.7).

Users meet mhdpy through one Python interface, `Simulation(problem, parameters=…)`, whose parameters come from a dictionary, a parameter file, or both (D15.1). Every parameter is declared by its module with a type, a default, a check, its documentation and whether it may change on restart. Values are resolved in layers: the defaults (or, on restart, the restart file's record), then a TOML parameter file, then overrides from the command line or a dictionary (D15.2, D15.3). Unknown names, wrong types and values out of range are refused before the run starts, and the resolved set is recorded in every output. A problem is itself a module, declaring its parameters, the modules it needs, its initial conditions and, optionally, its own boundary conditions, sources, hooks and exact solution; numerical choices remain parameters, so that every problem runs with every scheme. The verification and benchmark problems of D02 form a library that comes with mhdpy (D15.4). The `mhdpy` command runs simulations and also lists problems, writes a parameter template for any of them, shows what a run would do without running it, and reports the installation (D15.5). Messages go through Python's `logging`: warnings and progress to the terminal, every detail to the log file in the output directory (D15.6). The public interface (the Python interface, the command line, parameter names, the file format and the declarations for compiled modules) is explicit and versioned semantically from 1.0, and files of every earlier format version remain readable (D15.7).

### 3.9 Designed in, built later

Several capabilities are part of the architecture but not of its first implementation. The provisions for them are made now, so that adding them later does not require a redesign. Distributed memory through MPI is the largest of them, including the writing of files from several processes (D05.1, D14.6), followed by mesh refinement (D07.7, D08.5, D08.6) and, further away, execution on GPUs (D05.6). On the numerical side, spatial schemes of higher order, WENO and discontinuous Galerkin are provided for, with divergence cleaning where constrained transport does not apply (D03.1, D03.3, D03.5), as are integrators of higher order (D11.1), a dual-energy variable (D03.2), tabulated equations of state (D10.3) and further reconstruction methods (D10.5). The coordinate-system interface leaves room for distorted meshes and the coordinate systems of general relativity (D07.6).

Other options were considered and set aside for now, but are noted as possible additions should a need arise: step rejection (D11.5), IMEX Runge–Kutta methods for sources that are both stiff and strongly coupled to the flow (D11.3), implicit diffusion with a global solver (D11.4), subcycling of refinement levels, which would supersede D08.6 (D11.6), compilation of user code at run time (D12.4), lossy compression with a bounded error (D14.5), and a reader of mhdpy's own for yt (D14.2).
