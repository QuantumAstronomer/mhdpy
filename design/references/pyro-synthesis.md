# Synthesis of pyro

This synthesis digests pyro, a two-dimensional hydrodynamics code written in Python, in its release 4.5.1, kept with its documentation as `References/Pyro/Code`. Two papers on the code complete the sources, kept in `References/Pyro/Docs`: the pyro paper (Zingale 2014, arXiv:1306.6883v3) and the paper in the Journal of Open Source Software (Harpole et al. 2019, arXiv:1902.08702v1), the JOSS paper. Additions found by web search, which fill gaps in these sources or check their claims, are marked **[GK]** and cited. A **[GK]** mark covers the rest of its paragraph or list item. Code is cited by its path in the repository and the name of a function or class, as in (`pyro/compressible/riemann.py`, `riemann_hllc`), and a page of the documentation by its path. A section sign without a named source refers to the pyro paper.

## 1. Overview

### 1.1 Origin, version and licence

pyro, short for python hydro (§1), was first written in 2003 and 2004 to help Michael Zingale understand the methods of computational hydrodynamics (`docs/source/history.rst`). It used the Numeric array package, with hand-written C extensions for the costly kernels, and was ported to numarray when that replaced Numeric. The present code, pyro2, was revived from 2012, rewritten for NumPy with kernels in Fortran through f2py, and later moved to numba. It served as a tool to learn the methods for research before they were built into production codes (acknowledgements of the pyro paper). The pyro paper of 2014 presents it as a teaching code, and its results were made with git version 3a17947.

The change log begins at version 2.0, the state towards the end of 2017, when fourth-order finite-volume methods had just been introduced (`CHANGES.md`). Version 2.1 brought documentation in Sphinx, unit tests on a continuous-integration service and a compressible solver with spectral deferred corrections, and 2.2 the shallow-water solver and tracer particles. Version 3.0 replaced the Fortran kernels by functions that numba compiles at run time, so that pyro is now written entirely in Python (JOSS paper). Version 3.1 is essentially that of the JOSS paper, which also names a `Pyro` class that runs the code from Jupyter notebooks as well as from the command line, and output in HDF5 instead of through Python's pickle module. Version 4.0 gave the source the standard layout of a Python package, published on PyPI and usable from anywhere. Versions 4.1 to 4.5 added solvers for the inviscid and viscous Burgers' equation and for viscous incompressible flow, spherical geometry in $r$ and $\theta$ for the mesh and the compressible solver, and problem setups written in Jupyter notebooks. A special relativistic solver, `compressible_sr`, was removed in 4.3.0. Version 4.5.1 brings fixes, tests on Python 3.14 and macOS, and a check that the fourth-order solvers run only on square cells.

The code is kept on GitHub as python-hydro/pyro2, and its documentation is published at python-hydro.github.io/pyro2 (`README.md`). In 2014 they were at github.com/zingale/pyro2 and bender.astro.sunysb.edu/hydro_by_example (§1). The package installs from PyPI as pyro-hydro. **[GK]** Release 4.5.1 is the tag 4.5.1 of python-hydro/pyro2, commit adaf5c5 of 24 July 2026, which on 29 October 2026 is also the head of its main branch. The local copy agrees with that commit in all 521 files, and lacks only 17 hidden files, such as those that configure continuous integration, linters and Zenodo. PyPI received release 4.5.1 on the same day. github.com/zingale/pyro2 is now a fork of python-hydro/pyro2, and commit 3a17947 dates from 11 June 2014.

### 1.2 Aims and scope

pyro is meant to show how the basic methods of astrophysical simulations work, and to prototype new ideas (`docs/source/index.rst`). The pyro paper explains the need for a teaching code (§1). The methods of astrophysical fluid flow mostly appear first in journals of applied mathematics, which astrophysics students rarely meet in their courses, and the few students who take up computational astrophysics each year cannot fill regular courses. Production codes such as Flash (Fryxell et al. 2000) and Castro (Almgren et al. 2010) favour performance and a breadth of options over simplicity and clarity. Experience with Flash, Castro and Maestro (Nonaka et al. 2010) has shown that the methods are best learned by coding them, or by substantial changes to an existing code, for which a simple code is a good start. Texts such as LeVeque (2002) on finite volumes and Briggs et al. (2000) on multigrid give the theory, but details such as the number of ghost cells each part of an algorithm needs come only from practice. In 2014 pyro implemented one method representative of astrophysical practice for each system of equations, took clarity over performance, and left variations and extensions to the students. Its algorithms are established ones. What pyro adds is a careful implementation aimed at teaching, with exercises to work through.

All solvers work in two dimensions (§1). Some key design questions of a solver do not arise in one dimension, two dimensions are complex enough that the step to three is then straightforward, and they allow grid effects and instabilities to be explored. All simulations use a single grid, without domain decomposition, and runtime visualisation can show the solution as it evolves (`docs/source/intro.rst`). Given the choice between clarity and performance, clarity is still taken, and pyro is not meant for demanding scientific simulations. It is intended for self-study, together with notes that derive the methods (§1), which the documentation identifies as Zingale's text, digested in `computational-hydrodynamics-synthesis.md` (`docs/source/notes.rst`).

By the time of the JOSS paper, pyro had also become a framework for prototyping solvers before they go into science codes. Its object-oriented design lets solvers reuse the core components. The fourth-order compressible solver with spectral deferred corrections served as the model for higher-order schemes in Castro, and the low Mach number solver for atmospheres, based on Maestro, is to prototype new low Mach number algorithms.

Release 4.5.1 holds 17 solvers in seven families, each solver a package under `pyro/`, and several families offer more than one method for the same equations (`README.md`; docstrings of the packages).

- Linear advection: `advection`, a second-order unsplit method after Colella (1990), with characteristic tracing and corner coupling; `advection_rk`, piecewise linear in space with Runge-Kutta integration in time; `advection_fv4`, fourth-order finite volumes after McCorquodale and Colella (2011), with fourth-order Runge-Kutta integration; `advection_weno`, a finite-difference method with WENO reconstruction and Lax-Friedrichs flux splitting; `advection_nonuniform`, for a velocity field that varies in space.
- Burgers' equation: `burgers`, a second-order unsplit method for the inviscid equation; `burgers_viscous`, which adds constant-coefficient viscosity, treated by Crank-Nicolson.
- Compressible hydrodynamics: `compressible`, the second-order unsplit piecewise linear method of Colella (1990), with a two-shock or HLLC approximate Riemann solver; `compressible_rk`, with Runge-Kutta integration in place of characteristic tracing; `compressible_fv4`, of fourth order after McCorquodale and Colella (2011); `compressible_sdc`, the same reconstruction with spectral deferred corrections in time; `compressible_react`, the method of `compressible` with reactions by Strang splitting.
- Shallow water: `swe`, a second-order unsplit method after Colella (1990).
- Diffusion: `diffusion`, second-order implicit diffusion by Crank-Nicolson, solved with multigrid.
- Incompressible flow: `incompressible`, a second-order cell-centred approximate projection method; `incompressible_viscous`, which adds viscosity.
- Low Mach number flow: `lm_atm`, a second-order approximate projection method for atmospheres.

`multigrid` solves elliptic equations with constant and variable coefficients, both for the solvers that need it and on its own (`README.md`; `docs/source/design.rst`). `particles` follows Lagrangian tracer particles in any solver with a velocity field (JOSS paper). In 2014 pyro had five solvers, for linear advection, compressible hydrodynamics, elliptic equations by multigrid, implicit diffusion and incompressible flow, all of second order in space and time (§1). At 4.5.1, `advection_fv4`, `compressible_fv4` and `compressible_sdc` are of fourth order and `advection_weno` reconstructs with WENO, while the other solvers are of second order.

The pyro paper foresaw solvers for MHD and for radiation hydrodynamics in the flux-limited diffusion approximation, examples of multiphysics such as diffusion with reactions and the viscous Burgers' equation, and unit tests (§4). Release 4.5.1 has the viscous Burgers' equation and unit tests, but no solver for MHD, radiation or diffusion with reactions. The README announces `lm_combustion`, a low Mach number solver for small-scale combustion, as in development. **[GK]** `lm_combustion` exists only on a branch of the repository, last changed in March 2018, as does `radhydro`, and a branch `mhd` was last changed in February 2019.

The pyro paper sets out the motivation and design of the code, summarises the algorithms of its five solvers with verification tests, and suggests extensions for students. ## 2. Numerical methods

Ten subjects group the numerical methods by solver family. `plan.md` lists them, with the steps that write them.

### 2.1 Grids, reconstruction and time integration

The package `mesh` holds what the solvers share: the finite-volume grid with its geometry, its boundary conditions and the transfers between grids, and the kernels for reconstruction and time integration.

#### 2.1.1 The finite-volume grid

Grid-based methods replace derivatives by differences on a grid, particle-based methods represent the solution by a set of particles, and both are popular in astrophysics, with strengths and weaknesses of their own (§3; Agertz et al. 2007; Hubber et al. 2013). pyro uses structured grids, logically Cartesian, on which one integer per dimension addresses a zone. They suit astrophysics, whose domains are seldom complex in shape, and make good use of processors with caches. A finite-difference grid stores values at points and discretises the differential form of the equations, while a finite-volume grid stores averages over zones and discretises the integral form. A cell-centred finite-difference grid is equivalent to a finite-volume grid to second order in $\Delta x$. pyro uses finite volumes, with integer indices $i$ for the zone centres and half-integer ones, $i - 1/2$ and $i + 1/2$, for the interfaces on either side (fig. 1). Its data structure does not distinguish centred values from averages, which suffices at second order, and the fourth-order methods convert between the two (`docs/source/mesh_basics.rst`).

A grid holds $n_x \times n_y$ zones with $n_g$ ghost cells on each side, one by default, so that its arrays span $n_x + 2 n_g$ zones in x (`pyro/mesh/patch.py`, `Grid2d`). The valid zones run from $i_\mathrm{lo} = n_g$ to $i_\mathrm{hi} = n_g + n_x - 1$, and likewise in y. The zone width is $\Delta x = (x_\mathrm{max} - x_\mathrm{min})/n_x$, with $[0, 1] \times [0, 1]$ as the default domain. Zone $i$ has its left edge at $x_\mathrm{min} + (i - n_g)\Delta x$, its right edge one $\Delta x$ further and its centre midway, and the grid stores these coordinates both as one-dimensional arrays and over the whole two-dimensional index space, ghost cells included. The grid knows nothing of boundary conditions, which can differ between variables. Grids coarser or finer by an integer factor, with the same extent and number of ghost cells, serve multigrid.

#### 2.1.2 Cartesian and spherical geometry

Two subclasses of the grid add its geometry, flagged by `coord_type` (`pyro/mesh/patch.py`). On the Cartesian grid, with the coordinates $x$ and $y$, the face normal to x has the area $\Delta y$ and the face normal to y the area $\Delta x$, per unit depth, a zone has the volume $\Delta x \Delta y$, and the logarithmic derivatives of the areas vanish (`Cartesian2d`, `coord_type` 0). The spherical grid takes $x$ as the radius $r$ and $y$ as the polar angle $\theta$, a three-dimensional geometry reduced to two by axisymmetry, without velocity in $\phi$ (`SphericalPolar`, `coord_type` 1). It requires $0 \le \theta \le \pi$ and ghost cells at non-negative radii, and its default radial range runs from 0.2 to 1. Its zones have the lengths $\Delta r$ and $r \Delta\theta$, the latter at the zone centre. The lower radial face of a zone has the area $2\pi r_{i-1/2}^2 (\cos\theta_{j-1/2} - \cos\theta_{j+1/2})$, its lower polar face, a cone, the area $\pi \sin\theta_{j-1/2} (r_{i+1/2}^2 - r_{i-1/2}^2)$, and the zone the volume $(2\pi/3)(\cos\theta_{j-1/2} - \cos\theta_{j+1/2})(r_{i+1/2}^3 - r_{i-1/2}^3)$. The arrays hold the area of the lower face of each zone, so that its upper face is the lower face of its neighbour (`pyro/mesh/tests/test_patch.py`). The logarithmic derivatives of the face areas, per unit length along each direction, are $2/r$ and $\cot\theta / r$ at the zone centres. All these quantities are arrays over the whole grid, ghost cells included.

#### 2.1.3 Boundary conditions

There is a single grid, so every boundary is physical unless it is periodic (`pyro/mesh/array_indexer.py`, `ArrayIndexer.fill_ghost`). Each variable carries its own boundary conditions, one type for each of the four edges, so that a wall can reflect the density evenly and the normal momentum oddly (`docs/source/mesh_basics.rst`; `pyro/mesh/boundary.py`, `BC`). The types fill the ghost cells as follows.

- `outflow` copies the nearest valid zone into all ghost cells, a zero gradient.
- `periodic` copies the zones from the opposite side of the domain, and must be set on both sides.
- `reflect-even` mirrors the valid zones about the boundary, and `reflect-odd` mirrors them with a change of sign, so that the value vanishes on the boundary. `reflect` becomes `reflect-odd` on the boundaries normal to the direction given as `odd_reflect_dir`, and `reflect-even` elsewhere, as the normal velocity at a wall requires.
- `neumann` and `dirichlet` act as `outflow` and `reflect-odd` when homogeneous. For inhomogeneous conditions, a function of the coordinate along the boundary, evaluated on the grid when the condition is built, gives the gradient or the value on the boundary, and only the first ghost cell is set. At the lower x boundary it becomes $a_{i_\mathrm{lo}} - \Delta x\, g$ for the gradient $g$, and $2 g - a_{i_\mathrm{lo}}$ for the value $g$.
- Further types are defined per solver with `define_bc`, which registers a function that fills the ghost cells after the standard types (`pyro/mesh/patch.py`, `CellCenterData2d.fill_BC`).

A table records for the Riemann solvers which types are solid walls, through which no flux passes. All reflecting types and `dirichlet` are, `outflow`, `periodic` and `neumann` are not, and each new type declares its own (`pyro/mesh/boundary.py`, `bc_solid`). Face-centred data support only periodic boundaries. A demonstration fills each standard type on a small grid and prints the result (`examples/mesh/bc_demo.py`), and the unit tests check the outflow, periodic and reflecting fills with two ghost cells (`pyro/mesh/tests/test_patch.py`, `test_bcs`).

#### 2.1.4 Restriction and prolongation

Restriction averages blocks of $2 \times 2$ or $4 \times 4$ fine zones into one coarse zone (`pyro/mesh/patch.py`, `CellCenterData2d.restrict`). Prolongation refines by two with the linear reconstruction $a_{i,j} \pm m_x/4 \pm m_y/4$ at the four child centres, with the centred, unlimited slopes $m_x = (a_{i+1,j} - a_{i-1,j})/2$ and $m_y = (a_{i,j+1} - a_{i,j-1})/2$ (`CellCenterData2d.prolong`). These are the transfers of Zingale's text, given in 2.6.5 of its synthesis, and on a uniform grid both conserve the total, as the unit tests check. Neither weights the zones by volume, and the coarser or finer grid is a plain `Grid2d`, without geometry. Face-centred data offer neither operation.

#### 2.1.5 Slopes and limiters

A single function returns the limited difference of a variable across each zone, in the units of the variable rather than per unit length, on the valid zones and two ghost cells on each side (`pyro/mesh/reconstruction.py`, `limit`). The parameter `limiter` selects the method. With 0, the difference is centred and unlimited, $(a_{i+1} - a_{i-1})/2$. With 1, it is the second-order monotonised central limiter of 2.3.9 of the synthesis of Zingale's text: the smallest in magnitude of the centred difference and twice each one-sided difference, with their common sign, and zero where the one-sided differences differ in sign (`limit2`). Any other value gives the fourth-order variant, which Zingale's text cites without stating it (`limit4`). It applies the same limiting to the centred estimate $\tfrac{4}{3}(a_{i+1} - a_{i-1})/2 - (\Delta a_{i+1} + \Delta a_{i-1})/6$, built from the second-order limited differences $\Delta a$ of the two neighbours.

For a gravitating atmosphere, a well-balanced variant limits the pressure in y as a deviation from hydrostatic equilibrium (`well_balance`). It sets $p'_j = 0$ and $p'_{j \pm 1} = p_{j \pm 1} - [p_j \pm (\Delta y/2)(\rho_j + \rho_{j \pm 1})\, g]$, and limits $p'$ with the second-order limiter, so that a discretely hydrostatic profile gets no slope. It works only with `limiter` 1 and stops the program otherwise, and `compressible_rk` uses it.

#### 2.1.6 Flattening

Flattening coefficients reduce the slopes at strong shocks (`pyro/mesh/reconstruction.py`, `flatten`). In each direction, $z = |p_{i+1} - p_{i-1}| / \max(|p_{i+2} - p_{i-2}|, 10^{-10})$ measures how steep the pressure jump is over three zones against five, and gives $\xi = \min[1, \max(0, 1 - (z - z_0)/(z_1 - z_0))]$. The coefficient applies only where the flow converges, $u_{i-1} > u_{i+1}$, and the relative jump in pressure, $|p_{i+1} - p_{i-1}| / \min(p_{i+1}, p_{i-1})$, exceeds $\delta$, and it is 1 elsewhere. The constants $\delta$, $z_0$ and $z_1$ are runtime parameters of the compressible solver. The multi-dimensional coefficient is the smallest of $\xi$ in x and in y, each at the zone and at its neighbour towards lower pressure (`flatten_multid`). The solvers `compressible`, `compressible_rk`, `compressible_fv4` and `swe` use these coefficients. 2.5.13 of the synthesis of Zingale's text treats flattening in general.

#### 2.1.7 WENO reconstruction

`weno_upwind` reconstructs the value at the right edge of a zone from the $2r - 1$ values around it, for $r = 2$ or 3, in the notation of 2.3.19 of the synthesis of Zingale's text (`pyro/mesh/reconstruction.py`). Each of the $r$ stencils of $r$ zones gives a candidate value and a smoothness indicator $\beta$, a quadratic form in the values. The weights are $\alpha/\sum \alpha$ with $\alpha = C/(\epsilon + \beta^2)$ and $\epsilon = 10^{-16}$, as in eq. 5.79b of Zingale's text, and the optimal weights $C$ are $1/3$ and $2/3$ for $r = 2$, and $1/10$, $3/5$ and $3/10$ for $r = 3$, in the order of the stencils of 2.3.19. For the left edge the data are passed in reverse. A function `weno` would do both edges along a whole row, but nothing calls it. **[GK]** It takes the shape of the array, a tuple, as the number of points, and so would fail if called.

#### 2.1.8 Fourth-order interface states

The fourth-order solvers reconstruct the interface states from zone averages with the method of McCorquodale and Colella (2011), whose eqs. 24 to 32 the comments of the code follow (`pyro/mesh/fourth_order.py`, `states`). The edge value $a_{i-1/2} = \tfrac{7}{12}(a_{i-1} + a_i) - \tfrac{1}{12}(a_{i-2} + a_{i+1})$ is fourth-order accurate. With $\delta a^- = a_i - a_{i-1/2}$ and $\delta a^+ = a_{i+1/2} - a_i$, a zone counts as an extremum if their product is not positive, or if that of $a_i - a_{i-2}$ and $a_{i+2} - a_i$ is not.

- At an extremum, the second difference of the parabola through the zone, $\delta^2 a = 6(a_{i-1/2} - 2a_i + a_{i+1/2})$, is compared with the centred second differences $\delta^2 a_c$ of the zone and its two neighbours. If all four share a sign $s$, the limited value is $s \min(|\delta^2 a|, 1.25|\delta^2 a_{c,i-1}|, 1.25|\delta^2 a_{c,i}|, 1.25|\delta^2 a_{c,i+1}|)$, and otherwise zero, and $\rho$ is its ratio to $\delta^2 a$, or zero where $\delta^2 a$ is negligible.
- Where $\rho < 1$ and the third differences on the four nearby interfaces vary by at least a tenth of their largest magnitude, the edge values are limited. At a strict extremum, $\delta a^- \delta a^+ < 0$, they become $a_i - \rho\, \delta a^-$ and $a_i + \rho\, \delta a^+$. Otherwise a side whose departure from $a_i$ is at least twice that of the other is blended, to $a_i - 2(1 - \rho)\delta a^+ - \rho\, \delta a^-$ or its mirror image.
- Away from extrema, an edge value that departs from $a_i$ by at least twice the departure on the other side is cut back to twice it, $a_i - 2\delta a^+$ or $a_i + 2\delta a^-$.

A comment marks eq. 29 of the paper as misprinted. The form the code uses, $a_i - \rho\, \delta a^-$, reduces to the unlimited edge value at $\rho = 1$. Each zone sets the right state of its left interface and the left state of its right interface, and the arrays index both states of interface $i - 1/2$ by $i$. `states_nolimit` returns the interpolated edge values without limiting. Both functions are explicit loops over the zones, compiled by numba.

#### 2.1.9 Averages and centres

Beyond second order, a zone average differs from the value at the centre (2.1.1). `FV2d`, a subclass of `CellCenterData2d`, holds zone averages and converts them to fourth order, assuming $\Delta x = \Delta y$ (`pyro/mesh/fv.py`). `to_centers` returns the centre values $a - (\Delta x^2/24) \nabla^2 a$, with the five-point Laplacian of 3.2, on the valid zones and all but the outermost ghost cells. On request it keeps the average where the centre value would be negative. `from_centers` turns centre values into averages in place, $a + (\Delta x^2/24) \nabla^2 a$, after filling the ghost cells.

#### 2.1.10 Runge-Kutta integration

`RKIntegrator` advances data by an explicit Runge-Kutta method given as a Butcher tableau (`pyro/mesh/integration.py`). The methods are `RK2`, the midpoint method, `TVD2` and `TVD3`, the second- and third-order total variation diminishing methods of Gottlieb and Shu, and `RK4`, the classic fourth-order method and the default. `TVD3` has the stages $y_n$, $y_n + \Delta t\, k_1$ and $y_n + (\Delta t/4)(k_1 + k_2)$, at the times $t$, $t + \Delta t$ and $t + \Delta t/2$, and the weights $1/6$, $1/6$ and $2/3$. A solver stores the starting state and asks for the state of each stage, $y_n + \Delta t \sum_s a_{is} k_s$ at $t + c_i \Delta t$, a clone of the start (3.2). It evaluates its right-hand side there and stores the increment $k_i$ without the factor $\Delta t$. The final update overwrites the start with $y_n + \Delta t \sum_i b_i k_i$. 2.1.7 and 2.3.12 of the synthesis of Zingale's text treat these methods in general.

### 2.2 Advection

Five solvers integrate the linear advection equation $a_t + u a_x + v a_y = 0$, the simplest hyperbolic equation (eq. 2, §3.1). Its exact solution carries any profile unchanged with the velocity $(u, v)$, which makes it a test bed for numerical methods, and its methods return in the compressible and incompressible solvers (`docs/source/advection_basics.rst`). Zingale's text treats them in 2.3 of its synthesis.

#### 2.2.1 The unsplit CTU method

Advection shows two ways into several dimensions (§3.1). Dimensional splitting builds the fluxes of each direction without regard to the flow across it, updates direction after direction, and alternates their order for second-order accuracy (Strang 1968). It reuses one-dimensional methods unchanged, but preserves symmetries less well (Almgren et al. 2010). An unsplit method lets each interface state see the change carried in the transverse direction, and updates with the fluxes of all directions at once. `advection` uses the unsplit corner transport upwind (CTU) method of Colella (1990), whose procedure the compressible and incompressible solvers repeat. A Taylor expansion in space and time gives the time-centred state on the left of interface $i + 1/2$ from zone $i$ as $a_{i,j} + \tfrac{1}{2}(1 - u\Delta t/\Delta x)\Delta a_{i,j} - (\Delta t/2)\, v\, \partial a/\partial y|_{i,j}$ (eq. 3). Here $\Delta a$ is the limited difference, for which the paper uses the fourth-order limiter of Colella (1985) and refers to Bell et al. (1988) on limiting in several dimensions. The last term is the transverse flux difference, without which diagonal advection would not see the upwind state. The prediction without it is the normal, or hat, state (eq. 4). Riemann problems between the hat states on all interfaces give the transverse states, whose differences complete the interface states, and a final Riemann problem gives the state on each interface (fig. 2). For advection each Riemann problem is upwinding. The conservative update then advances $a$ with the fluxes $u a$ and $v a$ on the four faces (eq. 5), and the time step is $\Delta t = C \min(\Delta x/|u|, \Delta y/|v|)$, with the CFL number $C \le 1$ (eq. 6).

The code forms only the upwind state on each face, as upwinding makes the other unnecessary (`pyro/advection/interface.py`, `linear_interface`; `pyro/advection/advective_fluxes.py`, `unsplit_fluxes`). With $c_x = u\Delta t/\Delta x$, the hat state on face $i - 1/2$ is $a_{i-1} + \tfrac{1}{2}(1 - c_x)\Delta a_{i-1}$ for $u \ge 0$ and $a_i - \tfrac{1}{2}(1 + c_x)\Delta a_i$ for $u < 0$. The full state subtracts $\Delta t/(2\Delta y)$ times the difference of the transverse fluxes $v\hat{a}$ on the upper and lower faces of the upwind zone, and the flux is $u$ times that state. The velocities are the runtime parameters `advection.u` and `advection.v`, 1 by default, and the default limiter is the fourth-order one of 2.1.5 (`pyro/advection/_defaults`). The grid has four ghost cells, the CFL number is 0.8 by default, and tracer particles, if switched on, move with the constant velocity (`pyro/advection/simulation.py`).

#### 2.2.2 Method-of-lines solvers

`advection_rk` reconstructs the interface states in space alone, as the upwind value $a_{i-1} + \Delta a_{i-1}/2$ or $a_i - \Delta a_i/2$, and integrates in time with the Runge-Kutta methods of 2.1.10, `RK4` by default (`pyro/advection_rk/fluxes.py`, `simulation.py`). The transverse coupling then comes through the stages of the integrator. The method of lines restricts the time step further, to $\Delta t = C/(|u|/\Delta x + |v|/\Delta y)$, as 2.3.16 of the synthesis of Zingale's text explains. Second order allows centre values and averages to be treated alike (`docs/source/advection_basics.rst`). **[GK]** A branch for values of `advection.limiter` of 10 or more expects two slopes from `limit`, which returns one array, and so would fail.

`advection_weno` is a finite-difference method that splits the flux after Lax and Friedrichs and reconstructs each part with WENO, after a review by Shu, in the notation of Gerolymos et al. (2009) (`pyro/advection_weno/__init__.py`, `fluxes.py`). Along each row and column, the parts $f^\pm = (u \pm \alpha)a/2$, with $\alpha = (u^2 + v^2)^{1/2}$ in both directions, are reconstructed to each face with `weno_upwind` (2.1.7), $f^+$ from the left and $f^-$ from the right, and the flux is their sum. The parameter `advection.weno_order` is $r$, 2 or 3, and 3 by default, for a scheme of order $2r - 1$, and the grid needs more than $r$ ghost cells. The default CFL number is 0.5, the time step and integrator are those of `advection_rk`, and the reconstruction runs in loops of Python over the points. The docstring expects the splitting to make the method diffusive, and notes that it lacks transverse terms.

#### 2.2.3 The fourth-order solver

`advection_fv4` holds zone averages in an `FV2d` object and follows McCorquodale and Colella (2011) (`pyro/advection_fv4/simulation.py`, `fluxes.py`). The problem sets centre values, which `preevolve` converts to averages (2.1.9). On each face, the average of $a$ comes from the limited states of 2.1.8, upwinded by the sign of the velocity, or from the unlimited interpolation if `advection.limiter` is 0, the default being 1. The value at the centre of the face follows by subtracting $1/24$ of the second difference along the face (eqs. 18 and 19 of the paper). The face-averaged flux is the flux of that value plus $1/24$ of the second difference along the face of the flux of the face averages (eq. 20). Integration is by `RK4`, with the time step of `advection_rk` and a default CFL number of 0.8, and the zones must be square (2.1.9). **[GK]** For the linear flux the two corrections cancel exactly, so that the face-averaged flux is $u$ times the face average. They matter for nonlinear fluxes, as in `compressible_fv4`.

#### 2.2.4 Advection by a varying velocity

`advection_nonuniform` advects with a velocity field that varies in space, for the slotted disc of Zalesak (1979) (`docs/source/advection_basics.rst`; `pyro/advection_nonuniform/`). The velocity components are variables of their own, with odd reflection at walls, and so is the upwind direction in each zone, which is set once from the sign of the initial velocity. The fluxes are those of the CTU method of 2.2.1, computed zone by zone in loops of Python with the local velocity and Courant number. The time step is $C \min(\Delta x/\max|u|, \Delta y/\max|v|)$, and particles move with the velocity field. **[GK]** The flux through face $i - 1/2$ takes the velocity and Courant number of zone $i$. For the rotation of the slotted disc, whose $u$ depends only on $y$ and $v$ only on $x$, this is the velocity of the face, but for a general field it shifts the flux by half a zone and costs an order of accuracy.

#### 2.2.5 Problems and tests

The variants of `advection` share its problems (`pyro/advection/problems/`).

- `smooth`: $a = 1 + \exp\{-60[(x - x_c)^2 + (y - y_c)^2]\}$ about the centre of the domain, smooth enough that the limiters act little (eq. 7). Its inputs take $32 \times 32$ zones on the unit square with periodic boundaries, $u = v = 1$ and $C = 0.8$, run to $t = 1$, one period along the diagonal, with the fourth-order limiter, a first step at the full size and no limit on the growth of the step. Output follows every 0.2 in time, and particles start on a grid.
- `tophat`: $a = 1$ inside a circle of radius 0.1 about the centre and 0 outside, which tests the limiters, with the same set-up.
- `test`: $a = 1$, for the unit tests.
- `slotted`, for `advection_nonuniform`: $a = 1$ in a disc of radius 0.15 whose centre lies 0.25 above that of the domain, less a slot 0.05 wide from its centre down to its edge, and 0 elsewhere. It rotates clockwise about the centre of the domain with $u = \omega(y - y_c)$ and $v = -\omega(x - x_c)$, $\omega = 0.5$. The inputs take $64 \times 64$ zones on the unit square with periodic boundaries, $C = 0.8$ and the fourth-order limiter, to $t = 12.5664$, one revolution.

With `smooth` at $32^2$ zones and $C = 0.8$, the pyro paper finds nearly second-order convergence after one period, the departure being due to the limiters (fig. 3, §3.1.1). The documentation finds nearly second order for `advection` and fourth order for `advection_fv4`. A notebook runs `advection_fv4` at 16 to 256 zones with $C = 0.5$ and compares the final with the initial averages: the error falls by about 16 at each doubling from 32 zones on, while 16 zones do not resolve the profile (`docs/source/advection-error.ipynb`). The script `smooth_error.py` instead compares an output with the problem's initial values set afresh on the same grid, and reports the absolute and relative $L_2$ norms of the difference (`pyro/analysis/smooth_error.py`). **[GK]** These initial values are centre values, so that for the averages of `advection_fv4` the difference includes $(\Delta x^2/24) \nabla^2 a$, of second order, which would cap the measured convergence at second order. The regression tests run `smooth` with `advection`, `advection_rk` and `advection_fv4`, and `slotted` (3.4), and the unit tests check the initial data (`tests/` of each solver).

### 2.3 Burgers' equation

Two solvers integrate the two-dimensional Burgers' equations, $u_t + u u_x + v u_y = 0$ and $v_t + u v_x + v v_y = 0$, in which the velocity advects itself (`docs/source/burgers_basics.rst`). Unlike linear advection, the equations form shocks and rarefactions, and their Riemann problem depends on the shock speed from the Rankine-Hugoniot condition. 2.4 of the synthesis of Zingale's text treats the one-dimensional equation.

#### 2.3.1 The inviscid solver

`burgers` follows the CTU method of `advection` with another Riemann solver and time step (`pyro/burgers/simulation.py`, `burgers_interface.py`). The limited slopes of $u$ and $v$ in both directions, with the fourth-order limiter by default, give normal states on both sides of every face. On the faces normal to x, both components are predicted with the speed $u$ of the zone, as $q_i \pm \tfrac{1}{2}(1 \mp u_i \Delta t/\Delta x)\Delta^x q_i$, and on the faces normal to y with $v$ (`get_interface_states`). The Riemann problem of Burgers' equation gives zero if $q_L \le 0 \le q_R$, $q_L$ if $q_L > 0$ and $q_L + q_R > 0$, and $q_R$ otherwise, as in 2.10.3 of the synthesis of Zingale's text (`riemann`). Upwinding by the sign of a velocity $s$ picks $q_L$ or $q_R$, or their mean where $s = 0$ (`upwind`).

The transverse corrections take the normal velocities on the faces from Riemann problems of the normal states, upwind all normal states with them, and average them over each zone (`apply_transverse_corrections`). Each state on a face normal to x then loses $(\Delta t/2\Delta y)\, \bar{v}$ times the difference of the upwinded states on the upper and lower faces of its zone, and likewise in y. A second Riemann problem gives the advective velocities on the faces, called MAC velocities, the states are upwinded with them, and the fluxes are half the product of state and MAC velocity, as $\tfrac{1}{2} u\, u^\mathrm{MAC}$ and $\tfrac{1}{2} v\, u^\mathrm{MAC}$ on the faces normal to x (`construct_unsplit_fluxes`). A conservative update advances both components. The time step is $C \min(\Delta x/\max|u|, \Delta y/\max|v|)$ with $C = 0.8$, and particles move with the velocity. **[GK]** With these fluxes the update solves $u_t + (u^2/2)_x + (uv/2)_y = 0$ and the corresponding equation for $v$. These differ from the stated equations by $\tfrac{1}{2}(u v_y - v u_y)$ and $\tfrac{1}{2}(v u_x - u v_x)$, which vanish where $u = v$. Every problem of the solver starts with $u = v$, which the equations then keep, so that its tests do not show the difference.

#### 2.3.2 The viscous solver

`burgers_viscous` adds a constant viscosity, $u_t + u u_x + v u_y = \epsilon(u_{xx} + u_{yy})$ and the same for $v$, with $\epsilon$ = `diffusion.eps`, 0.005 by default (`pyro/burgers_viscous/`). The prediction adds the explicit viscous term $(\Delta t/2)\,\epsilon \nabla^2 q$ of the zone, with the five-point Laplacian, to the four states of each zone, before the transverse corrections of the inviscid solver (`interface.py`, `apply_diffusion_corrections`). The divergence of the fluxes then forms the advective term $A$ of each component, and a Crank-Nicolson step solves $(1 - \tfrac{1}{2}\Delta t\, \epsilon \nabla^2)\, q^{n+1} = q^n + \tfrac{1}{2}\Delta t\, \epsilon \nabla^2 q^n - \Delta t\, A$ with the multigrid solver for the Helmholtz equation, from a zero initial guess, to a relative tolerance of $10^{-12}$ and with the boundary conditions of the component (`diffuse`). The time step is that of the inviscid solver, as the implicit diffusion sets no limit. 2.10.6 of the synthesis of Zingale's text treats viscosity in the same way for incompressible flow.

#### 2.3.3 Problems and tests

Both solvers use the problems of `burgers`, and all set $u = v$ (`pyro/burgers/problems/`).

- `test`: $u = v = 3$ below the line $y = 1 - x$ and 1 above it, so that a shock runs along the diagonal towards the upper right with the speed 2 in each direction. Its inputs take $128 \times 128$ zones on the unit square with outflow boundaries, $C = 0.8$ and the fourth-order limiter, to $t = 0.1$.
- `converge`: $u = v = A + A \exp\{-50[(x - x_c)^2 + (y - y_c)^2]\}$ with $A = 0.05$, smooth up to $t = 1$. Its inputs, for 32 to 256 zones on a side with periodic boundaries, fix the time step at $0.01 \times 32/N$ for $N$ zones and switch the limiter off.
- `tophat`: $u = v = 1$ inside a circle of radius 0.1 about the centre and 0 outside, on $32 \times 32$ periodic zones to $t = 1$.

**[GK]** `converge` and `tophat` define no `PROBLEM_PARAMS`, which the driver reads without a fallback (3.3), so that neither runs at 4.5.1. The directory also holds an inputs file for a problem `smooth` that does not exist. A script measures the speed of the shock of `test` from two outputs, through the averages of $|U|$ along the diagonals, and compares it with the exact $2\sqrt{2}$ along the diagonal (`pyro/burgers/problems/verify.py`). With viscosity, the documentation shows the same shock smeared out as it moves. The regression tests run `test` with `burgers` (3.4), and `burgers_viscous` has neither regression nor unit tests.

### 2.4 Compressible hydrodynamics

Five solvers integrate the Euler equations, $\partial \rho/\partial t + \nabla \cdot (\rho \mathbf{U}) = 0$, $\partial (\rho \mathbf{U})/\partial t + \nabla \cdot (\rho \mathbf{U}\mathbf{U}) + \nabla p = \rho \mathbf{g}$ and $\partial (\rho E)/\partial t + \nabla \cdot [(\rho E + p)\mathbf{U}] = \rho \mathbf{U} \cdot \mathbf{g}$, with $E = e + \tfrac{1}{2}|\mathbf{U}|^2$ and a constant gravitational acceleration (eqs. 8 to 11, §3.2; `docs/source/compressible_basics.rst`). The equations carry no dissipation, as it is usually negligible in astrophysics. They share flattening at shocks, artificial viscosity, a gamma-law equation of state, a choice of Riemann solvers in some of them, and the problems of `compressible`. 2.5 of the synthesis of Zingale's text treats the methods in general.

#### 2.4.1 Variables and equation of state

The conserved variables are the density, the two momenta, the total energy $\rho E$ and any passive scalars $\rho X$, and the primitive ones $\rho$, $u$, $v$, $p$ and $X$ (`pyro/compressible/simulation.py`, `Variables`). The gamma-law equation of state $p = \rho e(\gamma - 1)$ closes the system, with $\gamma = 1.4$ by default (eq. 12; `pyro/compressible/eos.py`). The conversion to primitive variables sets the velocity to zero where the density vanishes and asserts a positive density and internal energy in the valid zones (`cons_to_prim`). Derived variables give the velocity, the internal energy, the pressure, the primitive set, the sound speed $(\gamma p/\rho)^{1/2}$, the Mach number and the vorticity from centred differences (`pyro/compressible/derives.py`). The grid has four ghost cells. The x- and y-momenta reflect oddly at walls normal to x and to y, and $\gamma$ and the gravitational acceleration travel with the data as auxiliary values.

#### 2.4.2 Interface states

`compressible` is the unsplit, piecewise linear CTU method of Colella (1990), which Castro also offers (Almgren et al. 2010), and the paper calls it more approachable for students than the formally more accurate piecewise parabolic method of Colella and Woodward (1984), to which the upgrade is then straightforward (§3.2; Miller and Colella 2002). As for advection, interface states come from a Taylor expansion to the half time, but the normal prediction works on the primitive variables, through a characteristic projection that adds only the jumps carried towards the interface. The paper writes a jump as $\Delta \mathbf{q} = \sum_\nu (\mathbf{l}^{(\nu)} \cdot \Delta \mathbf{q})\, \mathbf{r}^{(\nu)}$, with the left and right eigenvectors of the primitive system (eq. 13; LeVeque 2002). Where most papers write out the products $\mathbf{l} \cdot \Delta \mathbf{q}$, as in eqs. 3.6 and 3.7 of Colella and Woodward (1984), pyro builds the eigenvectors explicitly, to show what the procedure does.

In the code, the slopes of all primitive variables come from the limiter of 2.1.5, the fourth-order one by default, and are multiplied by the flattening coefficient of 2.1.6, which is on by default with $z_0 = 0.75$, $z_1 = 0.85$ and $\delta = 0.33$ (`pyro/compressible/unsplit_fluxes.py`, `interface_states`; `_defaults`). In x, the eigenvalues are $u - c$, $u$, $u$ and $u + c$, and $u$ for each scalar (`pyro/compressible/interface.py`, `states`). The left state on face $i + 1/2$ starts from the reference $\mathbf{q} + \tfrac{1}{2}[1 - (\Delta t/\Delta x)\max(u + c, 0)]\Delta \mathbf{q}$, extrapolated with the fastest wave towards the face. Each wave $\nu$ that moves to the right adds $(\Delta t/2\Delta x)(\lambda_\mathrm{max} - \lambda_\nu)(\mathbf{l}^{(\nu)} \cdot \Delta \mathbf{q})\, \mathbf{r}^{(\nu)}$, and the right state on face $i - 1/2$ follows in the same way with $u - c$ and the waves that move to the left. On the spherical grid, the zone lengths replace $\Delta x$ and $\Delta y$. A geometric source $-\tfrac{1}{2}\Delta t\, \rho u\, \partial \ln A/\partial x$, with the logarithmic derivative of the area of 2.1.2, is added to the density of both states, and $c^2$ times it to the pressure. The states are then converted to conserved variables. The kernel is a loop compiled by numba.

#### 2.4.3 Sources and transverse corrections

Half a time step of the source terms of the zone, evaluated at the old time, is added to the momenta and energy of each interface state it predicts (`apply_source_terms`). The sources pass through an auxiliary data object, whose ghost cells are filled first.

The transverse correction follows (`apply_transverse_flux`). Riemann problems between the normal states give fluxes on all faces, and each state on a face normal to x loses $\Delta t/(2V)$ times the difference of the y-fluxes, weighted by the face areas, of the zone it comes from. The states on faces normal to y lose likewise the difference of the x-fluxes. On the spherical grid, whose momentum fluxes carry no pressure, the transverse pressure gradient, from the pressure of the Riemann solution divided by the zone length, enters the momenta separately. **[GK]** For the left states on the faces normal to x, which come from zone $i - 1$, these terms divide by the volume and length of zone $i$, which matters only on the spherical grid, where both vary with the radius. The final interface states then pass to the Riemann solver selected by `compressible.riemann`, HLLC by default, which the spherical grid does not support.

#### 2.4.4 Artificial viscosity and the update

Artificial viscosity adds a diffusive flux $\alpha (\mathbf{U}_{i-1} - \mathbf{U}_i)$ to every face normal to x, and likewise in y, with $\alpha = c_\mathrm{visc} \max(-\nabla \cdot \mathbf{U}\, L_x, 0)$, the zone length $L_x$ and $c_\mathrm{visc} = 0.1$ by default (`apply_artificial_viscosity`; `pyro/compressible/interface.py`, `artificial_viscosity`). The divergence is taken at the corners of the zones from the averaged velocities, in its spherical form on the spherical grid, and averaged to the face, so that only converging flow is damped. The conservative update then advances all variables with the fluxes weighted by the face areas and divided by the zone volume, $\Delta t/V\, (F_{i-1/2} A_{i-1/2} - F_{i+1/2} A_{i+1/2} + \ldots)$. On the spherical grid the pressure gradients follow from the pressures of the Riemann solutions, $\Delta p/\Delta r$ and $\Delta p/(r \Delta\theta)$.

#### 2.4.5 Source terms

The external sources are gravity, the geometric terms of the spherical grid and an optional source of the problem (`pyro/compressible/simulation.py`, `get_external_sources`). On the Cartesian grid gravity acts in y, with the sources $\rho g$ for the y-momentum and $\rho v g$ for the energy, and on the spherical grid it acts in $r$. The spherical grid adds $(\rho u_\theta)^2/(\rho r)$ to the radial momentum and $-(\rho u_r)(\rho u_\theta)/\rho$ to the polar momentum. **[GK]** The axisymmetric momentum equation in $\theta$ has the source $-\rho u_r u_\theta/r$, so that the factor $1/r$ is missing, which is consistent only for $r = 1$.

The sources enter by a predictor and corrector, which centres them in time (`docs/source/compressible_sources.rst`). After the update with the fluxes, $\mathbf{U}^\star = \mathbf{U}^n + \ldots + \Delta t\, \mathbf{S}(\mathbf{U}^n)$, the correction adds $\tfrac{1}{2}\Delta t[\mathbf{S}(\mathbf{U}^\star) - \mathbf{S}(\mathbf{U}^n)]$. For gravity, the corrected momentum enters the source of the energy, which makes the update appear implicit in time. A problem can add a source through a function `source_terms(myg, U, ivars, rp)` that returns the vector of sources, as the problem `convection` does with heating.

A sponge damps the velocity where the density is low, as above an atmosphere with outflow boundaries, by a term $-(f/\tau)\rho \mathbf{U}$ in the momentum equation (`get_sponge_factor`). The factor $f$ is 0 above the density `sponge.sponge_rho_begin`, 1 below `sponge.sponge_rho_full`, and $\tfrac{1}{2}\{1 - \cos[\pi(\rho - \rho_\mathrm{begin})/(\rho_\mathrm{full} - \rho_\mathrm{begin})]\}$ between them, and $\tau$ is `sponge.sponge_timescale`, best a few to ten time steps. The code divides the momenta by $1 + \Delta t f/\tau$, an implicit step, and changes the total energy by the change in kinetic energy, so that the internal energy stays as it was. The sponge is off by default. A density floor, `compressible.small_dens`, applies at the start of each step, and is off by default.

#### 2.4.6 Boundary conditions and time step

Beyond the standard types of 2.1.3, the compressible solvers define three of their own, none a solid wall (`pyro/compressible/BC.py`, `user`). `hse` holds an atmosphere in hydrostatic equilibrium at the lower or upper boundary in y. The ghost cells copy the density, the momenta and the other variables from the edge zone, and the pressure falls or rises by $g \rho \Delta y$ from zone to zone with the density of the edge zone, while the kinetic energy of the edge zone is kept in the total energy. `ambient` fills the upper boundary in y with an ambient state of density, velocity and pressure set by the problem. `ramp` serves the double Mach reflection, in which a Mach 10 shock meets a reflecting wall at an angle of 60°. The lower boundary in x holds the post-shock state $\rho = 8$, $u = 7.1447096$, $v = -4.125$ and $p = 116.5$. The lower boundary in y holds the same state for $x < 1/6$ and reflects beyond it. The upper boundary in y follows the exact position of the moving shock, blending the pre-shock state, $\rho = 1.4$, $p = 1$ and zero velocity, with the post-shock state by sampling each ghost zone at four points.

The time step is $C \min[L_x/(|u| + c), L_y/(|v| + c)]$ over the zones, with $C = 0.8$ by default (`method_compute_timestep`). Tracer particles, if switched on, move with the velocity.

## 3. Software architecture

The software architecture draws on steps 1 to 4 of `plan.md`.

### 3.1 Packaging, installation and development

pyro is the Python package pyro-hydro, built with setuptools, which takes its version from the git tags through setuptools_scm (`pyproject.toml`). It needs numpy, numba, matplotlib and h5py, and assumes Python 3.9 or later (`README.md`). It installs from PyPI with `pip install pyro-hydro`, or from a clone of the repository with `pip install .`, and with `pip install -e .` for work on the solvers, so that changes to the source take effect without a new installation (`docs/source/installation.rst`). Installation puts the driver, `pyro_sim.py`, on the path. As a quick test, `pyro_sim.py advection smooth inputs.smooth` should show a smooth pulse that advects diagonally through the periodic domain. Plotting during a run needs an interactive backend of matplotlib, such as TkAgg (`README.md`), and the unit tests need pytest. The file `requirements.txt` adds the packages for development: scipy and prettytable, which two analysis scripts import, nbval and pytest-cov for the tests, flake8 and codespell, and the tools that build the documentation. **[GK]** PyPI states no minimum version of Python for pyro-hydro, and its wheel is pure Python.

Contributions arrive as pull requests from forks against the main branch, and any change that may alter results must take this route (`docs/source/help.rst`). The unit and regression tests run automatically on each pull request, after which a developer reviews it. A pull request of many small commits may be squashed on merge, so that its title and first post become the commit message. Issues serve for bug reports and requests for features, and the discussions of the repository for questions and support. The documentation is built with `make html`, which runs all its notebooks unless `SKIP_EXECUTE=TRUE` is given.

### 3.2 Grids and data

The pyro paper describes the design of 2014 (§2). NumPy is fast when it operates on whole arrays rather than on single elements in loops of Python, but its slice notation can hide the index notation of the papers, especially in two dimensions. A second derivative, for instance, becomes a difference of slices of the array between the first and last valid zones (eq. 1), and nonlinear switches make such expressions complex. To balance clarity against the features of NumPy, some kernels were then written in Fortran and interfaced with f2py. Each Fortran function had to be self-contained, with all information passed through its interface and no external dependencies, and each module had at most one Fortran file, compiled with a single command. The paper names two fundamental classes for the data: `Grid2d` for the grid and its coordinates, and `CellCenterData2d` for the data on it. The latter registers variables with their own boundary conditions, gives access to a variable, fills ghost cells, restricts and prolongs data for multigrid, prints small grids and writes to disk. At 4.5.1, `ArrayIndexer` restores the index notation through shifted views, and numba compiles the remaining kernels (1.1). The package `mesh` holds further classes: the grids `Cartesian2d` and `SphericalPolar` on the base `Grid2d`, `FaceCenterData2d`, the indexers `ArrayIndexer` and `ArrayIndexerFC`, and the container `BC`, besides classes for fourth-order data and Runge-Kutta integration (`pyro/mesh/__init__.py`).

A grid object holds the sizes, extrema, index bounds and coordinates of 2.1.1, and the subclasses add the geometry of 2.1.2 (`pyro/mesh/patch.py`). Its method `scratch_array` returns a work array over the whole index space, with one or more components, and its methods `coarse_like` and `fine_like` return the grids for multigrid.

`CellCenterData2d` is built in steps (`pyro/mesh/patch.py`, `CellCenterData2d`). The object is created on a grid, with a data type, double precision by default. Each variable is registered with a name and a `BC` object. Auxiliary data that are needed to interpret the output, such as the ratio of specific heats of the equation of state, are set as pairs of keyword and value, and functions for derived variables are added. `create` then allocates a single array of shape $(n_x + 2n_g, n_y + 2n_g, n_\mathrm{var})$ and locks the object, so that no variable can be added later. `get_var` returns a variable as a view, through which changes reach the object, or else asks each derived function in turn for the name. Further methods return a variable by its index or all variables at once, fill the ghost cells of one or all variables, give the minimum and maximum over the valid zones, zero a variable, restrict and prolong it (2.1.4), and print it. A clone copies an object with its variables, data, auxiliary data and derived functions (`cell_center_data_clone`). `write` stores the object in HDF5. The file holds a group for the auxiliary data, one for the grid with its sizes, extrema and `coord_type`, and one for the state, with a group per variable that holds its valid zones, without ghost cells, and the names of its four boundary conditions.

`FaceCenterData2d` holds data on the faces normal to x or to y, with one zone more in that direction (`pyro/mesh/patch.py`). It supports neither derived variables nor custom boundary conditions, restriction or prolongation, and writes its state to a group of its own.

`ArrayIndexer` subclasses the NumPy `ndarray` and carries its grid (`pyro/mesh/array_indexer.py`). Its methods `v`, `ip`, `jp` and `ip_jp` return views of the valid zones, shifted by whole zones in x, y or both, so that $a_{i+1,j} - a_{i-1,j}$ over the valid zones is `a.ip(1) - a.ip(-1)`. Options widen a view by ghost cells, given as one number, per side or per edge, select a component, and set a stride, which restriction and prolongation use. The views are plain arrays without a grid, as they no longer span it, but they share its memory, so that writing into one changes the array (`pyro/mesh/mesh-examples.ipynb`). The first index $i$ runs in x and the second $j$ in y, so that in the row-major storage of NumPy the zones of equal x lie next to each other in memory. Further methods give the five-point Laplacian, the norm $(\Delta x \Delta y \sum a^2)^{1/2}$ over the valid zones, a copy on the same grid, tests of left-right symmetry and antisymmetry, the filling of ghost cells (2.1.3) and a printout with the ghost cells in colour. `ArrayIndexerFC` does the same for face-centred data, whose valid region holds the $n_x + 1$ faces in its direction.

The unit tests cover the grids, the geometric formulas, the methods of the data object, the boundary fills, the indexer and a round trip of writing and reading (`pyro/mesh/tests/`). Experiments by the developers compare slicing, boolean masks, `np.roll` and the indexer for a centred difference on $1024 \times 2048$ zones, and explore the subclassing of `ndarray` (`examples/mesh/experiments/`).

### 3.3 Driver, simulations and runtime parameters

The pyro paper notes how alike the methods for the different systems of equations are (§2). The grids and the locations of the data are the same, the boundary conditions analogous, and the flowchart of the driver identical, so that one driver serves all time-dependent solvers. Each solver has its own directory, with a subdirectory `problems/` for the initial conditions and default parameters of its problems and `tests/` for the benchmark output of the regression tests. In 2014 pyro was run as `./pyro.py [options] solver problem infile [runtime-options]`, with one of four solvers, advection, compressible, diffusion or incompressible, and the eleven problems of table 1. Runtime parameters were defined in plain-text files for the main directory, for each solver and for each problem, read at run time, and could be overridden at the end of the command line. Each solver's `Simulation` class held the runtime parameters, the data and timers, with the methods `initialize`, `timestep`, `preevolve`, `evolve`, `dovis` and `finalize`.

At 4.5.1, pyro runs either from the command line, with the installed script `pyro_sim.py`, or through the class `Pyro` in Python or Jupyter (`docs/source/running.rst`). The script takes the solver, the problem and an inputs file, which it also seeks in the solver's `problems/` directory, then any runtime parameters as `section.option=value`, and the flags `--make_benchmark` and `--compare_benchmark` for regression testing (`pyro/pyro_sim.py`, `parse_args`). With the class, `Pyro("compressible")` creates the driver, `initialize_problem("kh")` sets up a problem and `run_sim()` runs it, while `single_step()` advances it by one step.

`Pyro` takes the name of one of the 17 solvers, imports its package, and reads the main `_defaults` and the solver's `_defaults` into a `RuntimeParameters` object (`pyro/pyro_sim.py`, `Pyro`). `initialize_problem` imports the problem module from the solver's `problems/` by its name, or takes a problem registered with `add_problem`, such as one defined in a notebook (`docs/source/adding_a_problem_jupyter.ipynb`). The parameters are then set in a fixed order. The problem's own parameters are added, an inputs file may override existing parameters but not add new ones, visualisation, verbose output and I/O are switched off unless pyro runs from the command line, and a dictionary passed as `inputs_dict` overrides the rest. The full set is written to `inputs.auto`. The solver's `Simulation` is created with the names of solver and problem, the problem's functions and the parameters, and its `initialize` and `preevolve` are called. `run_sim` writes and plots the initial state if asked, takes steps until the simulation is finished, writes the final state if output is on or forced, reports unused parameters and timings when verbose, and calls `finalize`. Each step fills the ghost cells of all variables, computes the time step, evolves the state, and writes and plots it when due, with images optionally saved. Output files are named by `io.basename` and the number of the step in four digits. A subclass, `PyroBenchmark`, compares the final state with a stored benchmark, to a relative tolerance of $10^{-12}$ by default, or stores a new one.

A problem is a module in a solver's `problems/` directory, which the driver finds by its name (`docs/source/problems.rst`; `pyro/pyro_sim.py`, `Pyro.initialize_problem`). It provides a dictionary `PROBLEM_PARAMS` of the parameters it needs, named `problem.parameter`, with their defaults. `DEFAULT_INPUTS` names the inputs file read when `Pyro` is given none, or is `None`. `init_data(my_data, rp)` fills the state of a `CellCenterData2d` or `FV2d` object, through the same interface for every solver. `finalize()` is called at the end, mostly to print how the output can be analysed, and a function `source_terms` may add sources. Inputs files in the same directory set the domain, the boundary conditions and other parameters of a run.

`NullSimulation` is the base of every solver's `Simulation` (`pyro/simulation_null.py`). It holds the step number, the time step and the previous one, the limits `driver.tmax` and `driver.max_steps`, the runtime parameters, the data, the particles, the problem's functions and the timers. A simulation is finished once $t \ge t_\mathrm{max}$ or $n \ge n_\mathrm{max}$. Output is due when $t$ passes the next multiple of `io.dt_out` or $n$ is a multiple of `io.n_out`, provided `io.do_io` is set. The time step is `driver.fix_dt` if that is positive. Otherwise the solver's `method_compute_timestep` gives it, multiplied by `driver.init_tstep_factor` on the first step and capped at `driver.max_dt_change` times the previous step afterwards, and the last step is shortened to end at $t_\mathrm{max}$. The base `evolve` only advances $t$ and $n$, and `initialize`, `preevolve` and `dovis` are hooks for the solvers. `write` stores in HDF5 the solver, problem, time and step number as attributes, the data of 3.2, the particles, the runtime parameters and any extras of the solver. Two helpers build the grid and the boundary conditions from the runtime parameters (`grid_setup`, `bc_setup`). The grid is Cartesian or spherical, and a spherical grid that reaches the axis, within 0.05 of $\theta = 0$ or $\theta = \pi$, gets reflecting boundaries there. Three boundary objects are returned, one plain and two with odd reflection in x or in y, for the velocity normal to a wall.

Runtime parameters are kept in files of sections in brackets and lines `key = value ; comment`, whose keys become `section.option` in lower case and whose values are read as integers, floats or strings (`pyro/util/runparams.py`, `RuntimeParameters`). A later definition replaces an earlier one, and in the mode used for inputs files only existing keys can change, with a warning for unknown ones. Comments from the defaults are kept for `inputs.auto` and for the tables of the documentation. The object records which parameters are read, so that unused ones can be reported, and it writes all parameters to the HDF5 output. The main `_defaults` end a run at $t = 1$ or after 10,000 steps, take 0.01 of the solver's time step for the first step, let the step grow by at most a factor of 2, and write output every 0.1 in time under the basename `pyro_`, with visualisation on (`pyro/_defaults`). The default mesh is Cartesian with $25 \times 25$ zones on the unit square and reflecting boundaries. Particles are off by default, and 100 are placed at random when they are switched on.

Messages are coloured by kind, and a failure prints the message and the stack and stops the program unless Python runs interactively (`pyro/util/msg.py`). The package exports the mesh classes, `Pyro`, `RuntimeParameters` and `TimerCollection`. It imports its version from `pyro/_version.py`, which setuptools_scm writes at installation, so that the bare source, as in the local copy, lacks it (`pyro/__init__.py`; `pyproject.toml`). The unit tests cover the stopping criteria, the control of the time step and the set-up of the grid, the set-up and a short run through `Pyro`, and the parsing of runtime parameters (`pyro/tests/`; `pyro/util/tests/test_runparams.py`).

### 3.4 Output, analysis and testing

In 2014 the main data object was written to disk with Python's pickle module (§2). Runtime visualisation with matplotlib was on by default and updated the plots every step, so that students could watch the effects of boundary and initial conditions and chase bugs.

At 4.5.1 the simulation writes HDF5 files (3.3). A file holds the solver, the problem, the time and the step number as attributes, and groups for the auxiliary data, the grid and the state (3.2), the particles with their current and initial positions, and all runtime parameters as attributes (`pyro/simulation_null.py`, `NullSimulation.write`). Solvers add groups of their own: `compressible` and `incompressible_viscous` record their custom boundary conditions with the flag for solid walls, and `lm_atm` its base state (`write_extras`). `read` rebuilds what a file holds (`pyro/util/io_pyro.py`). It creates a Cartesian or spherical grid after `coord_type`, defines the custom boundary conditions again through the `user` function of the solver's own module, which the variants of `compressible` share, and restores the variables, the auxiliary data and the particles. For a file written by a simulation it creates the solver's `Simulation`, without problem function or parameters, sets its time, data and particles, reads the extras, and adds the derived variables of the first `derives` module along the class hierarchy. For a file written by a data object alone it returns that object. **[GK]** The loops over the variables reuse the name `n` of the step number read from the file, so that a simulation read back carries the name of its last variable as its step number.

The script `plot.py` reads an output file, fills its ghost cells and plots it with the solver's own `dovis`, by default into `plot.png` of $8 \times 4.5$ inches, with text set by LaTeX (`pyro/plot.py`). `plotvar.py` plots one variable, or the vorticity $\partial v/\partial x - \partial u/\partial y$ from centred differences, optionally in logarithm or without axes, and `plotcompact.py` and `plot_thumbnail.py` make compact plots and thumbnails of 128 pixels (`pyro/analysis/`). During a run, the panels of the solver's plot are arranged in rows, in columns or in a square grid by the aspect ratio of the domain, each with its colour bar, and Ctrl+C in the plot window aborts the run (`pyro/util/plot_tools.py`, `setup_axes`). A collection of named timers profiles a run (`pyro/util/profile_pyro.py`). Each timer accumulates wall-clock time between `begin` and `end`, and the report indents it by the number of timers running when it was created, a nesting that is not enforced.

Two scripts measure convergence without an exact solution (`pyro/analysis/convergence.py`, `convergence_plot.py`). The first restricts the output on the finer of two grids, $N$ times finer, to the coarser grid (2.1.4) and reports the maximum and the $L_2$ norm of the difference for one variable, the density by default. The second takes three or more outputs, finest first, tabulates these norms for all variables with an order of convergence between successive pairs, and plots the norms against the number of zones with a reference line. **[GK]** The order it prints is the square root of the ratio of successive norms. For a refinement factor of 2 and a true order $p$ that is $2^{p/2}$, which equals $p$ only for $p = 2$ and $p = 4$, and the refinement factor given does not enter. The order follows instead from the logarithm of the ratio divided by the logarithm of the factor. The reference line has slope 2 whatever order is given, which sets only its label. The scripts that compare single problems with their exact solutions are digested with their solvers.

The regression tests run 16 problems of 14 solvers, without I/O or visualisation but with a final output, each in a directory of its own and in parallel processes if asked (`pyro/test.py`). Each compares its final state with the benchmark in its solver's `tests/` directory through `PyroBenchmark` (3.3). Four multigrid tests compare with benchmarks of their own. The report lists passes and failures, and the exit code is their number. Options run a single test, one solver or only the multigrid tests, reset failed benchmarks or store all anew, and set the tolerance and the number of processes. `advection_weno`, `burgers_viscous` and `compressible_react` have no regression test. A comparison requires equal grids and variable names, and then agreement of each variable over the valid zones to a relative tolerance of $10^{-12}$ by default (`pyro/util/compare.py`), also from the command line for two files. **[GK]** It uses `numpy.allclose`, whose default absolute tolerance of $10^{-8}$ also applies, so that values smaller than that always agree.

The pyro paper preferred an exact comparison, zone by zone, as the tool sfocu of the FLASH test suite makes (§2.1; Flash Center for Computational Science 2014). A difference at the level of round-off then shows that either the code or the software environment has changed, which a tolerance would hide, at the price of separate benchmarks for each platform. The documentation still notes that a new machine may need new benchmarks (`docs/source/testing.rst`). The unit tests run under pytest, with nbval for the notebooks, whose stored outputs it compares (`pytest -v --nbval`). The notebook `pyro/solver-test.ipynb` runs eleven solvers for one step on $8 \times 8$ zones, and `pyro/solver_test_swe.ipynb` five problems of the shallow-water solver. The options of pytest skip the documentation, whose notebooks are links to the tested ones, and a notebook of symbolic derivations (`pyproject.toml`).

The paper also names the lessons in software engineering that pyro offers students (§2.1; Ferland 2002; Wilson et al. 2012; Turk 2013). Open source, under the BSD licence, puts more eyes on the code, and open code increasingly counts as part of peer review (Shamir et al. 2013). The built-in regression tests show what testing is. The code comes through git, then newly on GitHub, so that each student's clone is a repository of its own, and many students in Zingale's graduate classes had not met version control before.
