# Package

**Prefix.** PACK.

**Status.** Agreed on 2026-11-11.

**Briefs.** [B1D1](../../briefs/B01-strata-in-package.md#b1d1-the-subpackages-of-the-strata), [B1D2](../../briefs/B01-strata-in-package.md#b1d2-the-rule-between-the-strata), [B1D3](../../briefs/B01-strata-in-package.md#b1d3-the-rule-within-a-stratum), [B1D4](../../briefs/B01-strata-in-package.md#b1d4-the-place-of-the-tests), [B1D5](../../briefs/B01-strata-in-package.md#b1d5-the-check-of-the-rule), [B4D1](../../briefs/B04-packaging.md#b4d1-the-versions-of-python-and-the-platforms), [B4D2](../../briefs/B04-packaging.md#b4d2-the-build-backend), [B4D4](../../briefs/B04-packaging.md#b4d4-the-dependencies), [B4D5](../../briefs/B04-packaging.md#b4d5-the-licence) and [B4D6](../../briefs/B04-packaging.md#b4d6-the-version-and-its-record).

## Scope

The package is mhdpy as it is installed, editable from a checkout or from a wheel: its five subpackages and its tests, the rule of imports between and within them with its check, its metadata, and its version with the record of the code that a run uses. As stratum 1 holds no loop over cells, the kernels, their build in `setup.py`, the platforms of [B4D1](../../briefs/B04-packaging.md#b4d1-the-versions-of-python-and-the-platforms) and the wheels with the installation by one command are left to `kernels.md`, which is written with the first kernel of stratum 3. The modules within each subpackage are left to their own documents, and the form in which a run keeps the record of its code to the brief on outputs, restarts and analysis. The groups of development and the lock of [B4D4](../../briefs/B04-packaging.md#b4d4-the-dependencies) shape the environment of the tests rather than the package, and the naming of each test module after the module that it tests ([B1D4](../../briefs/B01-strata-in-package.md#b1d4-the-place-of-the-tests)) stays a convention, as tests that span modules, such as the small loop of the core, test no single module.

The strata are ordered as infrastructure, mesh, core, physics and driver, and a stratum lies above every stratum before it. The top package is `src/mhdpy/__init__.py`. The metadata is the core metadata of the installed distribution, as `importlib.metadata` reads it. mhdpy runs from a checkout where git confirms that the file of its top package is tracked by a repository, and from no checkout otherwise, as after an installation from a wheel or on a machine without git. The check is the test at the top of `tests/` that runs Import Linter without its cache on the packages `mhdpy` and `tests`, with the contracts held in `pyproject.toml`. The record of the code is the frozen dataclass `CodeProvenance`, with the fields `version`, `commit` and `modified`, that the function `code_provenance` of `mhdpy.infrastructure.provenance` returns. The package relies on setuptools and setuptools-scm to be built, on pytest and Import Linter to be tested, and on git to read its commit.

## Layout

<a id="pack01"></a>**PACK01** The package shall lie in `src/mhdpy/`, with one subpackage for each stratum, named `infrastructure`, `mesh`, `core`, `physics` and `driver`. [B1D1](../../briefs/B01-strata-in-package.md#b1d1-the-subpackages-of-the-strata) gives each stratum of the overview a subpackage of its own, so that the place of a module names its stratum and the check covers every later module without a change. [B1D4](../../briefs/B01-strata-in-package.md#b1d4-the-place-of-the-tests) places the package in `src/`, so that the tests run against the package as installed rather than against its sources.

<a id="pack02"></a>**PACK02** The tests shall lie in `tests/`, a package that holds one subpackage for each stratum, of the same name. [B1D4](../../briefs/B01-strata-in-package.md#b1d4-the-place-of-the-tests) mirrors the strata in the folders of the tests, after the practice of pytest that most Python developers know. Import Linter binds a folder of tests to its stratum only where `tests/` and its folders are packages ([B1D5](../../briefs/B01-strata-in-package.md#b1d5-the-check-of-the-rule)).

## The rule of imports

<a id="pack03"></a>**PACK03** No module of a stratum shall import a stratum above it, directly or through other modules, whether at its head, within a function or for type checking alone. [B1D2](../../briefs/B01-strata-in-package.md#b1d2-the-rule-between-the-strata) lets each stratum use any stratum below it and none above, so that each can be read and tested with those below it alone, as the overview builds them ([§3](../../overview.md#3-layers)). Code above is reached only through objects handed down at run time. An import within a function still loads the stratum above when it runs, and one for type checking alone still ties the code to it. The contract of layers of the check counts each of these, and imports through other modules as well ([B1D5](../../briefs/B01-strata-in-package.md#b1d5-the-check-of-the-rule), [B1E1](../../experiments/B01-strata-in-package/E1-violations-found-by-checks/README.md)).

<a id="pack04"></a>**PACK04** Within each stratum, at every level of its subpackages, the siblings shall import each other without a cycle, the imports of their descendants counted. [B1D3](../../briefs/B01-strata-in-package.md#b1d3-the-rule-within-a-stratum) lets the modules of a stratum build on each other, as long as they can be ordered from those that import nothing of the stratum to those that build on the most, so that each module can be read and tested with the modules that it imports. A cycle would leave one of its modules half loaded while another runs. The check holds the rule as a contract of acyclic siblings, with the five strata as its ancestors.

<a id="pack05"></a>**PACK05** When `mhdpy` is loaded, the top package shall import no stratum. Python runs the top package before any of its subpackages, so that a stratum imported there would load with any other ([B1D2](../../briefs/B01-strata-in-package.md#b1d2-the-rule-between-the-strata)). The version that the top package exposes comes from the metadata and needs no stratum ([PACK12](#pack12)). The contract of the check forbids every import of a stratum by the top package, within a function as well, so that an import placed there later to run only when called needs an exemption by `ignore_imports` ([B1E1](../../experiments/B01-strata-in-package/E1-violations-found-by-checks/README.md)).

<a id="pack06"></a>**PACK06** No module in the folder of a stratum in `tests/` shall import a stratum of the package above it. [B1D4](../../briefs/B01-strata-in-package.md#b1d4-the-place-of-the-tests) binds the tests to their stratum, so that each stratum is verified with those below it alone and no fault above can mask one below, as a test of the core that stepped its problems with the driver would. The check holds one contract of forbidden imports for each folder of tests below the driver and follows imports through other modules, so that a helper of the tests that imports a stratum above also fails ([B1E1](../../experiments/B01-strata-in-package/E1-violations-found-by-checks/README.md)).

<a id="pack07"></a>**PACK07** When the check runs on a copy of the package and its tests that holds one planted violation of [PACK03](#pack03) to [PACK06](#pack06), it shall fail. A contract missing from the configuration passes as silently as one that holds, so that only a violation planted on purpose shows that each contract applies. [B1E1](../../experiments/B01-strata-in-package/E1-violations-found-by-checks/README.md) planted such violations in a small package, and Import Linter reported each that the source shows. Each copy holds one of these: an upward import at the head of a module, within a function or for type checking alone, a cycle between two siblings, an import of a stratum by the top package, or an import of a stratum above by a test.

## Metadata

<a id="pack08"></a>**PACK08** The metadata shall admit no Python older than 3.14. [B4D1](../../briefs/B04-packaging.md#b4d1-the-versions-of-python-and-the-platforms) supports Python from 3.14 in both of its builds, the first version whose free-threaded build is supported, so that the code may use the language of 3.14 and an installer refuses an older Python at once rather than letting mhdpy fail later. The floor rises as SPEC 0 drops versions, which the requirement allows.

<a id="pack09"></a>**PACK09** The metadata shall name NumPy as the only dependency at run time, with a lower bound no older than release 2.3.2 and no upper bound. [B4D4](../../briefs/B04-packaging.md#b4d4-the-dependencies) keeps the installation as light as the exception of §1 wants, and leaves each further dependency to the brief that needs it. NumPy 2.3.2 is the first release with wheels for Python 3.14 and 3.14t on the four platforms of [B4D1](../../briefs/B04-packaging.md#b4d1-the-versions-of-python-and-the-platforms), so that no older release may be admitted, and the floor rises as SPEC 0 drops releases. Without an upper bound, a new release of NumPy installs without a new release of mhdpy.

<a id="pack10"></a>**PACK10** The metadata shall name no extra. [B4D4](../../briefs/B04-packaging.md#b4d4-the-dependencies) places the tools of development in groups of dependencies in `pyproject.toml`, which the published metadata leaves out, rather than in extras, which would appear there as if users needed them.

<a id="pack11"></a>**PACK11** The metadata shall name the licence by the SPDX expression `BSD-3-Clause` and include the file `LICENSE`. [B4D5](../../briefs/B04-packaging.md#b4d5-the-licence) places the code and the documents of the repository under the BSD licence of three clauses, whose text lies in `LICENSE`, and names it by an expression of SPDX after PEP 639, which setuptools reads from release 77.

## The version and its record

<a id="pack12"></a>**PACK12** `mhdpy.__version__` shall equal the version in the metadata. [B4D6](../../briefs/B04-packaging.md#b4d6-the-version-and-its-record) sets the version in one place, from which the build writes it into the metadata, and the top package reads it there through `importlib.metadata` without importing a stratum ([PACK05](#pack05)). Under an editable installation, the metadata keeps the version of the last installation, which [PACK14](#pack14) completes with the commit that a run reads from git.

<a id="pack13"></a>**PACK13** When mhdpy is built, its version shall be derived from git: at a commit that a tag marks, the version of the tag, and at any other commit, a version that names it. [B4D6](../../briefs/B04-packaging.md#b4d6-the-version-and-its-record) lets setuptools-scm, a plugin of the backend of [B4D2](../../briefs/B04-packaging.md#b4d2-the-build-backend), derive the version from the last tag, so that releases cannot diverge from their tags and every build names its code. A build at a tag gets the plain version, and one fourteen commits later a version such as `0.2.dev14+g5f3e2a1`, whose local part names its commit.

<a id="pack14"></a>**PACK14** While mhdpy runs from a checkout, the record of the code shall give the version of [PACK12](#pack12), the full hash of the commit of `HEAD`, and whether a file that git tracks differs from that commit. [B4D6](../../briefs/B04-packaging.md#b4d6-the-version-and-its-record) lets every run name the code that produced it. Under an editable installation, a change to a module of Python reaches a run without a new installation ([B4D2](../../briefs/B04-packaging.md#b4d2-the-build-backend)), so that the version names the commit of the last installation rather than that of the code, which git gives instead. As in the experiments ([rules of the experiments, §3](../../templates/experiment-rules.md#3-the-code)), a file that git does not track leaves the tree unchanged, so that a stray note does not mark every run. A frozen dataclass reads by attribute under strict typing, as the parameters of [B5D1](../../briefs/B05-parameters-and-units.md#b5d1-the-declaration-of-parameters) do, and the brief on outputs decides how files keep it.

<a id="pack15"></a>**PACK15** While mhdpy runs from no checkout, the record of the code shall give its version alone, with neither a commit nor a state of the tree. An installation from a wheel names its code by its version, which leads to the commit of its build through a tag or names it outright ([PACK13](#pack13)), so that git is neither needed nor asked. **[GK]** uv places the environment of a project in `.venv/` within its checkout, so that a wheel installed there lies inside a repository of git. A checkout is therefore recognised by the tracked file of the top package rather than by a repository around it, lest such a wheel take the commit of its surroundings.

## Verification

None in stratum 1. The installation by one command, by which [§1.3 of the overview](../../overview.md#13-success-criteria) judges the package, is required with the first kernel in `kernels.md`, since the wheels of [B4D7](../../briefs/B04-packaging.md#b4d7-the-wheels-and-their-publication) carry the compiled kernels, which stratum 1 does not hold.
