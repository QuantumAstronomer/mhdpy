## Scope

The brief settles the route in which the loops over cells of strata 2 to 4 are written ([§5](../overview.md#5-crosscutting-concepts) of the overview): vectorised in NumPy or compiled, and by which compiler, whether a simple version of each kernel stands beside the fast one to check it, and the benchmark by which the rate of cell updates per second is measured and tracked during development. For the brief on execution in parallel, it records whether each route runs on the free-threaded build. It leaves the order of the axes and the layout of the state to the brief on the arrays of the state, which serves the route chosen here, the sharing of the work among cores to the brief on execution in parallel, the build backend, the versions of Python and the dependencies to the brief on the package and its installation, and the time within which the production run must complete to the brief on the problems that verify the first pass. In place of that time, the rate of each route is also stated as the hours that the production run would take on the development machine. The brief builds on [B1D1](B01-strata-in-package.md#b1d1-the-subpackages-of-the-strata), which places what the route provides to the strata above in `mhdpy.infrastructure`, on [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata), under which a stratum reaches code above it only through objects handed down, and on [B1D4](B01-strata-in-package.md#b1d4-the-place-of-the-tests), which places the tests in `tests/`.

## B2D1 Vectorised or compiled

**Decision.** In the context of kernels that take most of the time of a run, facing a production run of some $9 \times 10^{10}$ cell updates, compiled loops over the cells, with copies of whole arrays left to NumPy (option B), are chosen over vectorised NumPy (A). This achieves performance, five to fifteen times that of NumPy in [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md), accepting wheels of mhdpy for every platform and version of Python that it supports, and kernels that are fast only once compiled. Decided on 2026-11-10, as recommended.

**Question.** Every loop over cells of strata 2 to 4 is written in one route, chosen before the first kernel, as the route fixes how kernels read and run, what the installation needs and the layout that the arrays of the state must serve ([§5](../overview.md#5-crosscutting-concepts) of the overview). The production run needs some $9 \times 10^{10}$ cell updates ([topic 42, §4](../topics/42-parallelisation-and-performance.md#4-assessment)), and no reference times one finite-volume kernel of hydrodynamics in every route on one machine ([topic 41, §1](../topics/41-vectorised-and-compiled-kernels.md#1-overview)). The compiler of a compiled route is chosen afterwards. To be read first are [topic 41, §2.1](../topics/41-vectorised-and-compiled-kernels.md#21-vectorisation-in-numpy), [§2.2](../topics/41-vectorised-and-compiled-kernels.md#22-compilers-for-python) and [§4](../topics/41-vectorised-and-compiled-kernels.md#4-assessment), and [topic 35, §2.5](../topics/35-packaging-configuration-and-build.md#25-compiled-kernels-and-their-builds). Wrapped Fortran, which pyro gave up for Numba ([pyro 1.1](../references/pyro-synthesis.md#11-origin-version-and-licence)), is left out. **[GK]** So are generated and traced kernels, with their heavy dependencies ([topic 41, §4](../topics/41-vectorised-and-compiled-kernels.md#4-assessment)).

**Option A: vectorised in NumPy.** Each kernel is a sequence of operations on whole arrays, which NumPy performs in compiled loops, so that mhdpy holds no compiled code. Ulula takes this route and reaches about $2.5 \times 10^6$ cell updates per second in two dimensions on a MacBook Pro of 2025, limited by the speed of NumPy ([Ulula 3.7](../references/ulula-synthesis.md#37-performance)). Each operation writes a temporary array, which streams over the memory bus, and slices hide the index notation of the papers unless shifted views restore it ([topic 41, §2.1](../topics/41-vectorised-and-compiled-kernels.md#21-vectorisation-in-numpy)). NumPy runs as fast in the free-threaded build as in the default one ([Performance in Python 2.4.3](../references/performance-in-python-synthesis.md#243-the-free-threaded-build-on-six-cores)). **[GK]** For mhdpy, the package stays pure Python and installs from wheels everywhere, 3.14t included ([Performance in Python 3.4](../references/performance-in-python-synthesis.md#34-numba-a-compiler-built-on-llvm)), and at Ulula's rate the production run takes about ten hours on one core. Kernels whose work differs between cells, such as the substeps of cooling, vectorise poorly, as every cell takes the longest path. The arrays of the state must keep each variable contiguous ([topic 36, §2.5](../topics/36-data-structures.md#25-layouts-for-kernels)).

**Option B: compiled loops.** Each kernel is a loop over the cells in the index notation of the papers, which a compiler turns into machine code, just in time or ahead of time. pyro compiles its kernels with Numba ([pyro 1.1](../references/pyro-synthesis.md#11-origin-version-and-licence)), and Athena++ makes the corresponding choice in C++, with loops along the axis contiguous in memory that the compiler vectorises ([Athena 3.9](../references/athena-synthesis.md#39-performance)). Fusing what NumPy does in steps, without temporaries, a typed loop of Cython runs about ten times faster than its expression in NumPy on large arrays, and Pythran brings one expression from 1.23 ms to 418 μs on one core ([Performance in Python 2.2.2](../references/performance-in-python-synthesis.md#222-cython), [2.3.2](../references/performance-in-python-synthesis.md#232-pythran-against-cpython-cython-pypy-and-numexpr)). **[GK]** For mhdpy, the kernels read like the papers, and each cell takes only the branches and substeps that it needs. The single command depends on the compiler, as Numba has no wheel for Python 3.14 on the development machine, and Cython and Pythran need wheels for every platform and version, and a compiler for an installation from the sources ([Performance in Python 2.2.3](../references/performance-in-python-synthesis.md#223-numba), [3.4](../references/performance-in-python-synthesis.md#34-numba-a-compiler-built-on-llvm)). Fast loops favour plain arrays ([topic 36, §2.5](../topics/36-data-structures.md#25-layouts-for-kernels)), and run without the GIL in the free-threaded build only where their compiler allows.

**Experiments.** [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) times one step of hydrodynamics in two dimensions on one core of the development machine. On $2048^2$ cells, the loop compiled by Cython or Pythran, which install and build on Python 3.13, 3.14 and 3.14t, updates $8.1$ to $9.5 \times 10^6$ cells per second, 11 to 15 times plain NumPy and 5 to 9 times NumPy in place, and compiled by Numba, on 3.13 alone, $4.2 \times 10^6$. Every version gives the result of plain NumPy to round-off.

**Recommendation.** Option B, since loops compiled by Cython or Pythran run 11 to 15 times faster than plain NumPy at the size of the production run, shortening it on one core from 34 to 40 hours to about three, and five to nine times faster than NumPy in place, beyond the factor of five that [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) set in advance. The option serves performance, the second priority of §1, and keeps readability, the third, as the loops read in the index notation of the papers, whereas NumPy in place takes three times the lines of plain NumPy. It gives up some extensibility, the fourth, as a new kernel runs fast only once compiled, and rests the exception of §1 on wheels of mhdpy for every platform and version of Python that it supports, which the brief on the package must provide.

**Set aside.** Option A would return if the wheels that option B needs could not be built for a platform or version of Python that mhdpy supports, since NumPy installs wherever its own wheels do.

## B2D2 The compiler of the kernels

**Decision.** In the context of compiled loops for every kernel, facing compilers that differ in what they demand of the source and the installation, Cython in its pure mode, with the signatures of each module in a file `.pxd` and the types of local variables inferred under `infer_types=True` (option B), is chosen over Numba (A) and Pythran (C). This achieves readability and performance, accepting a declaration per function apart from its code. Decided on 2026-11-10, as recommended.

**Question.** [B2D1](#b2d1-vectorised-or-compiled) makes every kernel of strata 2 to 4 a compiled loop, which leaves the compiler to be chosen before the first kernel, since it fixes how the types of a kernel are declared, which Python a kernel may use, and how the package is built and installed. The three compilers differ in when they compile and in what they demand of the source ([topic 41, §2.2](../topics/41-vectorised-and-compiled-kernels.md#22-compilers-for-python)), and [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) has compiled one module of loops with each. To be read first are [Performance in Python 2.2.2](../references/performance-in-python-synthesis.md#222-cython) to [2.2.5](../references/performance-in-python-synthesis.md#225-designing-a-code-with-numba), and [3.3](../references/performance-in-python-synthesis.md#33-cython-building-and-distributing-compiled-modules) to [3.5](../references/performance-in-python-synthesis.md#35-pythran-modules-that-stay-python).

**Option A: Numba.** Each kernel is plain Python, which Numba compiles through LLVM when it is first called, without declarations of types and without a compiler on the machine ([topic 41, §2.2](../topics/41-vectorised-and-compiled-kernels.md#22-compilers-for-python)). pyro compiles its kernels so, and AGATE spends about 13 s compiling at the start of each run, unless the compiled code is cached ([pyro 1.1](../references/pyro-synthesis.md#11-origin-version-and-licence), [Performance in Python 2.3.1](../references/performance-in-python-synthesis.md#231-the-modes-of-agate-on-the-orszagtang-vortex), [3.4](../references/performance-in-python-synthesis.md#34-numba-a-compiler-built-on-llvm)). Fast code calls for a data-oriented design of plain arrays ([2.2.5](../references/performance-in-python-synthesis.md#225-designing-a-code-with-numba)). **[GK]** For mhdpy, a kernel reads as plain Python, a new kernel needs no compiler, and the package stays pure Python. But the Package Index holds no wheel of Numba for Python 3.14 on macOS with Intel processors, so that on the development machine the single command fails for 3.14 and 3.14t, and the free-threaded build stays out of reach there ([2.2.3](../references/performance-in-python-synthesis.md#223-numba)).

**Option B: Cython.** Each kernel is a module of Python that Cython translates into C ahead of time, its types declared in the pure mode, in a file `.pxd` beside it or in decorators that the interpreter ignores, so that the module still runs uncompiled ([Performance in Python 2.2.2](../references/performance-in-python-synthesis.md#222-cython), [3.3](../references/performance-in-python-synthesis.md#33-cython-building-and-distributing-compiled-modules)). Veros writes its tridiagonal solves in Cython ([2.2.9](../references/performance-in-python-synthesis.md#229-tracing-by-jax-in-veros)). **[GK]** Cython reports its errors at the lines of the Python source, ignores annotations on request, so that a module keeps the imports and annotations that strict typing needs, and lets a module declare itself compatible with free threading, as experimental since its release 3.1 ([2.2.2](../references/performance-in-python-synthesis.md#222-cython)). For mhdpy, the types of a kernel are declared apart from its code and must be kept in step with it. The build backend must compile C, and the single command rests on wheels of mhdpy for every platform and version of Python that it supports.

**Option C: Pythran.** Each kernel is a function in a subset of Python without classes, whose exported signatures a comment declares, and Pythran compiles the module ahead of time into C++, the language of Athena++, inferring every other type ([Performance in Python 2.2.4](../references/performance-in-python-synthesis.md#224-pythran), [3.5](../references/performance-in-python-synthesis.md#35-pythran-modules-that-stay-python)). A build without Pythran can fall back to the module in pure Python ([topic 35, §2.5](../topics/35-packaging-configuration-and-build.md#25-compiled-kernels-and-their-builds)). **[GK]** SciPy builds some of its modules with Pythran ([3.5](../references/performance-in-python-synthesis.md#35-pythran-modules-that-stay-python)). For mhdpy, a kernel needs no declaration beyond its comment. Pythran accepts no import of `typing` or `numpy.typing` and compiles the annotations of a module, so that strict typing needs the arrays annotated by strings ([B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md)), and it reports its errors in the C++ that it generates. The build and the single command rest on wheels, as for Cython.

**Experiments.** [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) compiles one module of loops with each compiler on the development machine. On $2048^2$ cells, Cython updates $8.1$ to $9.3 \times 10^6$ cells per second and Pythran $8.6$ to $9.5 \times 10^6$, both install and build on Python 3.13, 3.14 and 3.14t and leave the GIL disabled on 3.14t, and Numba updates $4.2 \times 10^6$ on 3.13 alone, each with the result of plain NumPy. Pythran needs one comment, and [B2E2](../experiments/B02-kernels/E2-declarations-for-cython/README.md) shows that Cython keeps its rate with a file `.pxd` of the signatures alone, 6 lines instead of 14, if it infers the types of the local variables under `infer_types=True`.

**Recommendation.** Option B, since Cython runs the kernels as fast as Pythran and twice as fast as Numba, installs on every version of Python of the development machine, and needs only the signatures of the functions of a module, by [B2E2](../experiments/B02-kernels/E2-declarations-for-cython/README.md). Against Pythran, it keeps the imports and annotations of `numpy.typing` that strict typing needs, and reports its errors at the lines of the Python source rather than in generated C++. It serves readability, the third priority of §1, against Pythran, and performance, the second, against Numba, which the exception of §1 rules out on the development machine. It gives up a declaration per function in a file beside the module.

**Set aside.** Option C would return if Cython came to need more than signatures, as Pythran infers all but the exported types. Option A would return if Numba had wheels for every platform and version that mhdpy supports, as its kernels need no compiler.
