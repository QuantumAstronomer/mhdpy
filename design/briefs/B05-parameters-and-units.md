# B5 Parameters and units

**Status.** Open.

**Topics.** [Topic 37, §2.5](../topics/37-driver-and-control-of-time-step.md#25-runtime-parameters-and-units), with [topic 38, §2](../topics/38-problem-setups-and-user-functions.md#2-designs) for the parameters that problems declare, [topic 39, §2.2](../topics/39-output-restarts-and-analysis.md#22-snapshots-in-hdf5) for the parameters that outputs record, and [topic 2, §2.1](../topics/02-equations-of-state.md#21-the-ideal-and-the-isothermal-gas), [topic 17, §2.1](../topics/17-thermal-conduction.md#21-the-classical-flux-and-its-suppression) and [topic 20, §2.1](../topics/20-radiative-cooling.md#21-cooling-in-the-equation-of-the-energy) for the units and constants that the temperature, conduction and cooling need.

**Supersedes.** None.

## Scope

The brief settles how the parameters of a run reach the modules that use them, and in which units the parameters and the state are measured ([§5](../overview.md#5-crosscutting-concepts) of the overview). It decides how a module declares its parameters with their defaults and what is checked before a run starts, in which form a user gives their values, what a run records of them and of its seeds so that it can be repeated, the system of units, and the physical constants that conduction and cooling need. Its choices must serve the tests that close stratum 1 by [§3.1](../overview.md#31-infrastructure) of the overview: parameters with defaults, overrides and unknown names, and units against their constants. It leaves the form of a problem, and where a problem places its declaration, to the brief on problem setups and user functions. The form in which outputs and restarts keep the record, and which parameters a restart may change, are left to the brief on outputs, restarts and analysis. The launching of a run, from the command line or from Python, is left to the brief on the driver, and the parameters of each module, such as the mean mass of a particle that the temperature needs, to the briefs of its stratum. The brief builds on [B1D1](B01-strata-in-package.md#b1d1-the-subpackages-of-the-strata), which places what it provides in `mhdpy.infrastructure`, and on [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata), under which the strata above reach the infrastructure by imports downwards while it reaches them only through objects handed down, and the top package imports no stratum when it is loaded. [B1D4](B01-strata-in-package.md#b1d4-the-place-of-the-tests) places its tests in `tests/infrastructure/` under the same rule. It builds on [B4D3](B04-packaging.md#b4d3-when-the-physics-is-chosen), which compiles each kernel in versions fixed to the sizes on which its loops over cells depend, among which a run chooses as it starts, and gives values such as $\gamma$ to each call, so that the parameters must fix those sizes before a run starts and a size without a compiled version must fail at once. It also builds on [B3D1](B03-parallel-execution.md#b3d1-threads-or-processes), which shares each step among the threads of one process, whose number is a parameter of a run, on [B4D1](B04-packaging.md#b4d1-the-versions-of-python-and-the-platforms), under which the code may use the language of Python 3.14, on [B4D4](B04-packaging.md#b4d4-the-dependencies), under which NumPy is the only dependency at run time and any further package must be justified by the brief that needs it, and on [B4D6](B04-packaging.md#b4d6-the-version-and-its-record), beside whose record of the version a run records its parameters.

## B5D1 The declaration of parameters

**Decision.** In the context of parameters that every module of every stratum reads, facing faults that must show before any block is built, one frozen dataclass per module, whose fields give each parameter its name, type, default and allowed values, handed by the driver to the reader (option C), is chosen over dictionaries of defaults (A) and defaults stated where values are read (B). This achieves correctness and readability, as faults show before a run starts and strict checking follows every read, accepting a class in every module and a reader that checks types itself. Decided on 2026-11-11, as recommended.

**Question.** Every module declares the parameters that it reads, with their defaults ([§5](../overview.md#5-crosscutting-concepts) of the overview), in a form to be settled before the first module of stratum 1. The form fixes which faults are caught before a run starts: an unknown or misspelt name, a value of the wrong type, and a size for which no compiled version of a kernel exists, which must fail at once under [B4D3](B04-packaging.md#b4d3-when-the-physics-is-chosen). It also fixes whether the strict checking of types of §3.2 follows each read, and how the declarations reach the reader in the infrastructure, which may not import the modules above it ([B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata)). To be read first are [topic 37, §2.5](../topics/37-driver-and-control-of-time-step.md#25-runtime-parameters-and-units) and [§4](../topics/37-driver-and-control-of-time-step.md#4-assessment), [topic 38, §4](../topics/38-problem-setups-and-user-functions.md#4-assessment), [pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters) and [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop). **[GK]** Libraries that check typed settings, such as pydantic, are left out under [B4D4](B04-packaging.md#b4d4-the-dependencies), and so is a registry filled as modules are imported, whose contents would depend on what a process happened to import.

**Option A: dictionaries of defaults.** Each module names its parameters with their defaults in a dictionary, from which the reader infers their types, and reads a value by its name. pyro keeps such defaults in files and, for each problem, in a dictionary, lets an inputs file change only declared names, warning of others, and reports unread parameters at the end ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). **[GK]** For mhdpy, the driver hands the dictionaries of a run to the reader, so that an unknown name can be refused before the run starts. A value read by its name has no type that strict checking can follow, unless a typed dictionary states every name a second time with its type, and a name misspelt in the code fails only when its line runs. Allowed values, such as the sizes of B4D3, need checks of their own.

**Option B: defaults where values are read.** A module states the default of each parameter where it reads it, and a default joins the parameters of the run where the user gave no value. Athena++ reads so through `GetOrAddReal` and its siblings, which record every value in use for the head of its restart files, and lets its command line change only parameters that its input file holds ([Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop)). **[GK]** For mhdpy, no declaration stands apart, and a getter for each type returns a value that strict checking follows. An unknown name in the inputs can be found only after every module has read its values, so that all modules must be built before the first block. A name misspelt in the code takes its default unseen, and a parameter read in two places may receive two defaults.

**Option C: typed declarations handed to the reader.** Each module declares its parameters as one frozen dataclass of the standard library, whose fields give each parameter its name, type and default and, where it is limited, its allowed values, as for the sizes of B4D3. The driver hands the classes of a run to the reader, which checks the values given against them, fills the defaults and returns for each module an instance that cannot be changed, read by attribute. Ulula comes closest, as its scheme is a class whose constructor takes the parameters of the time step with their defaults and refuses values out of range ([Ulula 3.2](../references/ulula-synthesis.md#32-the-simulation-object-and-its-data)). **[GK]** A dataclass ([PEP 557](#pep-557)) takes the type of each field from its annotation, its constructor refuses an unknown name, and the metadata of a field can carry allowed values or a unit. For mhdpy, an unknown name, a value of the wrong type and a size without a compiled version all fail before any block is built, and strict checking follows every read, a misspelt attribute included. The parameters of a module stand in one place, each default once. Each module adds a class, and the reader must check the types of the values itself, as dataclasses do not.

**Experiments.** None, since the references and the documentation of Python settle what each option declares and when it can be checked.

**Recommendation.** Option C, since every fault that the question names then shows before any block is built, as [B4D3](B04-packaging.md#b4d3-when-the-physics-is-chosen) demands and [§3.1](../overview.md#31-infrastructure) of the overview tests, while strict checking follows every read, which option A allows only by stating each name twice, and option B only with names unknown until every module is built. The parameters of a module stand in one place, each default once. The option serves correctness, the first priority of §1, and readability, the third, and gives up none, performance included, at the price of a class in every module and a reader that checks types itself.

**Set aside.** Option B would return if the parameters of a module came to depend on values read while a run is built, such as a table that names parameters of its own, since reads at the point of use follow them without a declaration made in advance.

## B5D2 The format of the values

**Decision.** In the context of values that a user gives for a run and that its record must give back, facing a standard library that reads TOML but does not write it, files of TOML with one table to each class of [B5D1](#b5d1-the-declaration-of-parameters), overridden by values from Python and from the command line that may change only declared names, with the record written in TOML by a writer of mhdpy (option B), are chosen over Python alone (A) and files of sections read by `configparser` (C). This achieves correctness and usability, as a run can be repeated from its record and its values change without editing a script, accepting a writer of mhdpy for the record. Decided on 2026-11-11, as recommended.

**Question.** The reader of [B5D1](#b5d1-the-declaration-of-parameters) receives the values that a user gives for a run, checks them against the classes of its modules and fills the defaults. The form in which the values are given must be settled with the reader, since it fixes what the reader parses, how values given in several places override each other, as the tests of [§3.1](../overview.md#31-infrastructure) of the overview check, and in which form the record of a run can be read back. A problem setup is written in Python ([§2](../overview.md#2-context-of-a-run) of the overview), in a form that the brief on problem setups decides, and the launching of a run is left to the brief on the driver. To be read first are [topic 37, §2.5](../topics/37-driver-and-control-of-time-step.md#25-runtime-parameters-and-units), [pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters), [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop) and [Ulula 3.3](../references/ulula-synthesis.md#33-the-runtime-function). **[GK]** JSON, which the standard library reads and writes, is left out, as it allows no comments in files written by hand, and so is YAML, whose reader would join the dependencies at run time against [B4D4](B04-packaging.md#b4d4-the-dependencies).

**Option A: Python alone.** The script that runs a problem gives the values as instances of the classes of B5D1, and no file of parameters exists. Ulula passes its parameters so, as arguments of its runtime function and of the constructor of its scheme ([Ulula 3.2](../references/ulula-synthesis.md#32-the-simulation-object-and-its-data), [3.3](../references/ulula-synthesis.md#33-the-runtime-function)). **[GK]** For mhdpy, strict checking follows each value where it is written, the reader parses nothing, and one language serves problems and runs. A run is repeated by its script, a variant by a copy of the script or a loop in Python, and a value can be changed from the command line only by code of the script. The record of a run still needs a form in which a later run can read it.

**Option B: files of TOML.** A file in the format TOML gives one table to each class of B5D1, with lines `name = value` and comments, and holds integers, floats, booleans, strings and arrays as such. Values given from Python as a dictionary, and from the command line as `table.name=value`, override those of the file, which override the defaults, and each may change only a declared name, as pyro and Athena++ let theirs change only names they know ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters), [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop)). **[GK]** The standard library reads TOML from Python 3.11, the format of `pyproject.toml`, but leaves writing it to packages such as tomli-w ([PEP 680](#pep-680)). An override from the command line is itself a line of TOML, which the same reader parses. For mhdpy, the values of a run stand in a file apart from its code, to be kept, compared and changed without editing a script, and TOML tells an integer from a float, so that `nscalars = 1.0` fails as the wrong type. A record in TOML, which a later run could read, needs a writer of mhdpy for tables of single values and arrays, unless B4D4 admits a further dependency.

**Option C: files of sections, as pyro and Athena++.** A file of sections, one to each class of B5D1, with lines `name = value` and comments, as pyro reads `[section]` and Athena++ `<block>` ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters), [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop)), with overrides from Python and the command line as in option B. **[GK]** The module `configparser` of the standard library reads and writes such files, keeping each value as a string, which the reader converts by the type that B5D1 declares, once the substitution of values that it performs by default is switched off and its folding of names to lower case is allowed for. For mhdpy, the record is written and read by the standard library alone, in the format of the references, at the price of values without types of their own and of arrays written by a convention of mhdpy.

**Experiments.** None, since the standard library and the references settle what each format holds and how it is read and written.

**Recommendation.** Option B, since the values of a run then stand in a file apart from its code, which one parser reads together with the overrides from the command line, and in which the record can be written for a later run to read back, while TOML tells an integer from a float where the strings of option C cannot. Against option A, the form that the record needs in any case also serves the inputs, and values from Python remain possible as overrides. The option serves correctness, the first priority of §1, as a run can be repeated from its record, and usability, the fourth, through files of a format that Python projects know. It gives up some readability, the third, as the record needs a short writer of mhdpy, which spares the dependency that tomli-w would add.

**Set aside.** None, as option B keeps the values from Python that option A would offer alone, and holds all that the files of option C hold.

## B5D3 The record

**Decision.** In the context of runs that must be repeatable from the record that they leave, facing defaults that may change in the code after a run, every parameter of the modules of a run with its value in use, defaults included, written in TOML as one file of inputs as the run starts (option A), is chosen over the values given alone (B) and every value marked with its source (C). This achieves correctness and readability, as the record alone gives a later run the same values through the simplest writer, accepting a record that shows the values chosen only against the inputs of the run. Decided on 2026-11-11, as recommended.

**Question.** A run records its parameters beside the version and the commit of [B4D6](B04-packaging.md#b4d6-the-version-and-its-record), so that it can be repeated ([§5](../overview.md#5-crosscutting-concepts) of the overview), and [B5D2](#b5d2-the-format-of-the-values) writes the record in TOML, so that a later run can read it as its inputs. Which values the record holds must be settled before its writer is built, as it fixes whether a run can be repeated once a default has changed, and whether a reader of the record can tell the values chosen from the defaults. The record is written as a run starts, before its first step, so that a run that fails still leaves it. The seeds of the random numbers of a run are parameters like any other under [B5D1](#b5d1-the-declaration-of-parameters), declared by the modules that draw them, and the record holds them with the rest. Where outputs and restarts keep it is left to the brief on outputs, restarts and analysis. To be read first are [topic 37, §4](../topics/37-driver-and-control-of-time-step.md#4-assessment), [topic 39, §2.2](../topics/39-output-restarts-and-analysis.md#22-snapshots-in-hdf5) and [§4](../topics/39-output-restarts-and-analysis.md#4-assessment), [pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters) and [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop). **[GK]** A float written as Python represents it, by the shortest string that reads back to it, returns exactly, so that a record in TOML gives back every value of a run.

**Option A: every value in use.** The record holds every parameter of the modules of the run with its value, defaults included, as one file of inputs. pyro writes its full set to a file `inputs.auto` and into its outputs in HDF5, and Athena++ adds each default to its parameters as it reads it, so that the head of its restart files holds every value in use ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters), [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop)). For mhdpy, the record alone gives a later run the same values, even after a default has changed in the code, and names every value that the analysis of a run may need. Which values the user chose shows only against the inputs of the run.

**Option B: the values given alone.** The record holds only the values that the user gave, in the file and the overrides, and leaves the defaults to the code whose version and commit stand beside it. No reference records so. For mhdpy, the record is short and shows what was chosen for the run. A default changed in a later commit alters a run repeated from the record unseen, and B4D6 records whether the tree differed from its commit but not how, so that a run made with changes not yet committed cannot be repeated from its record.

**Option C: every value with its source.** As option A, with a comment beside each value that names where it came from: its default, the file, Python or the command line. No reference marks its values so, while pyro keeps beside the values of `inputs.auto` the comments of its files of defaults ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). **[GK]** A reader of TOML passes over comments, so that the record still reads back as inputs. For mhdpy, the record shows the full set and the values chosen at once. The reader must carry the source of each value through the overrides of B5D2, and a run repeated from a record marks every value as taken from its file.

**Experiments.** None, since the options differ in which values are written, which no measurement decides.

**Recommendation.** Option A, since the record then gives back every value of a run by itself, even after a default has changed or where the tree held changes never committed, which option B cannot, while its writer writes values alone, which option C would mark at the price of a source carried through every override. The values chosen show against the inputs of the run, which the brief on outputs may keep beside the record. The option serves correctness, the first priority of §1, and readability, the third, through the simplest reader and writer, and gives up a record that shows at a glance which values were chosen.

**Set aside.** Option C would return if records came to be compared across many runs, as in a study of parameters, since marks of the values chosen would show at a glance where runs differ.
