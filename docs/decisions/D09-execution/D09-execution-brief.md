## 1. Introduction

This brief decides how the work of a time step is organised and carried out over blocks and workers. It covers:

- whether a step is a fixed sequence of phases or a graph of tasks with dependencies;
- how large each call into compiled code is;
- how blocks are assigned to workers and how workers synchronise;
- the default number of workers.

The content of the step is decided elsewhere: which stages the integrator has (D11), which physics contributes which operations (D12), and how steps follow one another with outputs (D13). This brief fixes the machinery that runs them.

The earlier briefs fix much of the frame:

- **D04 (backend).** Python decides *what* happens and in which order; every operation that touches all cells of a block is compiled.
- **D05 (parallelism).** Workers are Python threads that update whole blocks, with development focused on the free-threaded interpreter while the standard one must perform well too (D05.3, D05.4). Results must not depend on the number of workers or on scheduling, and sums are combined in a canonical block order (D05.5). The default number of workers is to be the number of physical cores on the free-threaded interpreter, and on the standard one is to be chosen here (D05 §4).
- **D06 and D07 (data model, mesh).** All blocks of a process are one array per centring and role (`[block, var, k, j, i]`), stored in Morton order, so a contiguous range of blocks is a contiguous range of memory. Every worker needs several blocks.
- **D08 (communication).** Ghost cells are filled through exchange plans by a compiled kernel, one call per worker and stage. The order within a stage is: exchange, physical boundary conditions on primitives, conversion, kernels.

D08 also left one problem open. In a Linux container, the standard interpreter still collapsed beyond four workers, even with compiled ghost copies (E08.1). What still held the GIL there was the per-block kernel calls themselves. This brief tests the remedy: looping over a worker's blocks inside compiled code.

**What the references do** (syntheses in `References/`):

- **Athena++** expresses a step as **task lists**. Each task is a member function for one MeshBlock and one stage, with a dependency bit mask. The executor loops over blocks and their remaining tasks and runs whichever has its dependencies met. A task that waits for an MPI message reports failure and is retried later, so communication overlaps with independent work. The main list is built at start-up from the configured physics, and the integrator itself is encoded as task-list stages with weights. S20 counts task lists among the most important parts of the design. The synthesis notes two drawbacks: the main list is generated by a long chain of nested conditionals (marked "horrible" in a TODO in the source), and the flexibility it offers, different task lists in different regions, had no published application yet. Threads are coarse-grained (each updates whole MeshBlocks), and blocks are distributed over processes along the Z-order by measured cost, rebalanced periodically.
- **Athena** (C) used a fixed sequence per step, with separate integrators for 1D, 2D and 3D.
- **Pyro**, **Ulula** and **ZEUS** use a fixed sequence of operations per step: ZEUS a fixed order of operator-split substeps, Pyro and Ulula one method that calls the stages in order.

## 2. Evidence

### E09.1 — Orchestrating a step over blocks and workers

**Method.** [`experiments/E09.1b-orchestration.py`](experiments/E09.1b-orchestration.py) runs full SSP-RK2 steps on the thesis grid (4000 × 1000, periodic, blocks of 50² and 25² in Morton order). The ghost cells are filled through an exchange plan by the compiled copy kernel, one call per worker and stage (D08). The same work is orchestrated in four ways, with the kernels of [`E09.1a-kernels.py`](experiments/E09.1a-kernels.py):

- **per-block calls, persistent team:** a fixed team of worker threads, each owning a contiguous range of blocks, with a barrier after each stage; the kernels are called once per block, as in E05–E08;
- **ranged calls, persistent team:** the same team, but each worker makes one call per stage for its whole range. The compiled code loops over the blocks, computing each block's time derivative and stage combination without the GIL;
- **ranged calls, thread pool:** no persistent team. The main thread submits each stage as one task per worker to a `ThreadPoolExecutor` and waits for all of them before the next stage;
- **barriers only:** the persistent team synchronising twice per step without any work, which measures the cost of synchronisation alone.

[`E09.1d-run.py`](experiments/E09.1d-run.py) runs it natively (6 cores, 12 hardware threads) and in a Linux container ([`E09.1c-Dockerfile`](experiments/E09.1c-Dockerfile), 8 virtual CPUs), each with the free-threaded and the standard interpreter (requested as `3.14+gil`, and checked). All 72 configurations that compute were bit-for-bit identical to a single-block serial reference. Full output: [`results/E09.1d-orchestration.md`](experiments/results/E09.1d-orchestration.md).

**Results.** Million cell updates per second, at the largest number of workers (natively 12, in the container 8):

| Interpreter, platform | Block | Per-block calls | Ranged calls, team | Ranged calls, pool |
|---|---|---|---|---|
| Free-threaded, macOS | 50² | 34.0 | 36.6 | 35.6 |
| Free-threaded, macOS | 25² | 23.9 | 26.6 | 25.7 |
| With GIL, macOS | 50² | 29.0 | 37.0 | 38.4 |
| With GIL, macOS | 25² | 13.5 | **24.9** | **26.1** |
| Free-threaded, Linux container | 50² | 20.8 | 21.7 | 21.1 |
| With GIL, Linux container | 50² | 8.3 | **21.2** | **21.4** |
| With GIL, Linux container | 25² | 2.3 | **19.3** | **19.5** |

Synchronisation alone (two barriers per step) cost 0.15–0.5 ms per step natively and 0.5–2.2 ms in the container. A step of the thesis grid takes about 110–150 ms on 6–12 workers.

- **Ranged calls remove the collapse of the standard interpreter.** In the container with 8 workers and 25² blocks, throughput rises from 2.3 to 19.3 million cell updates per second, eightfold. With ranged calls, the standard interpreter is as fast as the free-threaded one on every platform, block size and number of workers measured. What remains under the GIL is a handful of calls per worker and stage, independent of the number of blocks. That settles the question D05.4 and D08 left open: *the standard interpreter performs well when the Python per stage does not grow with the number of blocks.*
- **Ranged calls are also never slower,** 3–13 % faster on one worker, and up to 11 % with several workers on the free-threaded interpreter.
- **A thread pool is as fast as a persistent team** within the run-to-run variation (±15 %). The pool is simpler: the main thread runs the stages in order and waits for each, with no barriers or command handshakes to program.
- **Barriers are cheap on one node:** 0.1–0.4 % of a step natively, 0.5–2 % in the container. Overlapping communication with computation, the main benefit of Athena++'s task lists, has little to gain where all data is in one shared memory. It is a matter for an MPI backend (D05.1).

### E09.2 — Assigning blocks of unequal cost to workers

**Method.** On the thesis problem, the cost per block will not be uniform. Radiative cooling with substeps, for example, costs most where the gas cools fastest, in and around the cloud. [`experiments/E09.2-load-balance.py`](experiments/E09.2-load-balance.py) emulates that on the thesis grid (4000 × 1000, blocks of 50² in Morton order):

- **The cloud:** blocks within 0.25 domain heights of a point get extra work in every stage, calibrated to four times their hydrodynamic update. That is 80 of 1600 blocks, adding 20 % to the total work, in one compact region.
- **Assignments compared**, with ranged calls (E09.1):
  - contiguous Morton ranges with equal block counts;
  - contiguous Morton ranges with equal total cost, from the known cost of every block;
  - dynamic chunks of 4 blocks claimed from a shared counter, phase by phase.
- **Baselines:** each assignment is also run with uniform cost.

It ran natively on 6 and 12 workers with both interpreters. All runs were bit-for-bit identical to the reference: the extra work does not change the state, and the assignment does not change the arithmetic. Full output: [`results/E09.2-load-balance.md`](experiments/results/E09.2-load-balance.md).

**Results.** Milliseconds per step:

| Assignment | Free-threaded, 6 | Free-threaded, 12 | With GIL, 6 | With GIL, 12 |
|---|---|---|---|---|
| Uniform cost, static equal counts | 127.5 | 110.8 | 124.1 | 111.0 |
| Uniform cost, dynamic | 107.3 | 124.3 | 106.5 | 95.7 |
| Cloud, static equal counts (heaviest worker 1.8× the mean) | 206.9 | 177.2 | 206.5 | 147.6 |
| Cloud, static cost-weighted | 141.5 | 141.4 | 141.0 | 120.6 |
| Cloud, dynamic | **120.2** | **138.9** | **119.0** | **104.5** |

- **Equal counts are badly unbalanced as soon as cost is concentrated.** A compact region falls into one or two contiguous Morton ranges, whose workers carry 1.8 times the mean load. The step took 20–75 % longer than with the alternatives (40–75 % on 6 workers).
- **Dynamic assignment was the fastest or equal in every case, and needs no cost model.** Cost-weighted ranges came second. They need the cost of every block in advance, measured in an earlier step, and are only as good as that measurement.
- **Dynamic assignment also helps when all blocks cost the same,** in three of four runs with 14–16 % less time per step. Static ranges assume all cores are equally fast; with hyperthreading, varying clock speeds and other processes, they are not, and a dynamic queue absorbs the difference. In the fourth run (free-threaded, 12 workers) the uniform dynamic run was slower, within the run-to-run variation.
- **Some runs with the cloud were faster than "uniform × 1.2" predicts.** The emulated cooling is pure arithmetic, and it parallelises better than the hydrodynamic update, which competes for memory bandwidth. Relative comparisons between assignments are unaffected.

**What the two experiments mean together.**

- **Ranged calls:** keeping the Python per phase independent of the number of blocks, by looping over blocks in compiled code, is what makes the standard interpreter scale.
- **Synchronisation:** it is cheap on one node, so bulk-synchronous phases cost nothing worth a task graph.
- **Assignment:** dynamic assignment of small chunks handles uneven cost and uneven cores without a cost model.
- **Determinism:** none of these choices affects the result, bit for bit.

## 3. Decisions

### D09.1 — The structure of a step

Is a step a fixed sequence of phases, or a graph of tasks with dependencies?

**Options**

- **A. A fixed sequence of phases, run bulk-synchronously.** Each stage of the integrator is a list of phases: exchange, boundary conditions, primitives, fluxes and update, sources. Each phase is carried out for all blocks by all workers, and the next phase starts when all have finished. Simple to read and to test; the order of operations is visible in one place.
- **B. Task lists per block with dependencies,** as Athena++. Every block runs through its own list, and a task runs once its dependencies are met, so blocks are never held up by a global synchronisation, and communication overlaps with computation. The executor would run in Python, one decision per task and block, and the gain it offers is small where synchronisation costs 0.1–2 % of a step (E09.1). Athena++'s experience also shows the cost: the list builder became a chain of nested conditionals.
- **C. A, with the phases described as data.** Each phase is a named operation with the arrays it reads and writes, contributed by the integrator (D11) and the physics modules (D12) through registration, not assembled by hand-written conditionals. The bulk-synchronous executor runs them in order. Because the dependencies are declared, a task-graph executor could later replace it, for example for an MPI backend that overlaps messages with computation, without touching the modules.

**Recommendation.** C. On one node, bulk-synchronous phases lose almost nothing (E09.1), and they keep the step readable and testable. Describing the phases as data takes the lesson from Athena++, "describe the algorithm as data", without its executor or its hand-built list. It keeps open the one case where a task graph pays off: distributed memory, where communication latency must be hidden. This serves **readability** and **extensibility**, at no cost in **performance**.

**Decision.** *(2026-10-12)* **C, a fixed sequence of phases, described as data.** A fixed sequence keeps the blocks and workers synchronised in a clear way, and describing the phases as data takes the lesson learned from Athena++ without its executor or its hand-built list.

### D09.2 — The granularity of compiled calls

Do kernels act on one block per call, or on a range of blocks?

**Options**

- **A. One block per call,** as D04.2 stated and E04–E08 did. The simplest interface. But Python then makes a call for every block and phase, and under the standard interpreter each call takes the GIL: the collapse of E05.2, E08.1 and E09.1.
- **B. A range of blocks per call:** kernels take the state's arrays and a range `b0 .. b1` (in the canonical Morton order) and loop over those blocks in compiled code without the GIL. They do every per-block step of a phase for one block before moving to the next, while its data is in the cache. The per-block computation is the same function as before; only the loop around it moves into compiled code. Per-block calls remain possible for tests.

**Recommendation.** B. It cured the collapse of the standard interpreter (8× in the container), was never slower and up to 13 % faster otherwise (E09.1). It makes the Python per phase independent of the number of blocks, the condition under which the standard interpreter performs as well as the free-threaded one. It also matches the GPU path of D05.6 (one launch for all blocks of a pack). This partly supersedes D04.2: "one call per block" becomes "one call per range of blocks"; the rest of D04.2 (kernels as functions over arrays, Python orchestrating) stands. This serves **performance**.

**Decision.** *(2026-10-12)* **B, a range of blocks per call.** It showed no downside in the tests, only gains. This partly supersedes D04.2 (one call per block).

### D09.3 — Assigning blocks to workers

How are the blocks of a phase divided among the workers?

**Options**

- **A. Static, equal counts:** each worker gets a fixed contiguous Morton range with the same number of blocks.
- **B. Static, cost-weighted:** contiguous Morton ranges with equal total cost, from costs measured per block during the run and rebalanced periodically, as Athena++ does across processes.
- **C. Dynamic:** workers claim chunks of a few consecutive blocks from a shared counter, phase by phase, until none are left.

**Recommendation.** C, dynamic assignment of chunks of a few consecutive blocks (4 in E09.2), in Morton order, so that a chunk is a contiguous range of memory and a ranged call (D09.2). It was the fastest in every comparison, it needs no cost model, and it adapts at once when the cost moves, as a cloud does. It also evens out cores of unequal speed. Static cost-weighted ranges (B) remain the right tool *between processes* when distributed memory comes (D05.1), where blocks cannot move cheaply and Athena++'s periodic rebalancing applies. Within a process, dynamic chunks are simpler and better. The chunk size is a parameter; 4 worked, and D13 can tune it. This serves **performance**.

**Decision.** *(2026-10-12)* **C, dynamic assignment: workers claim chunks of consecutive blocks.** Workers then do not sit idle while others finish their share, which is where the speed-up comes from, with uneven cost and with uneven cores alike.

### D09.4 — Managing the workers

How are the worker threads organised?

**Options**

- **A. A persistent team** that lives for the whole run and synchronises with barriers, with the main thread signalling each step (E05–E09.1).
- **B. A thread pool** (`concurrent.futures.ThreadPoolExecutor`): the main thread submits each phase as one task per worker and waits for all of them before the next phase.

**Recommendation.** B. It was as fast as the persistent team (E09.1), and simpler and safer. The step is plain sequential Python in the main thread, there are no barriers or command handshakes to get right, and an exception in a worker reaches the main thread through its future instead of leaving the others waiting at a barrier. That last failure, a hang, happened twice while setting up the experiments of D05 and D08. Scratch arrays stay per worker thread (D05). This serves **readability** and **correctness**.

**Decision.** *(2026-10-12)* **B, a thread pool**, in line with D09.1: the main thread runs the phases in order. No obvious downside was found.

### D09.5 — The default number of workers

How many workers does a run use when the user does not say?

**Options**

- **A. The number of physical cores.** Not available from Python's standard library without an extra dependency, and E09.1 measured more throughput with all hardware threads.
- **B. The number of logical CPUs available to the process** (`os.process_cpu_count()`, which respects CPU affinity and so the limits of a batch system or container **[GK]**), on both interpreters.
- **C. A small fixed number on the standard interpreter,** as D05 anticipated before the GIL problem was solved.

**Recommendation.** B, overridable by the user. With ranged calls (D09.2), the standard interpreter needs no smaller default. On the development machine, 12 workers on 6 cores were 5–20 % faster than 6 in E08.1, E09.1 and E09.2, although slower in some configurations of E05.2. The machine-specific optimum can only be found by measuring, so the default should be simple and the override easy. This serves **performance** and **ease of use**.

**Decision.** *(2026-10-12)* **B, the number of logical CPUs available to the process**, overridable, following the recommendation.

## 4. Consequences for higher layers

**For every layer**

- **Phases:** a time step is a fixed sequence of phases per integrator stage. Each phase is a named operation with the arrays it reads and writes. The integrator (D11) and the physics modules (D12) contribute phases by registration, and the order is assembled at set-up, not written as conditionals (D09.1).
- **Execution:** the main thread runs the phases in order. Each phase is executed by the workers of a thread pool, and the next phase starts when all of them have finished (D09.1, D09.4).
- **Kernel calls:** kernels are called for a range of blocks of the state's arrays and loop over them in compiled code without the GIL, doing all per-block steps of a phase for one block before the next (D09.2). The per-block function stays available, for tests and for the uncompiled coverage runs of D04.3.
- **Assignment:** blocks are claimed dynamically in chunks of a few consecutive blocks in Morton order, phase by phase (D09.3). Every operation must therefore give the same result whichever worker computes a block and in whichever order, as D05.5 already requires. All experiments of D05–D09 confirmed it bit for bit.
- **Worker count:** the default is `os.process_cpu_count()`, overridable (D09.5).
- **Python per phase:** the Python a phase executes must not grow with the number of blocks. That is the condition under which the standard interpreter performs as well as the free-threaded one (E09.1).

**For brief D04 (superseded in part)**

- D04.2's "one call per block" becomes "one call per range of blocks" (D09.2). Kernels remain functions over arrays that allocate nothing, with Python orchestrating; scratch arrays remain per worker.

**For the verification of D02**

- The invariant "1 worker against N workers" now also covers the dynamic assignment: repeated runs claim blocks in different orders and must agree bit for bit.
- Phases declare what they read and write, so tests can check the assembled sequence (no phase reads an array before the phase that writes it).

**For brief D11 (time integration)**

- The integrator provides its stages as phases, for example the stage combinations with their weights, as Athena++ encodes its integrator in task-list stages. The ranged stage kernels of E09.1 are the model.
- The global time step is a reduction (a minimum) over blocks, computed in a phase. It is exact in any order (D05.5).

**For brief D12 (physics module interface)**

- A physics module contributes phases (fluxes, source terms, conversions), each a ranged compiled kernel with declared inputs and outputs. It does not write the step itself.
- Costs that vary per block, such as cooling with substeps, need no special treatment: dynamic assignment absorbs them (E09.2).

**For brief D13 (driver)**

- The driver owns the thread pool and the sequence of steps. It sets the chunk size (4 worked in E09.2) and the number of workers, with the defaults above.

**For the MPI backend (D05.1)**

- Between processes, blocks are distributed by cost-weighted contiguous Morton ranges and rebalanced periodically, as Athena++ does. Within each process, dynamic chunks remain. Because the phases declare their data, an executor that overlaps messages with computation can replace the bulk-synchronous one there without changing the modules (D09.1).
