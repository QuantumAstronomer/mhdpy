## Scope

The brief settles how the work of a step is shared among the cores of a machine ([§5](../overview.md#5-crosscutting-concepts) of the overview): by threads within one process, by processes that exchange their data through MPI, or by both, what each thread or process updates, and whether execution in parallel enters the first pass or follows it as an extension. For the brief on the domain in blocks, it names what the share of each worker demands of the domain. It leaves the number, size and tree of the blocks to that brief, the exchange of ghost cells between blocks to the brief on ghost cells and boundaries, the versions of Python and the dependencies to the brief on the package and its installation, and the time within which the production run must complete to the brief on the problems that verify the first pass. In place of that time, the gain of each means is also stated as the hours that the production run would take on one core and on six. Graphics processors are left out, as the development machine has none that CUDA serves. The brief builds on [B1D1](B01-strata-in-package.md#b1d1-the-subpackages-of-the-strata), which places what the infrastructure provides in `mhdpy.infrastructure`, on [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata), under which a stratum reaches the code above it only through objects handed down, and on [B2D1](B02-kernels.md#b2d1-vectorised-or-compiled) and [B2D2](B02-kernels.md#b2d2-the-compiler-of-the-kernels), which make every kernel a loop compiled by Cython, whose modules leave the GIL disabled on the free-threaded build ([B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md)).

## B3D1 Threads or processes

**Decision.** In the context of a step shared among the cores of one machine, facing threads and processes with MPI that gain alike there, threads in one process, each kernel releasing the GIL (option A), are chosen over processes with MPI (B) and both (C). This achieves readability and usability at no cost in performance, accepting runs bound to one machine and faults of synchronisation that only tests can catch. Decided on 2026-11-10, as recommended.

**Question.** The work of a step can be shared among cores by threads, which share the memory of one process, or by processes, each holding a part of the data and exchanging what its neighbours need through MPI. The means decides what the briefs of stratum 2 must provide and whether the package depends on MPI or on the free-threaded build. The production run is to complete on the development machine, of six cores, and on a small server ([§1.3](../overview.md#13-success-criteria) of the overview). To be read first are [topic 42, §2.4](../topics/42-parallelisation-and-performance.md#24-parallel-execution), [§2.5](../topics/42-parallelisation-and-performance.md#25-threads-and-processes-in-python) and [§4](../topics/42-parallelisation-and-performance.md#4-assessment). Processes of the module `multiprocessing` are left out, as they pass their data by serialisation or shared memory, within one machine alone ([Performance in Python 2.5.2](../references/performance-in-python-synthesis.md#252-processes-against-threads)). **[GK]** So are threads that OpenMP starts within a compiled loop, as `prange` of Cython does, since Apple clang, the compiler of the development machine, refuses OpenMP.

**Option A: threads.** The workers are threads of one process, which share the arrays of the state. In the default build of Python, threads run in parallel only within code that releases the GIL, as NumPy does in its loops and a section of Cython declared `nogil` may, while the Python between such calls runs on one thread at a time ([Performance in Python 2.2.2](../references/performance-in-python-synthesis.md#222-cython), [2.4.2](../references/performance-in-python-synthesis.md#242-making-the-global-interpreter-lock-optional)). The free-threaded build of Python 3.14 removes the lock, at a cost of 13 to 43 per cent in sequential Python on a processor akin to that of the development machine ([2.4.3](../references/performance-in-python-synthesis.md#243-the-free-threaded-build-on-six-cores)). Athena++ shares the blocks of each process among threads ([Athena 3.5](../references/athena-synthesis.md#35-task-lists-and-parallelisation)). **[GK]** For mhdpy, no dependency joins the package. Each kernel must release the GIL, or the run must use the free-threaded build, on which the modules of Cython leave the GIL disabled ([B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md)). As every thread may write into any array, a fault of synchronisation corrupts results silently and only at times, and the work stays within one machine.

**Option B: processes with MPI.** Each worker is a process with its own interpreter and its own part of the domain, started with the others by `mpiexec`. Through MPI, it exchanges the ghost cells of its part with its neighbours and reduces quantities such as the step over all parts. mpi4py passes arrays to MPI at negligible cost ([Performance in Python 2.5.4](../references/performance-in-python-synthesis.md#254-mpi-through-mpi4py)). PetClaw runs the serial kernels of PyClaw unchanged on each process with about 300 lines of framework, but finds parallel Python hard to debug ([2.6.3](../references/performance-in-python-synthesis.md#263-ghost-cells-through-petsc-in-petclaw)). Athena and Athena++ exchange their ghost cells between processes so ([topic 42, §2.4](../topics/42-parallelisation-and-performance.md#24-parallel-execution)). For mhdpy, the GIL plays no part in any build, each process writes only its own part, and the same code serves several machines. Each part needs ghost cells and their exchange, each total over the domain a reduction and each output a gather, a run starts through `mpiexec`, and mpi4py and a library of MPI join the dependencies.

**Option C: both.** Processes of MPI, each with threads that update its parts, as Athena++ runs, since threads help on some machines, which needs a library of MPI that is safe for calls from many threads, a level that some clusters disable ([Athena 3.5](../references/athena-synthesis.md#35-task-lists-and-parallelisation)). For mhdpy, it bears the costs of both others.

**Experiments.** [B3E1](../experiments/B03-parallel-execution/E1-speed-up-of-each-means/README.md) times the step of [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) cut into slabs of rows, one to each worker. On $2048^2$ cells, six threads whose kernel releases the GIL, in either build, and six processes with MPI all run it 2.05 to 2.29 times faster than one, and every run gives the serial result exactly. A kernel that holds the GIL gains nothing in the default build, whose threads on 3.14 also fall behind on $256^2$ cells, to 0.95 against 2.42 in the free-threaded build. mpi4py and MPICH install from wheels on all three versions of Python.

**Recommendation.** Option A, since threads share the step as fast as processes with MPI at the size of the production run, by [B3E1](../experiments/B03-parallel-execution/E1-speed-up-of-each-means/README.md), without a dependency, a launcher or a reduction of every global quantity, on the single machines of §1.3. Every kernel releases the GIL, so that threads gain in both builds of Python, and in the free-threaded build on small parts as well. The option serves readability and usability, the third and fourth priorities of §1, at no cost in performance, the second, and gives up runs across machines. Its faults of synchronisation, a risk to correctness, the first priority, are left to tests that require a run on any number of threads to give the serial result exactly.

**Set aside.** Option B returns once a run needs more than one machine, as the distributed runs that the author foresees for scientific use would, and joins at little cost if the share of each worker gives every part ghost cells of its own. Option C would follow on clusters whose nodes hold many cores, as Athena++ runs.
