## Scope

The brief settles how mhdpy is built, installed and released, so that it installs on macOS and Linux with a single `pip` or `uv` command, as the exception of §1 and [§1.3](../overview.md#13-success-criteria) of the overview demand. It decides the versions of Python and the platforms for which mhdpy provides wheels, the build backend that compiles the kernels, whether the physics is chosen when mhdpy is built or when a run starts, the dependencies and how they are declared, the licence, the version and how a run records it ([§5](../overview.md#5-crosscutting-concepts) of the overview), and how the wheels are built, published and tested on clean systems ([§3.1](../overview.md#31-infrastructure)). The brief makes no release. It leaves the format and record of the runtime parameters to the brief on runtime parameters and units, the tools of testing to the brief on testing and verification, and what outputs and restarts hold beyond the version to the brief on outputs, restarts and analysis. The brief builds on [B1D4](B01-strata-in-package.md#b1d4-the-place-of-the-tests), which places the package in `src/mhdpy/` and its tests in `tests/`, on [B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule), which makes Import Linter a dependency of development, and on [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata), under which the top package imports no stratum when it is loaded. It builds on [B2D1](B02-kernels.md#b2d1-vectorised-or-compiled) and [B2D2](B02-kernels.md#b2d2-the-compiler-of-the-kernels), which make every kernel a module of Python that Cython compiles in its pure mode, with its signatures in a file `.pxd` and its types inferred under `infer_types=True`. They rest the single command on wheels for every platform and version of Python that mhdpy supports, failing which the vectorised route set aside in B2D1 returns. It also builds on [B2D3](B02-kernels.md#b2d3-a-simple-version-beside-the-fast-one) and [B2D4](B02-kernels.md#b2d4-the-benchmark), which keep the references in NumPy in `tests/` and the benchmarks of airspeed velocity in `benchmarks/`, and on [B3D1](B03-parallel-execution.md#b3d1-threads-or-processes), whose threads gain in both the default and the free-threaded build without a dependency of their own.

## B4D1 The versions of Python and the platforms

**Decision.** In the context of a single command that rests on a wheel for every version and platform, facing versions and processors that the development machine cannot all serve, wheels from Python 3.14 in both builds, on macOS and Linux, each on x86-64 and ARM64, every version kept for the three years of SPEC 0 (option C), are chosen over the versions of the development machine (A) and the window of SPEC 0 from 3.13 (B). This achieves the exception of §1 on every Mac and Linux machine, threads that gain in both builds and the language of 3.14, accepting sixteen wheels to a release, tests of those for ARM64 away from the development machine, and users of 3.13 left out a year early. Decided on 2026-11-10, as recommended.

**Question.** [B2D1](B02-kernels.md#b2d1-vectorised-or-compiled) rests the single command on a wheel of mhdpy for every version of Python and every platform that mhdpy supports. The set fixes the wheels of each release, the oldest version whose language the code may use and the versions on which the build backend is tried, and needs a rule for adding and dropping versions. The references ship wheels in pure Python, which serve every version at once ([pyro 3.1](../references/pyro-synthesis.md#31-packaging-installation-and-development), [Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation)). **[GK]** Python 3.13 now receives fixes of security alone, 3.14 and 3.15 fixes of bugs ([status of the versions](#python-versions)). The free-threaded build is supported from 3.14 and experimental before it ([PEP 779](#pep-779)). NumPy 2.5.4 needs Python 3.12 or later and has wheels for macOS and Linux, each on x86-64 and ARM64, for 3.12 to 3.15, 3.14t and 3.15t, but not for 3.13t ([NumPy 2.5.4](#numpy-254)). Cython cannot yet build for the stable ABI of 3.15, by which one wheel would serve both builds of every later version ([PEP 803](#pep-803), [Cython 3.3.0](#cython-changes)). The development machine builds and tests wheels for macOS and, in Docker, Linux on x86-64, but runs Linux on ARM64 only under emulation and macOS on ARM64 not at all, while the hosted runners of GitHub, free for public repositories, offer all four ([runner images](#runner-images)). Windows is left out, as [§1.3](../overview.md#13-success-criteria) of the overview names macOS and Linux alone. To be read first are [topic 35, §2.5](../topics/35-packaging-configuration-and-build.md#25-compiled-kernels-and-their-builds) and [topic 42, §2.5](../topics/42-parallelisation-and-performance.md#25-threads-and-processes-in-python).

**Option A: the versions of the development machine.** Wheels for Python 3.13, 3.14 and 3.14t on macOS and Linux on x86-64, six to a release, each built and tested on the development machine, where the kernels of [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) and [B3E1](../experiments/B03-parallel-execution/E1-speed-up-of-each-means/README.md) ran. **[GK]** For mhdpy, the code keeps to the language of 3.13. On a Mac with an ARM processor, the only kind that Apple has sold since 2023, and on a server with ARM64, an installation falls back to the source and needs a compiler, which breaks the single command.

**Option B: the window of SPEC 0.** Wheels for every version released in the last three years, in both builds where the free-threaded one is supported, on macOS and Linux, each on x86-64 and ARM64: now 3.13, 3.14, 3.14t, 3.15 and 3.15t, twenty to a release. **[GK]** A version is dropped three years after its release by the rule of [SPEC 0](#spec-0), which NumPy, SciPy and Matplotlib endorse and which drops 3.13 in the last quarter of 2027, and a new one joins once NumPy and Cython publish wheels for it. For mhdpy, the single command holds on every Mac and Linux machine and every version that the ecosystem still serves. The code keeps to the language of 3.13, which lacks the deferred annotations of 3.14 ([PEP 649](#pep-649)), so that a name used in an annotation before its definition must be quoted. The wheels for ARM64 are tested only on hosted runners or under emulation, and the development machine must install 3.15 and 3.15t.

**Option C: from 3.14, in both builds.** As option B, but from Python 3.14: now 3.14, 3.14t, 3.15 and 3.15t, sixteen to a release. **[GK]** It is the first version whose free-threaded build is supported. For mhdpy, every version comes in both builds, in each of which threads gain by [B3D1](B03-parallel-execution.md#b3d1-threads-or-processes), and the code may use the language of 3.14. Users of 3.13 must move to a newer version a year before SPEC 0 would drop it. The wheels for ARM64 and for 3.15 are tested as in option B.

**Experiments.** None, since the schedules of CPython and the wheels of NumPy settle what each option serves. Whether wheels of mhdpy build on each version is measured with the build backend.

**Recommendation.** Option C, since its wheels keep the single command on every Mac and Linux machine, which option A gives up, and every version that it serves has a supported free-threaded build, on which threads gained on small grids in [B3E1](../experiments/B03-parallel-execution/E1-speed-up-of-each-means/README.md) where the default build of 3.14 did not. Against option B, it gives up the users of 3.13, whose fixes of bugs have ended, a year before SPEC 0 does, while no release of mhdpy yet exists. The option serves the exception of §1, performance, the second priority, and readability, the third, through the deferred annotations of 3.14, and gives up some usability, the fourth.

**Set aside.** Option B would return if a user needed Python 3.13 before SPEC 0 drops it, late in 2027. Option A would return if wheels for ARM64 could be neither built nor tested on hosted runners or under emulation.

## B4D2 The build backend

**Decision.** In the context of kernels in the pure mode of Cython, built into wheels and an editable installation, facing backends that differ in their tools and in how a change to a kernel reaches the tests, setuptools, with the kernels in `setup.py` and their declarations named as package data (option A), is chosen over meson-python (B) and scikit-build-core (C). This achieves readability, with 11 lines of configuration and Cython alone beside it, and keeps the check of [B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule), accepting a new editable installation after each change to a kernel, which compiles every kernel again. Decided on 2026-11-10, against the recommendation of option C, since scikit-build-core brings with CMake, ninja and cython-cmake far more machinery and options than mhdpy needs.

**Question.** Every kernel is a module of Python that Cython compiles in its pure mode, with its signatures in a file `.pxd` beside it ([B2D2](B02-kernels.md#b2d2-the-compiler-of-the-kernels)), and the build backend turns these modules into extension modules, in the wheels of [B4D1](#b4d1-the-versions-of-python-and-the-platforms) and in the editable installation in which the code is developed. It must be chosen before the first module of stratum 1, as it fixes the files that configure the build, where each new kernel is entered, and how a change to a kernel reaches the tests, which run after every function in the way of working of §2.6. The references compile no module of Python: pyro and Ulula build their packages, pure Python, with setuptools, and Athena++ compiles by a makefile that its script of configuration writes ([topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages), [§2.3](../topics/35-packaging-configuration-and-build.md#23-configuration-at-build-time)). **[GK]** Cython's documentation covers four backends and recommends to new projects those other than setuptools, noting that much of the scientific ecosystem builds with Meson first ([Cython, compilation](#cython-compilation)). Hatchling, the fourth, needs a plugin for Cython and is left out.

**Option A: setuptools.** The backend of pyro and Ulula ([topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages)). **[GK]** Astropy builds its compiled modules with it. A file `setup.py` beside `pyproject.toml` hands the kernels to `cythonize`, as [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) and the experiments after it did. For mhdpy, every kernel is entered in `setup.py`, and the build needs setuptools and Cython alone. An editable installation, however, holds a compiled module as it was when installed ([setuptools, development mode](#setuptools-editable)), so that a change to a kernel reaches the tests only after a new installation. Cython writes its C beside the sources unless told otherwise.

**Option B: meson-python.** **[GK]** A backend that builds with Meson and ninja, in a folder of its own, from files `meson.build` that name what is compiled and installed, as NumPy, SciPy, scikit-learn, pandas and scikit-image build. Its editable installation rebuilds the compiled modules when the package is first imported in a process, and ninja rebuilds only what changed ([meson-python, editable installations](#mesonpy-editable)). For mhdpy, a change to a kernel reaches the next run of the tests without a step, provided that meson-python, Meson, ninja and Cython stay installed beside the package, as the editable installation is made without build isolation. Meson takes as Cython only files with the suffix `.pyx` ([Meson, Cython](#meson-cython)), so that each module in the pure mode needs a step of its own in `meson.build` that runs Cython on it, and modules of Python are installed only as `meson.build` names them.

**Option C: scikit-build-core.** **[GK]** A backend that builds with CMake from a file `CMakeLists.txt`, through the package cython-cmake for Cython, and installs the folder of the package without a list of its modules. Its editable installation redirects imports to the sources and to a folder of the build, and rebuilds on import only in a mode that it calls very experimental, a rebuild being started by hand otherwise ([scikit-build-core, editable installations](#skbuild-editable)). For mhdpy, CMake joins the tools with a language of configuration of its own, and every kernel is entered in `CMakeLists.txt`. A change to a kernel reaches the tests through the experimental rebuild or a step by hand, and the build tools stay installed beside the package, as for option B.

**Experiments.** [B4E1](../experiments/B04-packaging/E1-builds-of-each-backend/README.md) builds the kernel of [B2E2](../experiments/B02-kernels/E2-declarations-for-cython/README.md) and a copy with each backend on Python 3.14, 3.14t, 3.15 and 3.15t. Every wheel builds and gives the result of plain NumPy exactly, with the GIL disabled in the free-threaded builds, at $8.9$ to $9.8 \times 10^6$ cell updates per second. A change to a module or to its file `.pxd` reaches the next process without a step under meson-python and scikit-build-core, in 5 to 7 s, compiling that kernel alone, but needs a new installation of 9 to 10 s under setuptools, which compiles both kernels again. Import Linter fails under the editable installation of meson-python, whose loader hides the folders of the package. The configuration takes 11, 18 and 17 lines for options A, B and C.

**Recommendation.** Option C, since a change to a kernel then reaches the next run of the tests without a step and compiles that kernel alone, as §2.6 needs after every function, which setuptools does only by a new installation that compiles every kernel again, while the check of [B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule) keeps working, unlike under meson-python ([B4E1](../experiments/B04-packaging/E1-builds-of-each-backend/README.md)). The option serves correctness, the first priority of §1, as the rule is checked on the code as developed, and leaves performance, the second, unchanged. It gives up some readability, the third, as CMake joins TOML in the configuration, and leans on a rebuild that its makers call experimental, which a new installation replaces should it fail.

**Set aside.** Option C would return if the new installation after each change grew too slow as the kernels multiply, as scikit-build-core compiles the changed kernel alone, without a step. Option B would return if Import Linter could read a package behind the editable loader of meson-python, whose rebuild on import is stable.

## B4D3 When the physics is chosen

**Decision.** In the context of wheels that serve every run, facing sizes given at run time that cost a kernel a third to a half of its rate, versions of each kernel compiled within the wheel for the sizes on which its loops over cells depend, chosen as a run starts, with values such as $\gamma$ given to each call (option C), are chosen over every choice at run time (A) and at build time (B). This achieves performance within the single command of §1, accepting several versions of a kernel from one source, tests for each, and a new installation that compiles them all. Decided on 2026-11-10, as recommended, after [B4E2](../experiments/B04-packaging/E2-cost-of-choices-at-run-time/README.md), which the author asked for.

**Question.** The kernels reach their users as the wheels of [B4D1](#b4d1-the-versions-of-python-and-the-platforms), compiled once for every run on a version and platform. Whether a choice of physics or algorithm, such as the Riemann solver, the equation of state, the number of passive scalars or MHD once it enters, is fixed when mhdpy is built or when a run starts must be settled before the first kernel. It fixes whether a kernel takes such choices as arguments or as constants, and how the strata above select a component. To be read first are [topic 35, §2.3](../topics/35-packaging-configuration-and-build.md#23-configuration-at-build-time) and [§4](../topics/35-packaging-configuration-and-build.md#4-assessment), [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop), [topic 38, §2](../topics/38-problem-setups-and-user-functions.md#2-designs), and [Performance in Python 3.1](../references/performance-in-python-synthesis.md#31-agate-interfaces-and-implementations) and [3.9](../references/performance-in-python-synthesis.md#39-pace-components-compiled-at-initialisation).

**Option A: at run time.** Every choice is made when a run starts, from its parameters and its problem. Each kernel is compiled once for all runs and takes sizes, such as the number of scalars, as arguments, and the strata above hand the chosen components down, as [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata) asks. A choice then selects which compiled kernel a stage calls on a block, outside its loops over cells. pyro finds its solver and problem by name, Ulula and AGATE hand objects to the simulation, all when a run starts ([topic 38, §2](../topics/38-problem-setups-and-user-functions.md#2-designs), [Performance in Python 3.1](../references/performance-in-python-synthesis.md#31-agate-interfaces-and-implementations)). **[GK]** For mhdpy, one wheel per version and platform serves every problem, so that the single command holds for all of them, and a new module joins without a new build, as [§1.3](../overview.md#13-success-criteria) of the overview asks. The compiler cannot specialise a kernel to a choice that it does not know.

**Option B: at build time.** A step of configuration writes the choices as constants into a file that the kernels include, and the kernels are compiled for that configuration alone, the step refusing combinations that do not fit. Athena++ builds so, and Pace passes the constants of its configuration to the compiler of its stencils when a run starts ([topic 35, §2.3](../topics/35-packaging-configuration-and-build.md#23-configuration-at-build-time), [Performance in Python 3.9](../references/performance-in-python-synthesis.md#39-pace-components-compiled-at-initialisation)). **[GK]** For mhdpy, the compiler specialises every loop and branch to the configuration. A wheel, however, holds one configuration, so that every other needs a build from the sources with a compiler, which breaks the single command for it, and each combination of choices, such as MHD, the scalars and the equation of state, is a build of its own. A new module needs a new configuration and a new build.

**Option C: both.** As option A, but with chosen kernels compiled in several versions within the wheel, each specialised to one choice, such as one number of scalars up to a bound, generated from one source, each with a header of its constants, as in [B4E2](../experiments/B04-packaging/E2-cost-of-choices-at-run-time/README.md), and the run picks the version that fits. **[GK]** For mhdpy, the wheel serves every problem and the configurations most used run specialised, at the cost of a generator of versions, a larger wheel, and tests that must cover every version.

**Experiments.** [B4E2](../experiments/B04-packaging/E2-cost-of-choices-at-run-time/README.md) times on one core the stage of [B2E2](../experiments/B02-kernels/E2-declarations-for-cython/README.md) with passive scalars, its ratio of specific heats and number of scalars fixed as constants of a header when it is compiled, or given as arguments as the run starts. Fixed, the stage runs 1.4 to 2.1 times as fast: on $2048^2$ cells, at $9.68$ against $5.98 \times 10^6$ cell updates per second without a scalar, and at $7.99$ against $5.64 \times 10^6$ with one, even though the loops over scalars of the stage given run no iteration without one. The same stage without loops over scalars, its ratio of specific heats given as an argument, ran at $9.6 \times 10^6$ in [B4E1](../experiments/B04-packaging/E1-builds-of-each-backend/README.md). Every variant gives the same result exactly.

**Recommendation.** Option C, since sizes given at run time cost the kernel a third to a half of its rate by [B4E2](../experiments/B04-packaging/E2-cost-of-choices-at-run-time/README.md), which versions compiled for the sizes in use recover within the wheel, while option B would break the single command for every configuration but one. As the stage of [B4E1](../experiments/B04-packaging/E1-builds-of-each-backend/README.md) ran as fast with its ratio of specific heats as an argument, the versions need fix only the sizes on which a loop over cells depends, such as the number of scalars, while values such as $\gamma$, and the solver chosen among compiled kernels, stay arguments of a call. The option serves performance, the second priority of §1, and keeps the exception. It gives up some readability, the third, as the build makes several versions of a kernel from one source, each of which the tests must cover, and a new installation under setuptools compiles them all.

**Set aside.** Option A would return if kernels could keep every loop whose length the run gives outside their loops over cells, as one call per scalar would, since one version would then serve every run.

## B4D4 The dependencies

**Decision.** In the context of a package that users install with one command and that is developed through its tests, facing dependencies that weigh on the installation and versions that drift between sessions, NumPy alone at run time, from 2.3.2 with the floor raised as SPEC 0 drops releases and without upper bounds, each further package added by the brief that needs it, with the tools of development in groups of dependencies and their versions locked in a committed file `uv.lock` (option A), is chosen over extras without a lock (B) and the scientific stack at once (C). This achieves correctness, as the tests run on the same versions everywhere, and a light installation, accepting a lock to keep and a development that needs uv or pip 25.1. Decided on 2026-11-10, as recommended.

**Question.** The file `pyproject.toml`, which the first module of stratum 1 needs, names what mhdpy depends on: NumPy, whose arrays every kernel takes, at run time; setuptools and Cython for its build ([B4D2](#b4d2-the-build-backend)); and for its development pytest, Import Linter ([B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule)), airspeed velocity ([B2D4](B02-kernels.md#b2d4-the-benchmark)) and pyright (§3.2). It must be settled which packages the installation of a user pulls in, with which bounds, where the tools of development are named, and whether a file of locked versions fixes the environment in which the tests run. To be read first are [topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages), [§2.4](../topics/35-packaging-configuration-and-build.md#24-dependencies-licences-and-development) and [§4](../topics/35-packaging-configuration-and-build.md#4-assessment). **[GK]** NumPy 2.3.2 is the first release with wheels for Python 3.14 and 3.14t on the four platforms of [B4D1](#b4d1-the-versions-of-python-and-the-platforms), and 2.5.2 the first for 3.15 and 3.15t ([NumPy releases](#numpy-releases)). SPEC 0 now asks for NumPy 2.3 or later ([SPEC 0](#spec-0)).

**Option A: few dependencies, groups and a lock.** The installation pulls in NumPy alone, from 2.3.2, the floor rising as SPEC 0 drops releases, without upper bounds, and each later brief adds the package that it needs, as that on outputs may add h5py. Athena++ depends on as little as possible ([topic 35, §2.4](../topics/35-packaging-configuration-and-build.md#24-dependencies-licences-and-development)). **[GK]** The tools of development form groups of dependencies in `pyproject.toml` ([PEP 735](#pep-735)), which uv installs with the project and pip from release 25.1, and which the published metadata leaves out. A file `uv.lock`, committed, fixes the version of every package of the environment of development, which `uv lock --upgrade` raises when asked. For mhdpy, a user installs NumPy and mhdpy alone, the tests run on the same versions on every machine and in every session, and a change of version shows as a change of the lock. The lock must be kept, and the experiments keep their own environments by [PEP 723](#pep-723).

**Option B: few dependencies, extras without a lock.** As option A for the installation, but the tools of development are named as optional extras of the package, installed by `pip install -e ".[dev]"`, or in a file of requirements, as pyro names its own ([pyro 3.1](../references/pyro-synthesis.md#31-packaging-installation-and-development)), and their versions float. **[GK]** For mhdpy, any release of pip installs the environment without uv, and no lock needs keeping. The tests run on whatever versions an installation finds that day, so that a change of a dependency can alter a result unseen, and the extras appear in the published metadata as if users needed them.

**Option C: the scientific stack at once.** The installation pulls in NumPy, SciPy, Matplotlib and h5py from the start, as pyro and Ulula do, with the tools of development as in option A ([topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages)). **[GK]** For mhdpy, a user has plots and files of HDF5 at hand from the first release. The installation grows by the dependencies of those packages, and their choice comes before the briefs on outputs and analysis that are to make it, a provision that §2.3 builds early only when it costs little. Ulula imports a package that it does not declare and receives only through Matplotlib ([topic 35, §4](../topics/35-packaging-configuration-and-build.md#4-assessment)), which a stack declared at once invites.

**Experiments.** None, since the options differ in what is declared and where, which the facts of the tools settle.

**Recommendation.** Option A, since a lock keeps the tests on the same versions from one session to the next, so that a changed result points to the code rather than to a dependency, while the installation stays as light as the exception of §1 wants. Against option C, it leaves each further dependency to the brief that needs it. The option serves correctness, the first priority of §1, through the reproducible environment of the tests, and usability, the fourth, through a light installation, and gives up the upkeep of a lock and an installation of development that needs uv or pip 25.1.

**Set aside.** Option B would return if contributors without uv or a recent pip came to matter, as extras install with any release of pip.

## B4D5 The licence

**Decision.** In the context of a public repository without a licence, facing a code that others are to pick up and references under licences of their own, the BSD licence of three clauses for the code and the documents of the repository (option A) is chosen over MIT (B) and the GPL from version 3 (C). This achieves usability and extensibility, as others may build mhdpy into any code and code of pyro and Ulula may be taken with their notices, accepting that what others derive may stay closed and that no code of the modules of Athena++ under the GPL may be taken. Decided on 2026-11-10, as recommended.

**Question.** **[GK]** The repository of mhdpy is public but bears no licence, so that copyright reserves every use to its author: others may read the code, but not use, change or share it. The licence must be chosen before code is written that others might build on, and before the first wheel, whose metadata names it by an expression of SPDX in `pyproject.toml`, which setuptools reads from release 77 ([PEP 639](#pep-639)). It also bounds what mhdpy may take from the references, each of which keeps its own licence (§4.1). The documents of `design/` would share the licence of the code, so that one licence covers the repository. To be read first are [topic 35, §2.4](../topics/35-packaging-configuration-and-build.md#24-dependencies-licences-and-development) and [§4](../topics/35-packaging-configuration-and-build.md#4-assessment), with [pyro 1.1](../references/pyro-synthesis.md#11-origin-version-and-licence) and [Ulula 1.1](../references/ulula-synthesis.md#11-origin-version-and-licence). The Apache licence, whose grant of patents matters little to a code of simulation, is left out.

**Option A: BSD, three clauses.** The licence of Athena++, chosen over version 3 of the GNU General Public License as it eases the redistribution of derived works, for instance within the closed frameworks of national laboratories, and of pyro ([topic 35, §2.4](../topics/35-packaging-configuration-and-build.md#24-dependencies-licences-and-development), [pyro 1.1](../references/pyro-synthesis.md#11-origin-version-and-licence)). **[GK]** Anyone may use, change and redistribute the code, in open or closed form, keeping its notice of copyright, without naming its authors to endorse what derives from it. For mhdpy, others may build it into any code, and code of pyro and Ulula may be taken with their notices, but not code of the modules of Athena++ that bear headers of the GPL ([topic 35, §4](../topics/35-packaging-configuration-and-build.md#4-assessment)).

**Option B: MIT.** The licence of Ulula ([Ulula 1.1](../references/ulula-synthesis.md#11-origin-version-and-licence)). **[GK]** As permissive as option A in a shorter text, without its clause on endorsement. For mhdpy, the use that others may make of it, and what it may take from the references, are those of option A.

**Option C: GPL, version 3 or later.** **[GK]** A licence of copyleft: whoever distributes a work derived from the code must release its source under the same licence. For mhdpy, what others build on it stays open, and code of the modules of Athena++ under the GPL could be taken. No closed framework may embed mhdpy, the reason for which Athena++ chose BSD, and code of mhdpy could not flow back into pyro or Ulula without binding them to the GPL.

**Experiments.** None, since the options differ in the rights that they grant, which their texts settle.

**Recommendation.** Option A, since it lets others build on mhdpy freely, as Athena++ chose its licence to allow, and lets code of pyro and Ulula be taken with their notices, while its clause on endorsement keeps the names of its authors from being used for derived work, which option B leaves out. The option serves usability and extensibility, the fourth priority of §1, and the aim of a code that others can pick up ([§1.1](../overview.md#11-goals) of the overview). It gives up the guarantee of option C that what others derive stays open.

**Set aside.** Option C would return if mhdpy came to need code of the modules of Athena++ under the GPL, which only a licence of copyleft could take in.

## B4D6 The version and its record

**Decision.** In the context of runs that are to name the code that produced them, facing an editable installation whose metadata keeps the version of its last installation, a version derived from the tags of git by setuptools-scm, recorded by every run together with the commit and the state of the tree that a run from a checkout reads from git (option C), is chosen over a version raised by hand (A) and the version of the installation alone (B). This achieves correctness, as every result can be traced to its code, accepting a plugin of the build and a function of stratum 1 that reads git. Decided on 2026-11-10, as recommended.

**Question.** Every wheel names a version in its metadata, and every run is to record the version of mhdpy, so that the run can be reproduced ([§5](../overview.md#5-crosscutting-concepts) of the overview). The version must be set in one place, by hand or from the tags of git, and a run made during development must still name the code that produced it. The form of the record and where outputs keep it are left to the brief on outputs, restarts and analysis, and the numbering of releases to the sub-decision on the wheels and their publication. To be read first are [topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages) and [§4](../topics/35-packaging-configuration-and-build.md#4-assessment), and [topic 39, §2.2](../topics/39-output-restarts-and-analysis.md#22-snapshots-in-hdf5), where Ulula writes its version into each file and refuses files older than 1.0.0. **[GK]** An editable installation keeps the version of its last installation in its metadata.

**Option A: by hand, with git at run time.** The version is written in `pyproject.toml` and raised by hand before each release, as Ulula keeps its version in a file of its package ([Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation)). A run records it from the metadata of its installation and, where mhdpy runs from a checkout, also the commit and whether the tree differs from it, read from git as the experiments record theirs ([rules of the experiments, §3](../templates/experiment-rules.md#3-the-code)). **[GK]** For mhdpy, the build needs no plugin, and a run names its code wherever it runs. A release whose version was not raised repeats that of the last, and the tag of git must be kept in step with the version by hand.

**Option B: from the tags, as installed.** A plugin of setuptools, setuptools-scm, derives the version from the last tag of git when the package is built, as for pyro ([topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages)). **[GK]** A build at a tag gets the plain version, one fourteen commits later a version such as `0.2.dev14+g5f3e2a1` that names its commit, and one from a tree with changes a mark of the date. A run records the version of its installation. For mhdpy, releases and tags cannot diverge, and every wheel names its commit. A run made after later commits to modules of Python, which need no new installation under [B4D2](#b4d2-the-build-backend), records the commit of the last installation rather than that of its code.

**Option C: from the tags, with git at run time.** As option B, and a run from a checkout also reads the commit and the state of the tree from git, as in option A. **[GK]** For mhdpy, releases follow the tags, and every run names the code that produced it, from a wheel by its version and from a checkout by its commit. setuptools-scm joins the requirements of the build, and a short function of stratum 1 reads git.

**Experiments.** None, since the options differ in where the version is set and read, which the tools document.

**Recommendation.** Option C, since every run then names the exact code that produced it, during development as well as from a wheel, which option B fails to do after a commit without a new installation, while releases follow their tags without the raise by hand that option A needs. The top package can expose the version from the metadata without importing a stratum, as [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata) asks. The option serves correctness, the first priority of §1, as a result can be traced to its code, and gives up a plugin of the build and a function that reads git.

**Set aside.** Option A would return if setuptools-scm ceased to be maintained or to serve the backend of [B4D2](#b4d2-the-build-backend), as a version raised by hand needs no plugin.

## B4D7 The wheels and their publication

**Decision.** In the context of sixteen wheels a release and an installation by one command that stratum 1 must show on clean systems, facing platforms that the development machine cannot all run, wheels built and tested by cibuildwheel on the hosted runners of GitHub for every push and tag, each on its own platform, published by trusted publishing to TestPyPI alone until the first pass is built and afterwards, once approved, to the Package Index, with the installation by one command tried from TestPyPI on clean systems (option B), are chosen over building on the development machine (A). This achieves correctness and the exception of §1, as every wheel is tested where it runs before it is published, accepting a workflow on GitHub, which joins the repository with the approval of the author, and releases that rest on its free runners. Decided on 2026-11-10, as recommended.

**Question.** [B4D1](#b4d1-the-versions-of-python-and-the-platforms) asks for sixteen wheels a release, on macOS and Linux for x86-64 and ARM64, each built and tested, and [§3.1](../overview.md#31-infrastructure) of the overview closes stratum 1 with the installation by one command on clean macOS and Linux, the latter in Docker. It must be settled where the wheels are built and tested, how they reach the Package Index, and when releases begin. No problem runs before the driver of stratum 5 exists ([§3](../overview.md#3-layers) of the overview), so that a release can serve users only once the first pass is built. The references test their builds rather than their packages, Athena++ by continuous integration over several compilers and architectures, and none tests the installation of its package on a clean system ([topic 35, §3](../topics/35-packaging-configuration-and-build.md#3-tests)). **[GK]** The name mhdpy is free, on 2026-11-10, on the Package Index and on TestPyPI, its index for trials. cibuildwheel 4.3.5 builds the wheels of CPython 3.14 and 3.15 in both builds by default, those of Linux in containers of `manylinux_2_28`, and also wheels for Alpine ([cibuildwheel](#cibuildwheel)), which B4D1 did not weigh and which are left out. Releases are numbered by the tags of [B4D6](#b4d6-the-version-and-its-record), 0.y.z while the interface may still change.

**Option A: on the development machine.** cibuildwheel runs on the development machine. It builds the wheels for macOS on x86-64 natively and on ARM64 by compiling across, and those for Linux in containers of Docker, emulated for ARM64. The wheels are tested where the machine can run them, installed by one command in a container without a compiler for Linux, and uploaded to the Package Index with a token. **[GK]** For mhdpy, no service beyond the Package Index is needed. The wheels for macOS on ARM64 go out untested, those for Linux on ARM64 build and test slowly under emulation, every release waits on the machine, and a token for the Package Index lies on it.

**Option B: on hosted runners.** **[GK]** A workflow of GitHub Actions runs cibuildwheel on every push and every tag, and each wheel is built and tested by the tests of mhdpy on a runner of its own platform, all four natively, as NumPy and SciPy build theirs ([NumPy and SciPy](#numpy-scipy-wheels)). The job of a tag publishes the wheels and the source distribution by trusted publishing, which needs no token ([trusted publishing](#trusted-publishing)): until the first pass is built to TestPyPI alone, and afterwards first to TestPyPI and then, once approved, to the Package Index. From TestPyPI, each platform installs mhdpy by one command into a fresh environment that refuses builds from source, and Linux also into a container without a compiler. For mhdpy, every wheel is tested where it runs, ARM64 included, before it is published, and a release is a tag. The workflow joins the repository with the approval of the author, and the wheels rest on the free runners of public repositories, as B4D1 notes.

**Experiments.** None, since the options differ in where the wheels are built and tested, which the platforms of the development machine and of the runners settle.

**Recommendation.** Option B, since every wheel is then tested on the platform where it runs before it is published, the ARM64 wheels that the development machine cannot run included, and the installation by one command that §3.1 asks for is tried on clean systems from TestPyPI, while no token lies on the machine. The option serves correctness, the first priority of §1, and the exception, and gives up the independence of a release from GitHub, which option A keeps.

**Set aside.** Option A would return if the hosted runners ceased to be free for public repositories or to offer a platform of B4D1, as the development machine builds every wheel, if it cannot test every one.
