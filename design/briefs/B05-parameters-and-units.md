**Supersedes.** None.

## Scope

The brief settles how the parameters of a run reach the modules that use them, and in which units the parameters and the state are measured ([§5](../overview.md#5-crosscutting-concepts) of the overview). It decides how a module declares its parameters with their defaults and what is checked before a run starts, in which form a user gives their values, what a run records of them and of its seeds so that it can be repeated, the system of units, and the physical constants that conduction and cooling need. Its choices must serve the tests that close stratum 1 by [§3.1](../overview.md#31-infrastructure) of the overview: parameters with defaults, overrides and unknown names, and units against their constants. It leaves the form of a problem, and where a problem places its declaration, to the brief on problem setups and user functions. The form in which outputs and restarts keep the record, and which parameters a restart may change, are left to the brief on outputs, restarts and analysis. The launching of a run, from the command line or from Python, is left to the brief on the driver, and the parameters of each module, such as the mean mass of a particle that the temperature needs, to the briefs of its stratum. The brief builds on [B1D1](B01-strata-in-package.md#b1d1-the-subpackages-of-the-strata), which places what it provides in `mhdpy.infrastructure`, and on [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata), under which the strata above reach the infrastructure by imports downwards while it reaches them only through objects handed down, and the top package imports no stratum when it is loaded. [B1D4](B01-strata-in-package.md#b1d4-the-place-of-the-tests) places its tests in `tests/infrastructure/` under the same rule. It builds on [B4D3](B04-packaging.md#b4d3-when-the-physics-is-chosen), which compiles each kernel in versions fixed to the sizes on which its loops over cells depend, among which a run chooses as it starts, and gives values such as $\gamma$ to each call, so that the parameters must fix those sizes before a run starts and a size without a compiled version must fail at once. It also builds on [B3D1](B03-parallel-execution.md#b3d1-threads-or-processes), which shares each step among the threads of one process, whose number is a parameter of a run, on [B4D1](B04-packaging.md#b4d1-the-versions-of-python-and-the-platforms), under which the code may use the language of Python 3.14, on [B4D4](B04-packaging.md#b4d4-the-dependencies), under which NumPy is the only dependency at run time and any further package must be justified by the brief that needs it, and on [B4D6](B04-packaging.md#b4d6-the-version-and-its-record), beside whose record of the version a run records its parameters.

## B5D1 The declaration of parameters

**Decision.** In the context of parameters that every module of every stratum reads, facing faults that must show before any block is built, one frozen dataclass per module, whose fields give each parameter its name, type, default and allowed values, handed by the driver to the reader (option C), is chosen over dictionaries of defaults (A) and defaults stated where values are read (B). This achieves correctness and readability, as faults show before a run starts and strict checking follows every read, accepting a class in every module and a reader that checks types itself. Decided on 2026-11-11, as recommended.

**Question.** Every module declares the parameters that it reads, with their defaults ([§5](../overview.md#5-crosscutting-concepts) of the overview), in a form to be settled before the first module of stratum 1. The form fixes which faults are caught before a run starts: an unknown or misspelt name, a value of the wrong type, and a size for which no compiled version of a kernel exists, which must fail at once under [B4D3](B04-packaging.md#b4d3-when-the-physics-is-chosen). It also fixes whether the strict checking of types of §3.2 follows each read, and how the declarations reach the reader in the infrastructure, which may not import the modules above it ([B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata)). To be read first are [topic 37, §2.5](../topics/37-driver-and-control-of-time-step.md#25-runtime-parameters-and-units) and [§4](../topics/37-driver-and-control-of-time-step.md#4-assessment), [topic 38, §4](../topics/38-problem-setups-and-user-functions.md#4-assessment), [pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters) and [Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop). **[GK]** Libraries that check typed settings, such as pydantic, are left out under [B4D4](B04-packaging.md#b4d4-the-dependencies), and so is a registry filled as modules are imported, whose contents would depend on what a process happened to import.

**Option A: dictionaries of defaults.** Each module names its parameters with their defaults in a dictionary, from which the reader infers their types, and reads a value by its name. pyro keeps such defaults in files and, for each problem, in a dictionary, lets an inputs file change only declared names, warning of others, and reports unread parameters at the end ([pyro 3.3](../references/pyro-synthesis.md#33-driver-simulations-and-runtime-parameters)). **[GK]** For mhdpy, the driver hands the dictionaries of a run to the reader, so that an unknown name can be refused before the run starts. A value read by its name has no type that strict checking can follow, unless a typed dictionary states every name a second time with its type, and a name misspelt in the code fails only when its line runs. Allowed values, such as the sizes of B4D3, need checks of their own.

**Option B: defaults where values are read.** A module states the default of each parameter where it reads it, and a default joins the parameters of the run where the user gave no value. Athena++ reads so through `GetOrAddReal` and its siblings, which record every value in use for the head of its restart files, and lets its command line change only parameters that its input file holds ([Athena 3.1](../references/athena-synthesis.md#31-configuration-build-and-the-main-loop)). **[GK]** For mhdpy, no declaration stands apart, and a getter for each type returns a value that strict checking follows. An unknown name in the inputs can be found only after every module has read its values, so that all modules must be built before the first block. A name misspelt in the code takes its default unseen, and a parameter read in two places may receive two defaults.

**Option C: typed declarations handed to the reader.** Each module declares its parameters as one frozen dataclass of the standard library, whose fields give each parameter its name, type and default and, where it is limited, its allowed values, as for the sizes of B4D3. The driver hands the classes of a run to the reader, which checks the values given against them, fills the defaults and returns for each module an instance that cannot be changed, read by attribute. Ulula comes closest, as its scheme is a class whose constructor takes the parameters of the time step with their defaults and refuses values out of range ([Ulula 3.2](../references/ulula-synthesis.md#32-the-simulation-object-and-its-data)). **[GK]** A dataclass ([PEP 557](#pep-557)) takes the type of each field from its annotation, its constructor refuses an unknown name, and the metadata of a field can carry allowed values or a unit. For mhdpy, an unknown name, a value of the wrong type and a size without a compiled version all fail before any block is built, and strict checking follows every read, a misspelt attribute included. The parameters of a module stand in one place, each default once. Each module adds a class, and the reader must check the types of the values itself, as dataclasses do not.

**Experiments.** None, since the references and the documentation of Python settle what each option declares and when it can be checked.

**Recommendation.** Option C, since every fault that the question names then shows before any block is built, as [B4D3](B04-packaging.md#b4d3-when-the-physics-is-chosen) demands and [§3.1](../overview.md#31-infrastructure) of the overview tests, while strict checking follows every read, which option A allows only by stating each name twice, and option B only with names unknown until every module is built. The parameters of a module stand in one place, each default once. The option serves correctness, the first priority of §1, and readability, the third, and gives up none, performance included, at the price of a class in every module and a reader that checks types itself.

**Set aside.** Option B would return if the parameters of a module came to depend on values read while a run is built, such as a table that names parameters of its own, since reads at the point of use follow them without a declaration made in advance.
