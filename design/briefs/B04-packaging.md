# B4 Packaging

**Status.** Open.

**Topics.** [Topic 35](../topics/35-packaging-configuration-and-build.md), with [topic 42, §2.5](../topics/42-parallelisation-and-performance.md#25-threads-and-processes-in-python) for the free-threaded build whose wheels the brief weighs, and [topic 39, §2.2](../topics/39-output-restarts-and-analysis.md#22-snapshots-in-hdf5) for the version that a run records.

**Supersedes.** None.

## Scope

The brief settles how mhdpy is built, installed and released, so that it installs on macOS and Linux with a single `pip` or `uv` command, as the exception of §1 and [§1.3](../overview.md#13-success-criteria) of the overview demand. It decides the versions of Python and the platforms for which mhdpy provides wheels, the build backend that compiles the kernels, whether the physics is chosen when mhdpy is built or when a run starts, the dependencies and how they are declared, the licence, the version and how a run records it ([§5](../overview.md#5-crosscutting-concepts) of the overview), and how the wheels are built, published and tested on clean systems ([§3.1](../overview.md#31-infrastructure)). The brief makes no release. It leaves the format and record of the runtime parameters to the brief on runtime parameters and units, the tools of testing to the brief on testing and verification, and what outputs and restarts hold beyond the version to the brief on outputs, restarts and analysis. The brief builds on [B1D4](B01-strata-in-package.md#b1d4-the-place-of-the-tests), which places the package in `src/mhdpy/` and its tests in `tests/`, on [B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule), which makes Import Linter a dependency of development, and on [B1D2](B01-strata-in-package.md#b1d2-the-rule-between-the-strata), under which the top package imports no stratum when it is loaded. It builds on [B2D1](B02-kernels.md#b2d1-vectorised-or-compiled) and [B2D2](B02-kernels.md#b2d2-the-compiler-of-the-kernels), which make every kernel a module of Python that Cython compiles in its pure mode, with its signatures in a file `.pxd` and its types inferred under `infer_types=True`. They rest the single command on wheels for every platform and version of Python that mhdpy supports, failing which the vectorised route set aside in B2D1 returns. It also builds on [B2D3](B02-kernels.md#b2d3-a-simple-version-beside-the-fast-one) and [B2D4](B02-kernels.md#b2d4-the-benchmark), which keep the references in NumPy in `tests/` and the benchmarks of airspeed velocity in `benchmarks/`, and on [B3D1](B03-parallel-execution.md#b3d1-threads-or-processes), whose threads gain in both the default and the free-threaded build without a dependency of their own.

## B4D1 The versions of Python and the platforms

**Decision.** In the context of a single command that rests on a wheel for every version and platform, facing versions and processors that the development machine cannot all serve, wheels from Python 3.14 in both builds, on macOS and Linux, each on x86-64 and ARM64, every version kept for the three years of SPEC 0 (option C), are chosen over the versions of the development machine (A) and the window of SPEC 0 from 3.13 (B). This achieves the exception of §1 on every Mac and Linux machine, threads that gain in both builds and the language of 3.14, accepting sixteen wheels to a release, tests of those for ARM64 away from the development machine, and users of 3.13 left out a year early. Decided on 2026-11-10, as recommended.

**Question.** [B2D1](B02-kernels.md#b2d1-vectorised-or-compiled) rests the single command on a wheel of mhdpy for every version of Python and every platform that mhdpy supports. The set fixes the wheels of each release, the oldest version whose language the code may use and the versions on which the build backend is tried, and needs a rule for adding and dropping versions. The references ship wheels in pure Python, which serve every version at once ([pyro 3.1](../references/pyro-synthesis.md#31-packaging-installation-and-development), [Ulula 3.1](../references/ulula-synthesis.md#31-packaging-and-installation)). **[GK]** Python 3.13 now receives fixes of security alone, 3.14 and 3.15 fixes of bugs ([status of the versions](#python-versions)). The free-threaded build is supported from 3.14 and experimental before it ([PEP 779](#pep-779)). NumPy 2.5.4 needs Python 3.12 or later and has wheels for macOS and Linux, each on x86-64 and ARM64, for 3.12 to 3.15, 3.14t and 3.15t, but not for 3.13t ([NumPy 2.5.4](#numpy-254)). Cython cannot yet build for the stable ABI of 3.15, by which one wheel would serve both builds of every later version ([PEP 803](#pep-803), [Cython 3.3.0](#cython-changes)). The development machine builds and tests wheels for macOS and, in Docker, Linux on x86-64, but runs Linux on ARM64 only under emulation and macOS on ARM64 not at all, while the hosted runners of GitHub, free for public repositories, offer all four ([runner images](#runner-images)). Windows is left out, as [§1.3](../overview.md#13-success-criteria) of the overview names macOS and Linux alone. To be read first are [topic 35, §2.5](../topics/35-packaging-configuration-and-build.md#25-compiled-kernels-and-their-builds) and [topic 42, §2.5](../topics/42-parallelisation-and-performance.md#25-threads-and-processes-in-python).

**Option A: the versions of the development machine.** Wheels for Python 3.13, 3.14 and 3.14t on macOS and Linux on x86-64, six to a release, each built and tested on the development machine, where the kernels of [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) and [B3E1](../experiments/B03-parallel-execution/E1-speed-up-of-each-means/README.md) ran. **[GK]** For mhdpy, the code keeps to the language of 3.13. On a Mac with an ARM processor, the only kind that Apple has sold since 2023, and on a server with ARM64, an installation falls back to the source and needs a compiler, which breaks the single command.

**Option B: the window of SPEC 0.** Wheels for every version released in the last three years, in both builds where the free-threaded one is supported, on macOS and Linux, each on x86-64 and ARM64: now 3.13, 3.14, 3.14t, 3.15 and 3.15t, twenty to a release. **[GK]** A version is dropped three years after its release by the rule of [SPEC 0](#spec-0), which NumPy, SciPy and Matplotlib endorse and which drops 3.13 in the last quarter of 2027, and a new one joins once NumPy and Cython publish wheels for it. For mhdpy, the single command holds on every Mac and Linux machine and every version that the ecosystem still serves. The code keeps to the language of 3.13, which lacks the deferred annotations of 3.14 ([PEP 649](#pep-649)), so that a name used in an annotation before its definition must be quoted. The wheels for ARM64 are tested only on hosted runners or under emulation, and the development machine must install 3.15 and 3.15t.

**Option C: from 3.14, in both builds.** As option B, but from Python 3.14: now 3.14, 3.14t, 3.15 and 3.15t, sixteen to a release. **[GK]** It is the first version whose free-threaded build is supported. For mhdpy, every version comes in both builds, in each of which threads gain by [B3D1](B03-parallel-execution.md#b3d1-threads-or-processes), and the code may use the language of 3.14. Users of 3.13 must move to a newer version a year before SPEC 0 would drop it. The wheels for ARM64 and for 3.15 are tested as in option B.

**Experiments.** None, since the schedules of CPython and the wheels of NumPy settle what each option serves. Whether wheels of mhdpy build on each version is measured with the build backend.

**Recommendation.** Option C, since its wheels keep the single command on every Mac and Linux machine, which option A gives up, and every version that it serves has a supported free-threaded build, on which threads gained on small grids in [B3E1](../experiments/B03-parallel-execution/E1-speed-up-of-each-means/README.md) where the default build of 3.14 did not. Against option B, it gives up the users of 3.13, whose fixes of bugs have ended, a year before SPEC 0 does, while no release of mhdpy yet exists. The option serves the exception of §1, performance, the second priority, and readability, the third, through the deferred annotations of 3.14, and gives up some usability, the fourth.

**Set aside.** Option B would return if a user needed Python 3.13 before SPEC 0 drops it, late in 2027. Option A would return if wheels for ARM64 could be neither built nor tested on hosted runners or under emulation.

## B4D2 The build backend

**Decision.** In the context of kernels in the pure mode of Cython, built into wheels and an editable installation, facing backends that differ in their tools and in how a change to a kernel reaches the tests, setuptools, with the kernels in `setup.py` and their declarations named as package data (option A), is chosen over meson-python (B) and scikit-build-core (C). This achieves readability, with 11 lines of configuration and Cython alone beside it, and keeps the check of [B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule), accepting a new editable installation after each change to a kernel, which compiles every kernel again. Decided on 2026-11-10, against the recommendation of option C, since scikit-build-core brings with CMake, ninja and cython-cmake far more machinery and options than mhdpy needs.

**Question.** Every kernel is a module of Python that Cython compiles in its pure mode, with its signatures in a file `.pxd` beside it ([B2D2](B02-kernels.md#b2d2-the-compiler-of-the-kernels)), and the build backend turns these modules into extension modules, in the wheels of [B4D1](#b4d1-the-versions-of-python-and-the-platforms) and in the editable installation in which the code is developed. It must be chosen before the first module of stratum 1, as it fixes the files that configure the build, where each new kernel is entered, and how a change to a kernel reaches the tests, which run after every function in the way of working of §2.6. The references compile no module of Python: pyro and Ulula build their packages, pure Python, with setuptools, and Athena++ compiles by a makefile that its script of configuration writes ([topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages), [§2.3](../topics/35-packaging-configuration-and-build.md#23-configuration-at-build-time)). **[GK]** Cython's documentation covers four backends and recommends to new projects those other than setuptools, noting that much of the scientific ecosystem builds with Meson first ([Cython, compilation](#cython-compilation)). Hatchling, the fourth, needs a plugin for Cython and is left out.

**Option A: setuptools.** The backend of pyro and Ulula ([topic 35, §2.1](../topics/35-packaging-configuration-and-build.md#21-python-packages)). **[GK]** Astropy builds its compiled modules with it. A file `setup.py` beside `pyproject.toml` hands the kernels to `cythonize`, as [B2E1](../experiments/B02-kernels/E1-rate-of-each-route/README.md) and the experiments after it did. For mhdpy, every kernel is entered in `setup.py`, and the build needs setuptools and Cython alone. An editable installation, however, holds a compiled module as it was when installed ([setuptools, development mode](#setuptools-editable)), so that a change to a kernel reaches the tests only after a new installation. Cython writes its C beside the sources unless told otherwise.

**Option B: meson-python.** **[GK]** A backend that builds with Meson and ninja, in a folder of its own, from files `meson.build` that name what is compiled and installed, as NumPy, SciPy, scikit-learn, pandas and scikit-image build. Its editable installation rebuilds the compiled modules when the package is first imported in a process, and ninja rebuilds only what changed ([meson-python, editable installations](#mesonpy-editable)). For mhdpy, a change to a kernel reaches the next run of the tests without a step, provided that meson-python, Meson, ninja and Cython stay installed beside the package, as the editable installation is made without build isolation. Meson takes as Cython only files with the suffix `.pyx` ([Meson, Cython](#meson-cython)), so that each module in the pure mode needs a step of its own in `meson.build` that runs Cython on it, and modules of Python are installed only as `meson.build` names them.

**Option C: scikit-build-core.** **[GK]** A backend that builds with CMake from a file `CMakeLists.txt`, through the package cython-cmake for Cython, and installs the folder of the package without a list of its modules. Its editable installation redirects imports to the sources and to a folder of the build, and rebuilds on import only in a mode that it calls very experimental, a rebuild being started by hand otherwise ([scikit-build-core, editable installations](#skbuild-editable)). For mhdpy, CMake joins the tools with a language of configuration of its own, and every kernel is entered in `CMakeLists.txt`. A change to a kernel reaches the tests through the experimental rebuild or a step by hand, and the build tools stay installed beside the package, as for option B.

**Experiments.** [B4E1](../experiments/B04-packaging/E1-builds-of-each-backend/README.md) builds the kernel of [B2E2](../experiments/B02-kernels/E2-declarations-for-cython/README.md) and a copy with each backend on Python 3.14, 3.14t, 3.15 and 3.15t. Every wheel builds and gives the result of plain NumPy exactly, with the GIL disabled in the free-threaded builds, at $8.9$ to $9.8 \times 10^6$ cell updates per second. A change to a module or to its file `.pxd` reaches the next process without a step under meson-python and scikit-build-core, in 5 to 7 s, compiling that kernel alone, but needs a new installation of 9 to 10 s under setuptools, which compiles both kernels again. Import Linter fails under the editable installation of meson-python, whose loader hides the folders of the package. The configuration takes 11, 18 and 17 lines for options A, B and C.

**Recommendation.** Option C, since a change to a kernel then reaches the next run of the tests without a step and compiles that kernel alone, as §2.6 needs after every function, which setuptools does only by a new installation that compiles every kernel again, while the check of [B1D5](B01-strata-in-package.md#b1d5-the-check-of-the-rule) keeps working, unlike under meson-python ([B4E1](../experiments/B04-packaging/E1-builds-of-each-backend/README.md)). The option serves correctness, the first priority of §1, as the rule is checked on the code as developed, and leaves performance, the second, unchanged. It gives up some readability, the third, as CMake joins TOML in the configuration, and leans on a rebuild that its makers call experimental, which a new installation replaces should it fail.

**Set aside.** Option C would return if the new installation after each change grew too slow as the kernels multiply, as scikit-build-core compiles the changed kernel alone, without a step. Option B would return if Import Linter could read a package behind the editable loader of meson-python, whose rebuild on import is stable.
